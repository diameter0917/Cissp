01 — 📌 本日導讀

當偵測邏輯不是你寫的：把 ML 規則收進 SOC 流程

昨天你手寫了 Scheduled 與 NRT 規則——條件是你定的、門檻是你設的、誤報也是你自己扛。今天要看 Microsoft Sentinel 裡另外三種你寫不出來的規則：Fusion（多階段攻擊偵測，用機器學習把跨來源的低訊號串成一條攻擊鏈）、UEBA（實體行為分析，替每個使用者與裝置養出行為基準線）、Anomaly（異常規則，Microsoft 提供、參數可調的 ML 範本）。三者的共同特徵是：邏輯封裝在模型裡，你能調的是輸入的資料、門檻與例外，不是查詢本身。考試最愛問這個分界——什麼情況該寫 Scheduled 規則、什麼情況該交給 ML，以及 UEBA 啟用後為什麼前幾週安安靜靜。另一條主線是誤報處理三段式：先調規則、再用自動化規則自動關閉、最後才動抑制。

學習目標（對應官方考綱 D2「回應安全性事件」）：
  • ☐ 說明 Fusion 多階段攻擊偵測的運作前提、資料來源需求與調校方式（對應考綱 configure analytics rules in Microsoft Sentinel）
  • ☐ 完成 UEBA 啟用前置：選定資料來源、同步 Microsoft Entra ID 目錄資料
  • ☐ 判讀 BehaviorAnalytics 表、investigation priority score 與 peer group 分析結果
  • ☐ 用 flighting 模式調整 Anomaly 規則門檻，並在 Anomalies 表中驗證效果
  • ☐ 比較 Scheduled、Fusion、UEBA、Anomaly 四種規則的觸發方式與適用時機

03 — 🧬 Fusion

把一堆「還好啦」串成一條攻擊鏈

Fusion（進階多階段攻擊偵測）是 Sentinel 內建的關聯型 ML 規則：它不看原始記錄，而是吃其他偵測產生的警示與異常，用機器學習判斷這些散落在不同產品、不同時間點的低嚴重性訊號，是否其實屬於同一條攻擊鏈（例如「可疑登入 → 異常的收件匣規則建立 → 大量檔案下載」）。命中時會產生一個高或中嚴重性的事件，名稱通常長得像「偵測到多個可能與……活動相關的警示」，而且事件描述會告訴你它把哪幾則警示串在一起、對應哪些 MITRE ATT&CK 戰術。

三個必記的設計事實：
① Fusion 預設啟用，而且每個工作區只有一條，你不能自己建第二條、也不能改它的查詢。
② 它只在訊號夠多元時才有價值——你必須先接上多個資料來源（Microsoft Entra ID Protection、Defender for Cloud Apps、Defender for Endpoint、Defender for Identity、Defender for Office 365、Defender for Cloud，以及你自己的 Scheduled 規則等）。只接一個來源的工作區，Fusion 幾乎永遠不會觸發。
③ 你自訂的 Scheduled 規則要被 Fusion 納入關聯，必須做好實體對應與 MITRE 戰術對照——沒有實體，模型就無法把它和其他警示縫在同一個使用者或主機上。

Fusion for emerging threats（新興威脅的 Fusion 偵測）是同一引擎的延伸：不依賴既有的攻擊情境樣板，而是從更廣的訊號裡找出「看起來像新型態攻擊」的組合，對應勒索軟體等快速演化的手法；代價是誤報率相對較高，實務上先觀察一段時間再納入正式 SLA。

調校怎麼做？你改不了模型，但有三個旋鈕：其一，在 Fusion 規則的設定裡排除特定偵測樣式或來源訊號——某條自家 Scheduled 規則一直帶進雜訊，就把它從 Fusion 的輸入中排除；其二，回頭修正上游規則（誤報的根在來源警示，不在 Fusion）；其三，若某情境確定是預期行為（例如弱點掃描主機每晚的動作），用監視清單（Watchlist）搭配上游規則的排除條件處理，而不是把整條 Fusion 關掉。

🛡️ 實戰情境：讀懂一個 Fusion 事件

週四早上，佇列出現一個中嚴重性事件，來源顯示為 Fusion，標題是「偵測到多個可能與資料外洩活動相關的警示」。點開後，裡面有三則警示，單獨看每一則你昨天都會直接關掉：

  1. Entra ID Protection｜不熟悉的登入屬性（低）——使用者 k.tsai 從新的 ASN 登入，但通過了 MFA。單看：出差很常見。
  2. Defender for Cloud Apps｜建立可疑的收件匣轉寄規則（低）——一小時後，同一帳號建立了把含「invoice」字樣的信轉到外部信箱並標為已讀的規則。單看：使用者自己設的自動化，也不是沒見過。
  3. 你自己寫的 Scheduled 規則｜單一使用者大量 SharePoint 下載（中）——再兩小時後，同帳號在 20 分鐘內下載 480 個檔案。單看：季末財務報表整理期，常被當雜訊。

Fusion 做了什麼？它認出這三則警示共用同一個使用者實體、時間上前後相接、而且分屬初始存取 → 持續性／規避 → 外洩三個相鄰戰術——正是帳號接管後竊資的典型序列。單一訊號的嚴重性是低、低、中，串起來卻是一條完整的攻擊鏈。

分診怎麼走？(1) 先看事件描述列出的警示組合與戰術順序，確認「故事」說得通；(2) 到 k.tsai 的實體頁面看行為時間軸，比對這幾個動作是否偏離他自己與同儕的常態；(3) 驗證那條轉寄規則是否仍存在、外部信箱是誰；(4) 若成立，分類 True positive、判定「遭入侵帳戶」，並重設密碼、撤銷工作階段、移除轉寄規則。反過來說，若查出三個動作全來自公司資料移轉專案（有變更單、IT 帳號代操），分類就是 Informational, expected activity，接著把該情境從上游 Scheduled 規則排除，而不是抱怨 Fusion 亂報。

🎯 考點聚焦
題型一：「事件由多個不同產品的低嚴重性警示組成，且被自動標示為多階段攻擊，這是哪一種規則？」→ Fusion。關鍵字是多階段（multistage）、跨來源關聯、低嚴重性警示組合。
題型二：「Fusion 已啟用卻從未產生事件，該怎麼辦？」→ 不是去調門檻（沒有門檻可調），而是檢查資料來源是否足夠、上游規則是否設定了實體對應與戰術對照。
陷阱：「建立新的 Fusion 規則」永遠是錯的——每個工作區只有一條且預設存在；「把 Fusion 關掉來消除誤報」也是錯的，正解是排除特定偵測樣式或修正上游規則。
04 — 👤 UEBA

先養基準線，才有異常可談

UEBA（使用者與實體行為分析）回答的問題和 Fusion 不同：Fusion 問「這些警示是不是同一起攻擊」，UEBA 問「這個人今天的行為，跟他自己的過去、跟他的同儕比，正不正常」。它不靠特徵碼，靠的是每個實體的行為基準線。

啟用不是按一個開關而已，前置有三件事：(1) 具備足夠權限（啟用需要租用戶層級的管理角色，一般 Sentinel 參與者改不了）；(2) 勾選要分析的資料來源——典型是登入記錄（含非互動式、服務主體與受控識別）、稽核記錄、Azure 活動記錄與 Windows 安全性事件；(3) 同步 Microsoft Entra ID 目錄資料，讓 UEBA 拿得到部門、主管、群組成員資格，才能做同儕比較與帳號擴充。

啟用之後會多出幾張表：BehaviorAnalytics（每一筆被擴充過的行為事件，附帶 insights 與分數）、IdentityInfo（同步進來的身分中繼資料，搜捕時拿來擴充帳號屬性非常好用）、UserPeerAnalytics（同儕群組排名）。investigation priority score 是每筆活動被賦予的 0–10 分數，代表「這個動作有多值得你花時間看」，計算依據包含偏離自身基準線的程度、偏離同儕的程度、行為本身的敏感度，以及是否為首次出現（首次從某國家登入、首次執行某動作、首次使用某裝置）。

BehaviorAnalytics
| where TimeGenerated > ago(7d)
| where InvestigationPriority > 5
| summarize TotalScore = sum(InvestigationPriority),
            Events = count(),
            Actions = make_set(ActionType, 8)
        by UserPrincipalName
| order by TotalScore desc
| take 20

這段是「本週最該看誰」的排行榜。重點在 sum() 而非 max()——單一高分活動可能只是出差，但一個帳號在七天內累積出一堆中高分活動，才是帳號被接管的樣子。make_set(ActionType, 8) 讓你不用點開就看到他做了哪幾類動作。分數不是判決，只是排序工具：當成分診佇列的補充維度，接著仍要進實體頁面看行為時間軸與同儕比較。

peer group 分析的意義：同一個「存取財務共用資料夾」的動作，發生在財務部三十個人身上是常態，發生在剛報到的行銷實習生身上就是異常。UEBA 依目錄資料（同部門、同主管、同群組）建立同儕群組，讓「異常」有相對基準，而不是全公司一把尺。這也是為什麼目錄同步沒做好，UEBA 的判斷品質會直接崩掉。
🎯 考點聚焦
「UEBA 啟用兩週了，BehaviorAnalytics 幾乎沒有有意義的結果，為什麼？」這是高頻題，正解有兩層：
① UEBA 不回填歷史——啟用當下才開始寫入 BehaviorAnalytics，之前的記錄不會被追溯分析。
② 基準線需要養成期——模型必須先觀察一段時間（依 insight 類型不同，從數天到數週）才知道什麼叫「這個人的常態」；養成期內大量活動會被視為「首次出現」，分數失真，此時不該拿它當告警依據，也不該急著關掉功能。
其他錯誤選項的長相：「增加保留期」（保留期管的是資料留多久，不會讓分析變準）、「重新部署資料連接器」（連接器正常時無效）、「提高 investigation priority 門檻」（結果本來就少，調高只會更少）。正解方向永遠是確認資料來源已勾選、目錄已同步，然後給它時間。
05 — 📈 異常規則

可調參數的 ML 範本與 flighting 模式

Anomaly（異常）規則是介於 Scheduled 與 Fusion 之間的第三條路：模型由 Microsoft 提供並訓練（例如異常的登入、異常的資源建立、異常的 RDP 或 SSH 行為），但參數開放給你調——觀察窗長度、最少事件數、分數門檻、要不要排除特定帳號或 IP 範圍。範本標有需要的資料來源，接錯連接器就不會有結果。

兩個最會考的行為特性：
① 異常規則預設不直接產生事件：命中結果寫進 Anomalies 表，供搜捕、調查擴充，或當成 Scheduled 規則的輸入（把 Anomalies 和其他表 join 起來再告警）。想讓它變成事件，就寫一條 Scheduled 規則去查 Anomalies。
② flighting（測試）模式：當你調整一條異常規則的參數，Sentinel 會保留原本的 production 版本，另外跑一份 flighting 版本。兩份結果同時寫進 Anomalies 表並以欄位標示來源版本，你可以在同一段時間窗裡直接比較「調參後噪音降了多少、真陽性有沒有被誤殺」，滿意後再把 flighting 版本推上 production。
Anomalies
| where TimeGenerated > ago(14d)
| summarize Hits = count(), MaxScore = max(Score), Users = dcount(UserPrincipalName)
        by RuleName, RuleStatus
| order by RuleName asc, RuleStatus asc

這是調參前後的對照表：同一條 RuleName 會出現 production 與 flighting 兩列，直接比 Hits 與涉及人數。判讀原則是「量要降、質要留」——若 flighting 命中數從每天 300 降到 20，而已知的真陽性案例仍在名單裡，就可以推上 production；真陽性一起消失，代表門檻拉過頭。這種先觀察、再生產的節奏，是 ML 規則和手寫規則最大的操作差異。

什麼時候用邏輯明確、可寫成條件的已知威脅與合規要求要看見「單看都不嚴重、合起來很嚴重」的跨產品攻擊內部威脅、帳號接管，需要「相對於常態」的判斷沒有明確門檻、要靠統計找出離群值的場景

一句話判準：寫得出條件的，用 Scheduled；寫不出條件、只能說「這不像他平常會做的事」的，交給 UEBA 或 Anomaly；跨產品、跨時間的串鏈，交給 Fusion。它們不是替代關係——你的 Scheduled 規則正是 Fusion 的原料，UEBA 分數與 Anomalies 結果又能回頭餵進 Scheduled 規則變成高信心告警。

誤報處理三段式（順序不能顛倒）：
① 規則調校——治本。改查詢排除已知良性來源、拉高門檻、修好實體對應，或調整 Anomaly 參數。
② 自動化規則自動關閉——治標但可稽核。當某類事件確定良性又無法完全排除（例如特定弱點掃描主機），用自動化規則依條件比對後自動變更狀態為已關閉並填上分類，事件仍留有紀錄可回溯。
③ 抑制——最後手段。Scheduled 規則可設定「產生警示後暫停查詢一段時間」，避免同一波活動在短時間內重複產生大量事件；它壓的是數量不是對錯，用久了會遮住真攻擊。

資料品質是 ML 的天花板：連接器中斷幾天，UEBA 基準線會出現空洞、Fusion 少了半條鏈；時區或時間戳錯誤會讓「時間鄰近性」判斷失準；自訂記錄沒有正規化欄位，實體就對應不上，等於不存在於模型眼中。所以題目問「ML 偵測品質不佳，第一步做什麼」，答案通常不是調模型，而是確認資料完整性與實體對應。

07 — 🧩 考綱補洞

EP9 沒細講、考題卻會碰的

  • Microsoft security 規則類型：把 Microsoft 安全性解決方案（Defender 各產品、Entra ID Protection 等）產生的警示原封不動轉成 Sentinel 事件，可依嚴重性或警示名稱篩選。它不做關聯也不做評分——這正是它和 Fusion 的分界。
  • ML Behavior Analytics 範本：針對特定情境（如異常的 SSH／RDP 登入）的機器學習範本，同樣不可改查詢，只能啟用或停用。
  • 威脅情報比對規則：拿威脅情報指標比對記錄產生警示，屬規則型而非 ML，別和異常規則混淆。
  • 實體頁面的行為時間軸：使用者或主機的實體頁面把警示、書籤與 UEBA 行為洞察畫在同一條時間軸上並可切換時間範圍，調查帳號接管時比翻查詢快得多。
  • UEBA 與 Defender XDR 的分工：Entra ID Protection 的使用者風險等級、Defender for Identity 的身分態勢，和 Sentinel UEBA 是三種不同來源的分數；UEBA 的優勢是涵蓋你自己接進工作區的記錄並做同儕比較。
  • 成本觀點：UEBA 擴充資料與 Anomalies 都會寫進工作區，計入擷取與保留成本——勾選資料來源同時是成本決策。
