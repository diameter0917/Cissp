03 — 🌦️ 威脅情報基礎

情資是 SOC 的氣象預報：生命週期與 IoC 類型

把威脅情報想成氣象預報：它不能阻止暴風雨（攻擊者），但能告訴你哪裡正在下雨、暴風往哪走，讓你決定要不要收衣服、封港口。CTI（cyber threat intelligence）依受眾分三層：戰略情報給管理層看趨勢與風險、作戰情報描述攻擊者的活動與 TTP（戰術、技術與程序）、戰術情報就是機器可比對的 IoC——SC-200 的主場在戰術層。情報不是一張靜態清單，而是一個循環的生命週期：規劃與方向（要保護什麼、回答什麼問題）→ 收集（訂閱來源、感測器）→ 處理（正規化成 STIX 等標準格式）→ 分析（從資料變成可行動的判斷）→ 散播與回饋（送到 SIEM 比對、誤判回饋修正）。今天學的匯入、比對、失效管理，正好對應收集、散播與回饋三段。

戰術情報的主角是四大 IoC 類型，各自的「壽命」與精準度差很多：

IoC 類型範例特性與壽命
檔案雜湊（file hash）SHA256／SHA1／MD5最精準、零誤判空間；但攻擊者改一個位元組雜湊就全變，壽命最短
IP 位址C2 伺服器、掃描來源 IP易比對；雲端 IP 快速輪替、也可能是共用主機，誤判風險與時效問題最大
網域名稱（domain）釣魚網域、C2 網域攻擊者換網域比換 IP 貴一點，壽命中等；DNS 記錄是主要比對面
URL完整釣魚頁面連結最具體、指向單一攻擊資源；變形容易，常大量出現又快速失效
💡 記法（痛苦金字塔的精簡版）：越容易比對的指標，攻擊者也越容易換掉。雜湊與 IP 在金字塔底層、說換就換；TTP 在塔頂、攻擊者最難改——所以 IoC 比對要靠「持續更新的餵送」而不是一張永久清單，這正是連接器存在的理由。也因此每個指標都帶有效期（valid until）與信賴度（confidence），過期指標要能自動退場。
04 — 🚚 匯入三路徑

把情資弄進 Sentinel：三條路怎麼選

Sentinel 的威脅情報管理（intel management）頁面可以手動建立、編輯、標籤、失效個別指標——但手動只適合零星補刀。規模化匯入靠三條路，考題幾乎都是「給你來源型態、選匯入方式」：

面向STIX／TAXII 連接器上傳 API（upload API）MDTI 資料連接器
運作方向拉（pull）：Sentinel 依輪詢頻率定期向 TAXII 伺服器取指標推（push）：你的 TIP（威脅情報平台）或指令碼主動呼叫 API 送進來微軟自家情資自動流入，啟用即用
典型來源產業 ISAC、商業情資供應商、開放來源（提供 TAXII 2.0／2.1 服務者）MISP、Anomali、ThreatConnect 等 TIP 產品，或自寫整合Microsoft 研究團隊策展的高信賴 IoC
你要準備什麼API 根 URL＋集合（collection）ID＋帳密、輪詢頻率Microsoft Entra 應用程式註冊，並授與工作區 Microsoft Sentinel Contributor 角色幾乎不用——安裝解決方案、啟用連接器
支援內容STIX 格式指標STIX 2.1 物件：除了指標，還能送威脅執行者、攻擊模式、關係（relationship）等物件微軟管理的指標餵送（免額外擷取費用）
一句話記憶「訂報紙」：對方出版、你定時去拿「投稿」：你這邊主動推送「微軟直送」：開箱即用的基本盤
🎯 考點聚焦
匯入方式題的關鍵詞對照：題幹出現「API root URL＋collection ID」→ 答案是 TAXII 連接器，這兩個名詞幾乎只在 TAXII 情境出現。題幹說組織用 MISP／自家 TIP、要「推送」指標、或提到「應用程式註冊（app registration）」→ 上傳 API（舊的 Threat Intelligence Platforms 連接器走 Graph tiIndicators API，已淘汰，出現時視為干擾項）。題幹要「不額外採購、快速取得微軟高信賴指標」→ MDTI 連接器。陷阱：題目給的是內部業務清單（VIP、離職員工、允許的 IP）——那不是威脅情報，正解是監視清單（Watchlist），別被「清單」兩個字騙去選 TI 匯入。
05 — 🔭 MDTI 是什麼

微軟自家的情資工廠：文章、intel profiles 與網際網路地圖

Microsoft Defender Threat Intelligence（MDTI）是微軟的威脅情報產品，把微軟每天處理的數十兆安全訊號、收購 RiskIQ 得到的網際網路測繪資料，加上研究團隊的分析，做成「成品情資（finished intelligence）」。在 Defender portal 的威脅情報區你會用到四樣東西：

  • 情資文章（articles）：研究團隊對新活動、新弱點的分析文章，文末附可直接取用的 IoC 清單。
  • Intel profiles：威脅執行者、工具與弱點的「檔案卡」——這個攻擊者是誰、打哪些產業、用什麼 TTP、關聯哪些指標。
  • Intel explorer：網際網路地圖查詢——輸入網域或 IP，看歷史 DNS 解析（passive DNS）、WHOIS、憑證、關聯基礎設施，把攻擊者「換皮不換骨」的基礎設施挖出來。
  • Intel projects：把調查中蒐集的指標收進專案，團隊共用。

標準版 vs 進階版：標準版免費隨 Defender portal 提供，包含開放來源情資、有限的文章與 intel profiles 存取；進階版（premium）需授權，解鎖完整文章庫、全量 IoC、以及最有價值的網際網路資料集（passive DNS、憑證、WHOIS 歷史）。近年微軟持續把 MDTI 能力併入 Defender XDR 與 Security Copilot 的體驗中，考題重點放在「MDTI 能回答什麼問題」而不是購買細節。與 Sentinel 的整合就是上一節的 MDTI 資料連接器：把微軟指標餵進你的工作區參與比對。

🎯 考點聚焦
MDTI vs Sentinel 威脅情報管理的分工——一句話：MDTI 是「情資的生產者與百科」，Sentinel intel management 是「你家情資的營運中心」。題幹問「調查某網域的歷史解析、WHOIS、關聯基礎設施」「想看某威脅執行者的檔案與 TTP」→ 選 MDTI（Intel explorer／intel profiles）。題幹問「把 ISAC 給的指標拿來對自家記錄比對、產生事件」「幫指標加標籤、設定失效」→ 選 Sentinel 威脅情報管理＋TI map 規則。干擾項常放 Defender XDR 的 threat analytics（威脅分析）——它講的是「微軟追蹤的活動對你的組織的曝險與影響」，不是可查詢的網際網路資料集，方向不同。
06 — 🎯 TI 驅動偵測

指標進了表，還要規則來比對

匯入的指標落在工作區的 ThreatIntelIndicators 表（每列一個指標，觀測值放在 ObservableKey／ObservableValue），非指標的 STIX 物件（威脅執行者、關係等）放在 ThreatIntelObjects 表。舊表 ThreatIntelligenceIndicator（欄位長相是 NetworkIP、DomainName 那一代）已走入退場時程——考題兩個名字都可能出現，認得出「新舊」即可。先學會盤點自家指標：

// 盤點目前有效的 IP 指標：每個指標只留最新版本
ThreatIntelIndicators
| where TimeGenerated > ago(30d)
| where ObservableKey == "ipv4-addr:value"
| summarize arg_max(TimeGenerated, *) by Id
| where IsActive == true and ValidUntil > now()
| project ObservableValue, Confidence, Tags, ValidUntil, SourceSystem
| take 20

逐行解說：第 3 行用 ObservableKey == "ipv4-addr:value" 篩出 IP 型指標（網域是 domain-name:value、檔案雜湊是 file:hashes.'SHA-256' 這類 STIX 寫法）；第 4 行是關鍵——同一指標更新或重新發佈時會多一列，summarize arg_max(TimeGenerated, *) by Id 依指標 Id 只留最新版本，這是查新表的標準起手式；第 5 行再過濾「仍然有效」：IsActive 為真且 ValidUntil 還沒過期——別拿過期指標去比對，那是誤判製造機。

盤點完就能比對。TI 偵測的主力是內容中樞（Content Hub）Threat Intelligence 解決方案附的 TI map 系列規則範本：「TI map IP entity to CommonSecurityLog」「TI map Domain entity to DnsEvents」⋯⋯命名規律是「拿哪種指標、對哪張表」。它們是排程分析規則，背後的查詢邏輯就像這樣：

// TI map 的核心邏輯：拿有效 IP 指標對防火牆記錄
let bad_ips = ThreatIntelIndicators
    | where TimeGenerated > ago(30d)
    | where ObservableKey == "ipv4-addr:value"
    | summarize arg_max(TimeGenerated, *) by Id
    | where IsActive == true and ValidUntil > now()
    | project BadIp = ObservableValue, Confidence;
CommonSecurityLog
| where TimeGenerated > ago(1d)
| where isnotempty(DestinationIP)
| join kind=inner bad_ips on $left.DestinationIP == $right.BadIp
| project TimeGenerated, DeviceVendor, SourceIP, DestinationIP, DestinationPort, Confidence
| order by TimeGenerated desc

逐行解說：前段用 let 把「目前有效的壞 IP」存成 bad_ips，並 project 改名成 BadIp；後段從 CEF 防火牆記錄（CommonSecurityLog，昨天接的）出發，join kind=inner ... on $left.DestinationIP == $right.BadIp 做欄位名不同時的等值 join——命中就代表內網有裝置連向情資標記的位址。TI map 規則要能運作，兩邊都要有資料：指標來源（任一匯入路徑）＋對應的記錄表，缺一邊規則就是空轉，這是考題最愛的陷阱。另外微軟還有一條內建的 Microsoft Threat Intelligence Matching Analytics 規則，自動拿微軟指標對 CEF、DNS、Syslog 比對，不用自己寫。

07 — 📋 Watchlists 實戰

SOC 的合法小抄：建立、查詢、進規則

威脅情報處理「外面的壞東西」，監視清單（Watchlist）處理「你自己知道的事」：VIP 名單、離職員工、允許的掃描器 IP——這些業務脈絡不會出現在任何情資餵送裡，但偵測邏輯少了它們就會又聾又瞎。把 watchlist 想成 SOC 的合法小抄：把小抄夾進查詢，規則就懂得「這個帳號惹不起、那個 IP 不用理」。

建立：在 Sentinel 的 Watchlist 頁面用精靈上傳 CSV，設定三件事——名稱、別名（alias，之後查詢用它）、SearchKey（指定最常拿來 join 的欄位，引擎會最佳化它的查詢效能）。建立後可在 UI 直接增刪改單筆項目，不必改任何規則——清單內容與偵測邏輯解耦，這就是 watchlist 相對於把名單寫死在 KQL 裡的最大優勢。

📌 上限備忘：精靈直接上傳的 CSV 上限約 3.8 MB；更大的檔案（至 500 MB）走 Azure 儲存體＋SAS URL 的大檔路徑。清單要頻繁自動更新時，可用 Logic Apps 或指令碼呼叫 watchlist API 維護。

查詢：用 _GetWatchlist('別名') 把清單當成表來用。經典場景——VIP 帳號的登入失敗監控：

// VIP 使用者短時間多次登入失敗（可能是針對性密碼攻擊）
let vips = _GetWatchlist('VIPUsers')
    | project VipUpn = tostring(SearchKey);
SigninLogs
| where TimeGenerated > ago(1d)
| where ResultType != "0"
| join kind=inner vips on $left.UserPrincipalName == $right.VipUpn
| summarize FailedCount = count(), SourceIPs = make_set(IPAddress, 10) by UserPrincipalName
| where FailedCount >= 5

逐行解說：第 2–3 行取出 watchlist，SearchKey 是建立時指定的搜尋鍵欄位（這裡放 UPN），用它 join 效能最好；第 5–6 行只看過去一天的失敗登入（SigninLogs 的 ResultType == "0" 是成功，其餘是各種失敗碼）；第 7 行把登入記錄與 VIP 名單 inner join——非 VIP 的失敗全被濾掉；第 8–9 行統計每個 VIP 的失敗次數與來源 IP 集合，超過 5 次才浮出。把這段查詢貼進排程分析規則，就是「watchlist 在分析規則中的應用」：規則邏輯不動，名單在 UI 隨時維護。

常見場景速覽：VIP 使用者（高價值帳號給更低的告警門檻）、已知壞 IP／允許 IP（小規模自管黑白名單與降噪）、新進與離職員工（新人是釣魚高風險群、離職者不該再有登入）、資產富化（把主機對應的負責人、重要性等業務欄位 join 進告警）。

🎯 考點聚焦
watchlist vs 威脅指標怎麼分：資料是外部威脅觀測值（惡意 IP／網域／雜湊，帶信賴度與有效期、要參與 TI map 比對）→ 匯入為威脅指標；資料是內部業務清單（人、資產、白名單，要在查詢裡 join、要隨時手動維護）→ watchlist。第二個分辨點：題幹強調「分析師要能自行更新清單、不改規則」→ watchlist；強調「自動失效、來源信賴度」→ 威脅指標。兩者都不是「自訂表」——干擾項給你 DCR 自訂記錄表時，記住 watchlist 免擷取管線、UI 可編輯，內部小清單它永遠是最省事的正解。
08 — 🛡️ 實戰情境

ISAC 寄來一包 IoC，完整處理流

🛡️ SOC Walkthrough：從收件到回饋

你是金融業 SOC 的分析師。產業 ISAC 發佈緊急通告：一波針對金融業的活動，附上 IoC 清單（180 個 IP、40 個網域、25 個 SHA256），並提供其 TAXII 2.1 服務的 API 根 URL 與集合 ID。你的環境：Sentinel 已接 CEF 防火牆（CommonSecurityLog）與 DNS 記錄。走一遍完整處理流：

  1. 選匯入路徑：ISAC 有 TAXII 服務 → 設定 TAXII 連接器建立長期訂閱（填 API 根 URL、集合 ID、帳密、輪詢頻率），之後的更新自動進來；這次通告附的 CSV 若要立刻生效，少量可在威脅情報頁面手動建立、量大用上傳 API 推入。
  2. 加標籤與有效期：為這批指標加 tags（如 ISAC-2026-08、活動代號），沿用來源給的有效期——之後追蹤「這波活動命中幾次」全靠標籤。
  3. 驗證入庫：用第 06 節的盤點查詢確認 ThreatIntelIndicators 出現新指標、SourceSystem 正確。
  4. 啟用比對規則：環境有 CommonSecurityLog 與 DNS → 從範本啟用「TI map IP entity to CommonSecurityLog」與 domain 對 DNS 的規則；沒有對應資料表的規則不用開（開了也是空轉）。
  5. 回溯搜捕：規則只看未來，過去呢？拿同一段 join 查詢把時間拉長回查 30 天——確認這波活動是否早已進門。命中的話開事件、進分診流程。
  6. 回饋修正：三天後某個 IP 頻繁誤判（其實是合作夥伴的共用出口 IP）——回到威脅情報管理頁把該指標設為失效，規則與其餘指標不動。這一步就是生命週期的「回饋」：情資是活的，要營運。
