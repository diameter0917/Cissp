01 — 📌 本日導讀

分診：把一堆警示收斂成一個講得清楚的攻擊故事

今天進入第二大領域 D2「回應安全性事件」（35–40%），第一道關卡是分診（triage）：打開 defender.microsoft.com，佇列裡幾十個事件、幾百則警示，你先看哪一個、怎麼判斷、判斷完留下什麼紀錄。重點有三：第一，警示（alert）與事件（incident）的關係——關聯引擎如何把跨產品警示縫成攻擊故事（attack story）；第二，佇列管理動作——篩選、指派、狀態流、標籤、合併、命名，以及 2026 新考點 內嵌 Security Copilot 的事件摘要；第三，分類（classification）與判定（determination）對照，加上 tier-1 收斂與升級 tier-2 的判準。考題幾乎都是情境題：給你一個多警示事件，問「下一步做什麼」或「該如何分類」。

學習目標（對應官方考綱 D2「回應安全性事件」）：
  • ☐ 說明警示如何關聯成事件、嚴重性如何決定（對應考綱 respond to alerts and incidents identified by Microsoft Defender XDR）
  • ☐ 用篩選、指派、狀態與標籤管理佇列，並判斷何時該合併事件
  • ☐ 依資產重要性、攻擊階段、使用者風險與訊號多樣性排出處理順序
  • ☐ 用攻擊故事圖、警示時間軸、實體窗格與 Go hunt 完成一次調查
  • ☐ 正確選擇 true positive／informational, expected activity／false positive 及其子判定
  • ☐ 說明內嵌 Security Copilot 事件摘要在分診中的定位（對應考綱 manage and investigate threats by using Microsoft Security Copilot）

03 — 🧵 警示與事件

關聯引擎怎麼縫出攻擊故事

先排好名詞階梯：遙測（raw event）被偵測邏輯命中後產生一則警示（「這個行為可疑」）；關聯引擎再把相關警示歸成一個事件（「這是同一起攻擊」）。分析師的工作單位是事件——題目問「橫跨郵件與端點的攻擊該從哪裡開始查」，答案永遠是統一佇列中的那個事件，不是逐一翻各產品的警示清單。

關聯依據有三類：共同實體（同一裝置、使用者、信箱、檔案雜湊、IP／URL）、時間鄰近性、攻擊鏈邏輯（前後警示分屬 MITRE ATT&CK 相鄰戰術）。因此一個事件裡可同時出現 MDO 的釣魚郵件、MDE 的惡意程序、MDI 的帳號列舉、MDA 的異常下載、Entra ID Protection 的高風險登入，甚至 Purview DLP 的原則命中；工作區連入統一入口後，Microsoft Sentinel 分析規則的事件也進同一條佇列。

面向警示（alert）事件（incident）
產生者各產品偵測邏輯、自訂偵測、分析規則關聯引擎自動產生，或分析師手動合併
語意單點訊號完整攻擊故事
嚴重性偵測邏輯給定：高／中／低／資訊取所含警示的最高嚴重性
狀態新增 → 進行中 → 已解決作用中 → 進行中 → 已解決
分診角色證據與時間軸的來源指派、SLA 與結案單位

手動合併（merge）：同一波攻擊可能因時間拉長或實體沒接上而被拆成兩件，可在佇列勾選多個事件合併，被併入者轉為已解決並指向主事件。但入口沒有「拆分事件」的動作，合併前務必確認是同一起攻擊。

🎯 考點聚焦
嚴重性怎麼算：事件嚴重性＝所含警示的最高嚴重性，不是平均、不是數量多寡。題幹寫「事件含 12 則低嚴重性與 1 則高嚴重性警示」→ 事件嚴重性是高。延伸：新的高嚴重性警示關聯進來會把事件拉高；反之把警示標為誤判不會自動下修事件嚴重性。
04 — 🚦 佇列管理

篩選、指派、狀態流與標籤

佇列動作分兩半：篩選排序決定你怎麼看，指派、狀態與標籤決定團隊怎麼記。

  • 篩選：嚴重性／狀態／指派對象是三件組。「指派給我 ＋ 進行中」是個人工作清單；「未指派 ＋ 作用中 ＋ 高」是 tier-1 每天要清空的收件匣。
  • 篩選：服務來源與偵測來源（MDE、MDO、MDI、MDA、Entra ID Protection、Defender for Cloud、Sentinel），並可篩「多重服務來源」——幾乎等於「跨產品的真攻擊」。其餘維度：受影響資產／裝置群組、標籤、分類、自動調查狀態、資料敏感度。
  • 指派：一個事件一個擁有者，認領當下就把狀態改為「進行中」避免重工，這是「下一步該做什麼」的常見正解。
  • 狀態流：作用中 → 進行中 → 已解決。解決時要填分類，並可把結果套用到事件內的警示；日後若有新的相關警示關聯進來，已解決的事件可能被重新啟動。
  • 標籤：自訂文字標記（如 VIP-user、phishing-0817）可作篩選條件，Sentinel 自動化規則也能拿它當觸發條件；系統也會自動貼標籤（例如自動攻擊中斷）。
  • 命名：系統依偵測來源、攻擊類別與受影響資產自動命名（如「涉及多個端點的多階段事件」），可改成團隊看得懂的描述。
2026 的新同事：內嵌 Security Copilot 2026 新考點
事件的摘要面板可由 Security Copilot 產生自然語言事件摘要（把警示、實體與時序寫成一段人話），並以引導式回應建議下一步；另有代理式（agentic）分診能力，例如自動處理使用者回報的釣魚郵件並附上判定理由。考點記法：Copilot 產出的是摘要與建議，不是判決——分類、指派與回應仍由分析師負責，且只呈現使用者權限內的資料。
05 — ⚖️ 優先排序

嚴重性只是起點，不是順序

佇列裡同時躺著五個高嚴重性事件時，嚴重性就沒有排序能力了。真正的順序來自下表的綜合判斷。

判斷因素怎麼看提高優先度的訊號
資產重要性網域控制站、財務系統，還是訪客筆電命中被標記為關鍵資產的系統或特權帳號
攻擊階段類別欄顯示涵蓋哪些 MITRE 戰術已推進到憑證存取、橫向移動、外洩或影響
使用者風險Entra ID Protection 風險等級、是否特權帳號高風險使用者、全域管理員
訊號多樣性是否含多個服務來源的警示「多重服務來源」通常代表真攻擊
影響廣度受影響裝置、使用者、信箱數同一封信寄給 200 人、多台裝置同雜湊
自動化狀態自動調查或自動攻擊中斷是否已介入尚未被處置者優先，已中斷者跟進即可

一句話原則：先看「已推進到深層戰術、打在重要資產或特權帳號、又有多產品同時示警」的事件；單一低嚴重性、來源單一的，留到批次時間再收斂。

🎯 考點聚焦
解題順序：(1) 刪掉純資訊性與環境雜訊；(2) 比攻擊階段——有橫向移動或外洩跡象的贏過只有初始存取嘗試的；(3) 比資產與帳號重要性；(4) 平手看影響廣度。陷阱選項：「先處理警示數量最多的」（可能只是同一則雜訊重複觸發）、「先處理最新的」（時間新舊不代表風險）、「先處理已被自動攻擊中斷處置的」（路徑已切斷，該做的是驗證收尾，不是插隊）。
06 — 🔍 調查工具

攻擊故事圖、時間軸、實體窗格與 Go hunt

點進事件後，上方索引標籤就是工具箱——要知道哪個標籤回答哪個問題：

工具回答什麼分診怎麼用
攻擊故事圖發生了什麼、順序、牽連到誰第一眼看：節點是實體、連線是關係，可展開程序樹
警示清單哪些偵測命中、來源與嚴重性確認是否為多產品關聯
警示時間軸單一警示的前因後果找出真正的初始存取點
資產哪些裝置、使用者、信箱受影響估算影響廣度與是否升級
實體側邊窗格這個節點的來歷與可執行動作點任一節點就開，看風險等級並就地動作
調查／證據與回應自動調查做了什麼、牽涉哪些檔案與 IP避免重工，逐項確認實體
摘要一頁看完重點交接與寫紀錄最省時，Copilot 摘要也在此

Go hunt 是分診與搜捕之間的橋：在圖上對某實體按 Go hunt，系統會帶著它生成一段進階搜捕查詢，把範圍從「這個事件」擴大到「整個租用戶還有誰中了」。例如對寄件者做擴散確認：

EmailEvents
| where Timestamp > ago(7d)
| where SenderFromAddress == "billing@contoso-invoices.com"
| summarize Recipients = dcount(RecipientEmailAddress),
            Delivered = countif(DeliveryAction == "Delivered")
        by Subject
| order by Recipients desc

這段回答分診最關鍵的問題：「這是一封信，還是一波攻擊？」dcount 算收件人數、countif 算真的進到信箱（而非被攔截）的數量。若是 1 人且已攔截，可低調收尾；若是 180 人、60 封成功遞送，那就是該升級的釣魚 campaign。

分診的節奏感：攻擊故事圖看全貌（30 秒）→ 警示清單確認來源組成（30 秒）→ 對最可疑實體開側邊窗格（1 分鐘）→ Go hunt 確認擴散（2 分鐘）→ 決定收斂或升級。五步五分鐘走完，就是 tier-1 的標準節奏。
07 — 🏷️ 分類與結案

真陽性、資訊性、誤判的正確用法

結案不是把狀態改成「已解決」就好，還要選分類與底下的判定。這是 SC-200 高頻細節，因為它牽動報表品質與調校依據。

分類意思判定（子分類）典型情境
True positive偵測正確，確實是惡意活動多階段攻擊、惡意使用者活動、遭入侵帳戶、惡意程式碼、網路釣魚、不需要的軟體、其他使用者點了釣魚連結、帳號被接管
Informational, expected activity偵測正確、行為真的發生，但預期且無害安全性測試、確認的活動、企業營運（LOB）應用程式、其他紅隊演練、IT 管理工具批次操作
False positive偵測錯了，那件事根本不是它說的那回事非惡意、資料不足以驗證、其他正常檔案被誤判為惡意
Not set尚未分類—仍在調查，或忘了結案

為什麼要認真填？其一，它是調校依據——大量同型警示被標成誤判，就是該建警示調整（alert tuning）規則的訊號；其二，它是 SOC 的績效指標來源（誤判率、平均處理時間），且部分偵測會把判定回饋給引擎，填錯等於教錯。

🎯 考點聚焦
資訊性 vs 誤判是最會考的分岔，公式只有一句：「那件事真的發生了嗎？」發生了、只是無害或預期中（紅隊演練、內部工具、LOB 應用）→ Informational, expected activity；根本沒發生、偵測認錯了 → False positive。經典陷阱：「安全團隊執行滲透測試，事件確實記錄到該活動，應如何分類？」正解是資訊性＋判定「安全性測試」；選誤判是錯的，因為偵測完全正確。其次，「證據不足」不等於誤判——選 false positive 底下的「資料不足以驗證」，或維持未設定繼續調查。第三，分類是結案動作：問「解決事件時還必須做什麼」，答案就是分類與判定。
🛡️ 實戰情境：一起多警示事件的完整分診

週二 09:12，你是 tier-1 分析師。佇列頂端出現未指派的高嚴重性事件「涉及多個端點的多階段事件」，服務來源顯示多重來源。

  1. 掃描（09:12）：三個高優先訊號同時成立——多重服務來源、受影響資產含財務伺服器、類別涵蓋初始存取與憑證存取。決定先做它。
  2. 認領（09:13）：指派給自己、狀態改「進行中」、加標籤 fin-dept。
  3. 看攻擊故事（09:14）：四則警示——MDO「使用者點擊惡意 URL」、MDE「可疑 PowerShell 下載活動」、MDE「嘗試存取 LSASS 記憶體」、Entra ID Protection「陌生位置的高風險登入」。順序一目瞭然：郵件 → 端點執行 → 憑證竊取 → 帳號被用。
  4. 看細節（09:17）：時間軸顯示 PowerShell 的父程序是 Outlook 開啟的附件；使用者帳號屬財務群組、風險高；自動調查已封鎖惡意檔案，但帳號尚未處置。
  5. Go hunt（09:21）：從寄件者按 Go hunt，確認同一封信寄給 43 人、9 封成功遞送、1 人點擊——是小型 campaign。
  6. 升級（09:25）：命中判準——憑證存取戰術、財務系統、已擴散。tier-1 不自行處置帳號與裝置，改為加註發現、貼標籤 escalated-t2、重新指派給 tier-2。狀態維持「進行中」——升級不是結案。
  7. tier-2 收尾（11:40）：裝置隔離、密碼重設與工作階段撤銷、其餘 8 封信郵件修復後，狀態改「已解決」，分類 True positive、判定 網路釣魚，並套用到四則警示。

回顧：全程只有一個分岔——若 Go hunt 顯示信只寄給一人、來源是資安團隊自家的釣魚演練平台，分類就變成 Informational, expected activity ＋ 安全性測試。同樣的畫面、不同的事實，導向不同的分類。

tier-1 → tier-2 升級判準（可抄成 SOP）：符合任一項就升級——(1) 出現憑證存取、橫向移動、外洩或影響戰術；(2) 涉及網域控制站、特權帳號或關鍵資產；(3) 影響超過單一使用者／裝置；(4) 需要超出 tier-1 權限的回應動作（裝置隔離、帳號停用、即時回應）；(5) 30 分鐘內無法判定真偽。反之，單一來源、單一低嚴重性、資產不重要且自動調查已處理完畢者，tier-1 直接分類收斂。
08 — 🧩 考綱補洞

EP1 沒講、分診題卻會考的

  • 警示調整（alert tuning）：建規則讓符合條件的警示自動隱藏或標為誤判。分界：警示調整管未來的同型警示，分類管已發生的這一件；題目說「避免良性警示每天塞爆佇列」→ 建警示調整規則。
  • 動作中心（Action center）：考綱明列 manage actions and submissions in the Action center，它集中「待核准」與「歷史」兩類回應動作，可追蹤與復原（undo）。動作卡在待核准，往往就是事件沒收斂的原因。
  • 自動攻擊中斷：對高信心的勒索軟體、商業電子郵件詐騙，系統會自動停用帳號或隔離裝置並貼標籤。看到這類事件，任務是驗證處置與清理，不是從零重查。
  • Sentinel 事件同步：工作區連入統一入口後共用一條佇列，狀態、擁有者與分類雙向同步；Sentinel 自動化規則仍可依標籤與嚴重性自動指派或執行劇本（Playbook）。
  • 多租用戶與保留：MSSP 可在多租用戶入口一次分診多個租用戶的事件，權限仍受各租用戶授權限制；XDR 事件與警示保留 180 天，要更長回溯請走 Sentinel 與資料湖層。

QUESTION 1 · D2-0001
You are a security operations analyst reviewing the incident queue in the Microsoft Defender portal. One incident groups 12 low-severity alerts from Microsoft Defender for Endpoint together with 1 high-severity alert from Microsoft Defender for Office 365. Which severity does Microsoft Defender XDR show for the incident itself?
（你是安全性作業分析師，正在 Microsoft Defender 入口網站檢視事件佇列。某個事件把 Microsoft Defender for Endpoint 的 12 則低嚴重性警示，與 Microsoft Defender for Office 365 的 1 則高嚴重性警示關聯在一起。Microsoft Defender XDR 會把這個事件本身顯示為哪一種嚴重性？）
A. Low, because most of the correlated alerts are low severity
低，因為關聯進來的警示大多是低嚴重性
B. Medium, because the incident severity is the average of the alert severities
中，因為事件嚴重性是各警示嚴重性的平均值
C. High, because an incident inherits the highest severity among the alerts it contains
高，因為事件會沿用所含警示中最高的嚴重性
D. Informational, because the severity is calculated only after an analyst assigns the incident
資訊，因為嚴重性要等分析師指派事件之後才會計算
看正解與解析
正解：C

事件（incident）的嚴重性＝所含警示（alert）中的**最高**嚴重性，與警示數量、平均值或指派狀態都無關。因此 12 低＋1 高的組合，事件會顯示為「高」。延伸考點：日後若有新的高嚴重性警示關聯進來，事件嚴重性會被往上拉；反之把個別警示標成誤判，並不會自動把事件嚴重性往下修——要調整得由分析師處理事件本身。

  • A：警示數量多寡不是嚴重性的計算依據；12 則低嚴重性警示不會把事件壓成低，關聯引擎看的是最高值。
  • B：Defender XDR 不對嚴重性取平均。若採平均值，重大的單一高嚴重性訊號就會被大量雜訊稀釋掉，違反分診的設計目的。
  • D：嚴重性在事件產生時就由關聯的警示決定，與指派給誰、狀態是「作用中」還是「進行中」都無關；「資訊」是警示層級的嚴重性選項，不是未分診的預設值。

QUESTION 2 · D2-0002
You are a tier-1 analyst starting your shift. Five unassigned high-severity incidents are waiting in the Microsoft Defender XDR queue, so severity alone no longer tells you where to start. Which incident should you work on FIRST?
（你是 tier-1 分析師，剛開始輪班。Microsoft Defender XDR 佇列中有五個未指派的高嚴重性事件，嚴重性已經無法幫你排序。你應該「最先」處理哪一個事件？）
A. The incident whose alerts come from multiple service sources, whose affected assets include a finance server, and whose categories already cover credential access
警示來自多重服務來源、受影響資產含財務伺服器，且類別已涵蓋憑證存取的那個事件
B. The incident that contains the largest number of alerts
包含最多警示的那個事件
C. The incident that was created most recently
建立時間最新的那個事件
D. The incident that automatic attack disruption has already contained by disabling the account
自動攻擊中斷已經停用帳戶、完成遏制的那個事件
看正解與解析
正解：A

嚴重性相同時，優先序來自綜合判斷：攻擊階段（是否已推進到憑證存取、橫向移動、外洩或影響）、資產與帳號重要性（網域控制站、財務系統、特權帳號）、訊號多樣性（多重服務來源幾乎等同真攻擊）、影響廣度。選項 A 同時命中三個提高優先度的訊號，是最該先做的一件。

  • B：警示數量多常常只是同一則雜訊重複觸發，或某條偵測邏輯過於敏感，數量本身不代表風險。
  • C：事件的新舊與風險無關；只挑最新的處理，反而容易讓早幾分鐘產生、已經推進到深層戰術的攻擊被晾在佇列裡。
  • D：自動攻擊中斷已經切斷攻擊路徑，該事件的任務是驗證處置結果與清理收尾，不必插隊；尚未被任何自動化處置的事件才需要人先介入。

QUESTION 3 · D2-0003
Your organization hired an external red team to run an authorized penetration test last night. This morning Microsoft Defender XDR raised an incident that accurately recorded the red team credential dumping activity on two servers. You must resolve the incident so that the detection quality metrics of the SOC stay accurate. How should you classify it?
（你的組織昨晚委託外部紅隊執行經授權的滲透測試。今天早上 Microsoft Defender XDR 產生一個事件，正確記錄了紅隊在兩台伺服器上傾印認證的活動。你必須解決這個事件，同時讓 SOC 的偵測品質指標保持正確。你應該如何分類（classification）？）
A. False positive with the determination Not malicious
False positive（誤判），判定為「非惡意」
B. False positive with the determination Not enough data to validate
False positive（誤判），判定為「資料不足以驗證」
C. True positive with the determination Malicious user activity
True positive（真陽性），判定為「惡意使用者活動」
D. Informational, expected activity with the determination Security testing
Informational, expected activity（資訊性、預期中的活動），判定為「安全性測試」
看正解與解析
正解：D

判斷公式只有一句：「那件事真的發生了嗎？」紅隊確實執行了認證傾印，偵測完全正確，只是行為是預期且經授權的，因此分類為 Informational, expected activity，判定選「安全性測試（security testing）」。填對很重要：分類與判定是警示調校的依據，也是誤判率等 SOC 績效指標的來源，部分偵測還會把判定回饋給偵測引擎。

  • A：誤判代表「偵測認錯了、那件事根本沒發生」。這裡活動真的發生過，標成誤判等於教錯引擎，也會虛增誤判率、誤導後續調校。
  • B：「資料不足以驗證」用在證據不足、無法判定真偽的情況。本題已確知是紅隊演練，事實清楚，不適用。
  • C：真陽性用於確實發生的「惡意」活動。紅隊演練經過授權、非惡意，若標成真陽性會虛增真實攻擊數量並污染事件統計。

QUESTION 4 · D2-0004
Each morning the queue of your SOC fills with the same benign alert, which a scheduled IT management script triggers on 300 devices. Analysts waste time closing the same alert every day. You must prevent these alerts from filling the queue in the future while keeping a record that you can review later. What should you do?
（你的 SOC 佇列每天早上都被同一種良性警示塞爆——來源是一支排程執行的 IT 管理指令碼，在 300 台裝置上觸發。分析師每天都在關掉同一種警示。你必須讓這類警示未來不再塞爆佇列，同時保留日後可回查的紀錄。你應該怎麼做？）
A. Classify each incident as Informational, expected activity and resolve them again every morning
每天早上照樣把每個事件分類為 Informational, expected activity 後解決
B. Create an alert tuning rule that automatically hides or resolves the alerts that match the conditions
建立警示調整（alert tuning）規則，讓符合條件的警示自動隱藏或標記解決
C. Merge the incidents into one parent incident every morning
每天早上把這些事件合併成一個主事件
D. Add a tag to the incidents and create a Microsoft Sentinel automation rule that assigns them to a tier-1 analyst
為這些事件加標籤，並建立 Microsoft Sentinel 自動化規則把它們指派給 tier-1 分析師
看正解與解析
正解：B

分類（classification）處理的是「已經發生的這一件」，警示調整（alert tuning）處理的是「未來所有同型警示」。針對已知良性的內部工具，建立警示調整規則（依偵測名稱、實體、檔案路徑等條件）讓符合的警示自動隱藏或標為解決，才是治本作法；規則仍留有設定與命中紀錄可回查，需要時可停用規則恢復顯示。

  • A：分類只結掉今天這批，明天同樣的警示還是會進佇列，人力成本沒有下降，也不符合「未來不再塞爆佇列」的要求。
  • C：合併是把「同一起攻擊」被拆開的多個事件收成一件，用在重複的良性警示上並不會阻止新事件產生，而且入口網站沒有拆分事件的動作，誤併風險高。
  • D：標籤與自動化規則只是改變事件流向（誰被指派、跑什麼劇本），警示照樣產生、佇列照樣變長，只是把負擔換個人扛。

QUESTION 5 · D2-0005
Triage is complete on an incident you own: a delivered phishing message led to credential access on a finance server, a Go hunt query confirms that 43 mailboxes received the same message, and the affected account is privileged. The runbook of your SOC states that device isolation and account disablement are tier-2 actions only. Which combination of actions should you take next?
（你負責的事件已完成分診：一封成功遞送的釣魚郵件導致財務伺服器上發生憑證存取，Go hunt 查詢確認同一封信寄達 43 個信箱，受影響帳戶又是特權帳號。你們 SOC 的作業手冊規定，裝置隔離與停用帳戶只能由 tier-2 執行。接下來你應該採取哪一組動作？）
A. Isolate the device, reset the password of the user, and then resolve the incident as a true positive
自行隔離裝置、重設該使用者密碼，然後把事件解決為真陽性
B. Record your findings on the incident, add an escalation tag, reassign the incident to tier 2, and keep the status as In progress
在事件上記錄你的發現、加上升級標籤、把事件重新指派給 tier 2，並把狀態維持在「進行中」
C. Resolve the incident as True positive with the determination Phishing so that tier 2 can reopen it later
把事件解決為 True positive、判定為網路釣魚，讓 tier 2 之後再重新開啟
D. Leave the incident unassigned with the status Active and email the tier-2 distribution list
讓事件維持未指派、狀態「作用中」，改用電子郵件通知 tier-2 群組信箱
看正解與解析
正解：B

本題同時命中多條升級判準：已出現憑證存取戰術、涉及特權帳號與財務系統、影響超過單一使用者，且所需回應動作超出 tier-1 權限。正確作法是把調查結果寫進事件、貼上可篩選的升級標籤、把擁有者改成 tier-2，並把狀態維持在「進行中」——升級是交棒，不是結案；狀態留在進行中，SLA 與擁有權才追得下去，也避免事件掉出佇列。

  • A：裝置隔離與帳戶處置超出 tier-1 被授權的範圍，違反最小權限原則與作業手冊；而且攻擊尚未確認清除完畢就結案，等於提早關掉追蹤。
  • C：把仍在進行中的攻擊標成已解決，會讓事件離開作用中佇列、SLA 計時中止，指標也會失真；分類與判定應在回應完成、確認清除後才填。
  • D：事件留在未指派、作用中狀態，會被別的分析師重複認領造成重工；交接資訊寫在信裡而不寫在事件上，稽核軌跡與後續調查都接不上。
