01 — 📌 本日導讀

沒有警示的那些事：Sentinel 搜捕四件套

昨天在 Defender XDR 的 advanced hunting（進階搜捕）練了跨表查詢，今天換到 Microsoft Sentinel 的搜捕（hunting）頁面。Sentinel 把搜捕做成一套有紀律的流程：搜捕查詢負責發問、書籤（bookmark）負責留證、Livestream 負責盯現在、Hunts 把整件事包成可結案的專案。本日三重點：搜捕頁面全景與查詢怎麼挑；Hunts 與書籤這條「假說→證據→事件」的證據鏈；以及最容易被跳過的 Livestream——它跟排程分析規則差在哪、何時該用它。

學習目標（對應官方考綱 D3「執行威脅搜捕」）：
  • ☐ 依 MITRE ATT&CK 戰術瀏覽並批次執行內建搜捕查詢（對應考綱 use hunting queries in Microsoft Sentinel）
  • ☐ 建立自訂搜捕查詢，含實體對應與戰術／技術標記（對應考綱 create custom hunting queries）
  • ☐ 用 Hunts 管理一次獵捕的假說、查詢、書籤與狀態流（對應考綱 monitor hunts）
  • ☐ 用書籤保存與註記結果，並在需要時升級成事件（對應考綱 use bookmarks）
  • ☐ 用 Livestream 對即時事件測試查詢、取得通知並升級為警示（對應考綱 use livestream）

03 — 🔍 搜捕頁面全景

查詢清單怎麼挑：戰術、結果數與批次跑

搜捕頁面分成 Queries、Livestream、Bookmarks 幾個頁籤，新版再加 Hunts。查詢有兩種來源：內建範本（微軟與社群提供，隨內容中樞 Content Hub 的解決方案安裝）與你的自訂查詢。清單標示提供者、資料來源與 MITRE 戰術／技術——最實用的瀏覽維度：懷疑有人橫向移動，就篩 Lateral Movement 那一欄。

💡 三個常被忽略的操作：①Run all queries 批次執行——跑完先看「結果數」，有數字的才展開；②結果差異（Results delta）——「昨天 0 筆、今天 47 筆」比絕對數字更有訊號；③我的最愛——標記後進頁面自動執行，等於個人化搜捕儀表板。注意：搜捕查詢不會自己排程、不會產生警示，跑不跑取決於有沒有人按下去。

自訂查詢有兩條路：複製（Clone）既有範本後改寫，或直接新建。除了 KQL，還要填實體對應（把輸出欄位對應成 Account／Host／IP 實體）與戰術、技術：有實體對應，書籤才進得了調查圖；標了戰術，查詢才會出現在按戰術瀏覽的清單裡。先看一支典型查詢：

// 假說：帳號遭接管後，攻擊者會在短時間內把 SharePoint／OneDrive 檔案整批帶走
let lookback = 7d;           // 搜捕視窗：假說必須 time bound
let baseline_window = 30d;   // 用使用者「自己的過去」當基準線
let baseline =
    OfficeActivity
    | where TimeGenerated between (ago(baseline_window) .. ago(lookback))
    | where Operation in ("FileDownloaded", "FileSyncDownloadedFull")
    | summarize DailyCount = count() by UserId, bin(TimeGenerated, 1d)
    | summarize Normal = percentile(DailyCount, 90) by UserId;
OfficeActivity
| where TimeGenerated > ago(lookback)
| where Operation in ("FileDownloaded", "FileSyncDownloadedFull")
| summarize Downloads = count(), Files = dcount(OfficeObjectId),
            SrcIPs = make_set(ClientIP, 5)
        by UserId, Day = bin(TimeGenerated, 1d)
| join kind=leftouter baseline on UserId
| extend Normal = coalesce(Normal, 0.0)
| where Downloads > 100 and Downloads > Normal * 5
| project Day, UserId, Downloads, Files, SrcIPs, Normal
| order by Downloads desc

逐段解說：兩個 let 把時間參數提出來，改視窗只要改一行。baseline 算出每位使用者過去三十天的每日下載量，取 percentile(DailyCount, 90) 當「這個人的正常值」——會計每天下載兩百個檔案是日常，工程師就不是，個人基準線才抓得到相對異常。主查詢按「使用者×每日」聚合，make_set(ClientIP, 5) 留來源 IP 供 pivot；leftouter 讓沒有歷史的新帳號也留著（爆量更可疑）。最後一行是雙條件：絕對量夠大且比自己平常爆增五倍。存成自訂查詢時 UserId 對應 Account 實體、戰術標 Exfiltration。

04 — 📦 Hunts 專案

把一次獵捕包成可交接的專案

單支查詢跑完就沒了，但真實獵捕常要跑一兩週、動用十幾支查詢，中途還可能換人接手。Hunts 就是為此存在的容器：把假說、查詢、書籤、備註與發現綁在同一個工作項目下，讓「這次獵捕」變成可追蹤、可結案的專案。建立時填名稱、假說、擁有者、狀態與 MITRE 戰術；之後在 hunt 內執行查詢，把有價值的結果列存成書籤，自動掛在該 hunt 底下形成證據夾。

面向取值營運意義
Hunt 狀態New → Active → ClosedNew＝假說寫好未動手；Active＝正在跑查詢累積書籤；Closed＝結論已下並寫原因
假說狀態Unknown／Validated／Invalidated結案務必更新：不成立也是成果，代表這條路徑沒被利用，可停止重複投入
內容物查詢、書籤、備註、戰術標記接手的人打開就知道：問了什麼、找到什麼、還缺什麼
成果出口建立事件、查詢轉分析規則價值不在報告，而在「下次它會自己被抓到」
🎯 考點聚焦
「監控 hunts」題怎麼看：題幹提到「多位分析師協作、要追蹤搜捕進度與發現」→ 指向 Hunts，不是書籤或活頁簿：書籤是單筆證據、hunt 是整個專案，兩者是包含關係。另一陷阱：「假說被推翻要怎麼辦」，正解是標為 Invalidated 並結案，不是刪掉 hunt——刪掉等於丟掉「這條路查過了」的記憶。
05 — 🔖 書籤留證

可疑但還不確定？先存起來

搜捕最尷尬的狀態是「這列看起來怪，但還不敢說它是攻擊」。書籤就是為這狀態設計的：選取結果的某幾列存成書籤，Sentinel 會把那幾列資料、當時的 KQL、查詢的時間範圍一起保存。它是可重現的證據快照——三週後回頭看，你還知道當初怎麼問出這結果。建立時能補的四件事，每件都決定它後續能做什麼：

  • 備註與標籤：寫下判斷與待辦；標籤用獵捕代號（如 AiTM-2026-08）串起同一次調查的所有書籤。
  • 實體對應：把欄位對應成帳號、主機、IP。影片示範中最關鍵的一步——有對應才進得了調查圖。
  • MITRE 戰術／技術：讓證據帶著攻擊階段語意（影片把可疑 PowerShell 標成 command and control）。
  • 歸屬的 hunt：在 hunt 內建立的書籤自動歸檔到該專案。

下游有三條路：升級成新事件、加入既有事件、留著繼續觀察。書籤本身也是工作區的一張表，可以直接查，盤點與交接特別好用：

// 盤點本次獵捕留下的書籤：哪些已升級成事件、哪些還躺著沒人處理
HuntingBookmark
| where TimeGenerated > ago(30d)
| where SoftDeleted == false
| where Tags has "AiTM-2026-08"
| summarize arg_max(TimeGenerated, *) by BookmarkId
| extend LinkedIncident = tostring(IncidentInfo.Title)
| extend Status = iff(isempty(LinkedIncident), "未升級", "已連結事件")
| project TimeGenerated, BookmarkName, Status, LinkedIncident, Tags, Notes
| order by TimeGenerated desc

逐段解說：HuntingBookmark 存的就是書籤本身，含名稱、原始查詢、被保存的結果列與標籤；第 3 行濾掉已刪除的。第 5 行 arg_max(TimeGenerated, *) by BookmarkId 是重點：書籤每次被編輯都會新增一列，取每個 BookmarkId 的最新一列才是現況。IncidentInfo 是動態欄位，書籤已升級或加入事件時裡面帶有該事件資訊。這支查詢做成活頁簿磚就是「搜捕待辦清單」，每週看哪些證據躺著還沒結論。

06 — 📡 Livestream

盯著現在：即時串流一支查詢

前面的工具都在看過去。Livestream（搜捕即時串流）把鏡頭轉向現在：開一個互動式工作階段掛上查詢，資料一進工作區就比對，命中時在入口網站近即時通知你。可以從既有搜捕查詢直接建立（影片就是這樣做），也可以貼一段 KQL 從頭開始。

四個典型用途：①測試新規則邏輯——與其把沒把握的查詢設成排程規則、隔天收到一百張誤判，不如先串流幾小時看雜訊多不多，滿意再升級。②等攻擊者回來——剛清掉被入侵的主機，對方通常會再試一次，掛一支針對該 IoC 的串流，回來當下就知道。③事件期間盯梢——盯住特定帳號或主機，取代手動重新整理。④驗證圍堵——封帳號、隔離裝置後持續零命中，就是圍堵生效的即時證據。

💡 一鍵轉正式規則：Livestream 工作階段可升級成警示（elevate to alert），直接用同一段查詢建立排程分析規則，不必重打 KQL。這是搜捕成果轉正的最短路徑：假說 → 搜捕查詢 → Livestream 驗證雜訊 → 排程規則 → 自動化規則／劇本。

同一段 KQL 在搜捕與在 Livestream 裡該長得不一樣：搜捕常做長視窗聚合，Livestream 每次只面對剛進來的一小批資料，聚合與長視窗篩選會失去意義甚至誤導。把第 03 節那支改寫成串流版：

// Livestream 版：不看歷史、不聚合，只問「現在這個帳號還在下載嗎」
OfficeActivity
| where Operation in ("FileDownloaded", "FileSyncDownloadedFull")
| where UserId =~ "mei.chen@contoso.com"        // 鎖定調查中的帳號
| project TimeGenerated, UserId, ClientIP, OfficeObjectId, UserAgent
| order by TimeGenerated desc

改寫三原則：①拿掉時間篩選——工作階段已界定「從現在起」，不需要 ago(7d)。②拿掉 summarize 聚合——串流逐列即時比對，「超過基準線五倍」這種要累積才成立的條件算不出來；改鎖定已知目標或明確的高風險動作。③輸出逐列可讀——只留人眼一秒能判斷的欄位。查詢越輕，串流越不拖慢入口網站。

四件套的定位一次看清楚：

面向搜捕查詢書籤Livestream排程分析規則
時間軸與觸發過去（自訂視窗）；分析師手動或批次跑過去的某一刻；分析師手動保存現在（新進資料）；分析師開工作階段依排程週期回看；平台自動 24×7
何時用驗證假說、找沒有警示的行為有價值但無法定論，要留證與交接測試規則邏輯、等攻擊者回來、事件期間盯梢邏輯已驗證、雜訊可接受、要長期自動偵測
輸出到哪結果表格 → 書籤／Livestream／轉規則調查圖、事件、hunt 專案入口網站通知 → 可升級成警示／規則警示與事件 → 分診佇列、自動化規則、劇本
會產生事件嗎不會不會（要手動升級）不會（只通知）會（可設定事件建立與分組）
成本考量不另計查詢費，成本是分析師時間幾乎零成本，落在工作區表要人盯；查詢寫太重會拖慢佔規則配額；誤判直接變 SOC 工作量
🎯 考點聚焦
Livestream vs 排程規則 vs NRT 規則怎麼選：題幹出現「test a query／驗證邏輯／不確定會不會誤判」「interactive session」「調查期間要被通知」「不想製造警示」→ Livestream；「持續自動偵測」「產生事件並指派」「觸發劇本」→ 排程分析規則；「近乎即時、每分鐘」且仍要產生警示→ NRT 規則。NRT 是最容易與 Livestream 混淆的干擾項：兩者都強調快，但 NRT 會產生警示與事件、有數量上限；Livestream 不產生任何警示，關掉工作階段就沒了。一句話：Livestream 是給人看的，分析規則是給流程看的。
07 — 🛡️ 完整獵捕

從一句假說到一條偵測規則

🛡️ SOC Walkthrough：AiTM 釣魚後的資料外洩獵捕

威脅情報通報：一波 AiTM（adversary-in-the-middle）釣魚鎖定你的產業，得手後用竊得的工作階段權杖登入並整批下載檔案。你的環境沒有任何相關警示——正好是搜捕的主場。

  1. 寫假說並開 hunt：假說＝「過去 7 天內有帳號在非慣用 IP 上出現遠高於自身基準的下載量，且未觸發警示」——範圍窄、有時間界線、現有資料就能驗證。在 Hunts 建專案，狀態 New，標 Exfiltration。
  2. 跑內建查詢暖身：按戰術篩出 Exfiltration 與 Initial Access 的內建查詢，Run all queries，看哪幾支有結果、哪幾支的 Results delta 在跳動。狀態改 Active。
  3. 寫自訂查詢：用第 03 節那支基準線查詢收斂。三個帳號超標，其中一位財務同仁單日下載 1,340 個檔案、平常基準只有 12，來源 IP 在海外。
  4. 留證：書籤：把這幾列存成書籤，UserId 對 Account、ClientIP 對 IP 實體，戰術標 Exfiltration，標籤 AiTM-2026-08，自動掛進 hunt。
  5. 擴大關聯：從書籤進調查圖，圖上帶出同時段登入記錄：一個沒出現過的 IP、一次沒有 MFA 挑戰的權杖重放。假說開始成立。
  6. 掛 Livestream：把「這帳號的下載動作」做成串流，一邊處置一邊盯——唯一能回答「他現在還在下載嗎」的工具。同時請身分小組撤銷權杖。
  7. 升級成事件：把書籤升級成事件（若已有相關事件，改加入既有事件），嚴重性 High，進正式分診與 SLA；Livestream 續開，驗證撤銷權杖後是否歸零。
  8. 轉成偵測規則：收尾不是報告，是讓它下次自動被抓到。把驗證過的查詢建成排程分析規則（或從 Livestream 直接 elevate to alert），設好實體對應與自動化規則，命中就自動指派並跑撤銷權杖的劇本。
  9. 結案：hunt 改 Closed、假說標 Validated，備註寫下產出：1 張事件、1 條新規則、3 個書籤。下次有人問「我們查過 AiTM 外洩嗎」，打開 hunt 就有答案。
🎯 考點聚焦
書籤何時該升級成事件：判準只有一個——需不需要進入正式處理流程。要指派負責人、要 SLA 與稽核軌跡、要多人協作或自動回應 → 升級成事件；若同一批活動已有事件在跑，正解通常是加入既有事件而非新開一張（重複開會破壞關聯與統計，考題愛在此設陷阱）。只是「以後可能有用」→ 留在書籤加標籤與備註。也別把所有書籤都升級成事件，那是自製誤判洪水。
08 — 🧩 考綱補洞

EP10 沒講到、考試會考的

EP10 聚焦在「查詢→書籤→實體→Livestream→調查圖」這條動線，以下考綱能力影片著墨很少或完全沒提，本文已補講：

  • Hunts 專案與狀態流：影片完全未提。New／Active／Closed 三態、假說 Unknown／Validated／Invalidated（§04）。
  • Livestream 完整能力：影片只給三十秒。記住「不產生警示、互動式、可設通知、可 elevate to alert」，以及與排程規則、NRT 規則的分工（§06）。
  • 批次執行與結果差異：Run all queries 與 Results delta 是日常操作，影片未示範（§03）。
  • 自訂查詢的必填欄位：沒有實體對應就沒有調查圖，沒有戰術就無法按 ATT&CK 瀏覽（§03、§05）。
  • 書籤加入既有事件：影片只示範新增書籤；考題常在「新開事件 vs 加入既有事件」上分勝負（§07）。
  • 搜捕成果三去向：轉分析規則（自動偵測）、接自動化規則與劇本（自動回應）、留書籤存證（知識累積）。
