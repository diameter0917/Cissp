01 — 📌 本日導讀

攻擊者不是駭進來的，是登入進來的

這一週守了裝置、守了信箱，今天守的是把所有資源串起來的那條線——身分。現代入侵幾乎都長同一個樣子：先釣到一組帳密，再在網域裡東翻西找、偷票證、跳機器，最後拿下網域管理員；整條路上多半沒有惡意程式，只有「看似完全合法的驗證行為」。防毒攔不住合法登入，所以考綱 D2「回應安全性事件」給了身分兩個專屬武器：地端 Active Directory 交給 Microsoft Defender for Identity（MDI），雲端交給 Microsoft Entra ID Protection。今天釘死四件事：感應器裝哪、攻擊鏈每階段亮什麼燈、兩邊能按哪些回應按鈕，以及最常被混淆的「使用者風險 vs 登入風險」。

學習目標（對應官方 study guide D2「調查並修復由 Microsoft Defender for Identity 識別的威脅」與「調查並修復 Microsoft Entra ID Protection 中的身分風險」）：

  • ☐ 說明 MDI 感應器的部署位置（網域控制站、AD FS、AD CS）、目錄服務帳戶用途與 XDR 整合
  • ☐ 依攻擊鏈階段（偵察 → 認證竊取 → 橫向移動 → 網域支配）判讀 MDI 警示代表的攻擊技術
  • ☐ 用橫向移動路徑（lateral movement paths）評估帳戶曝險，依身分安全態勢（ISPM）建議修補
  • ☐ 對遭盜用身分執行正確回應：停用使用者、密碼重設、暫停帳戶、確認遭入侵
  • ☐ 分辨使用者風險與登入風險，設定風險型條件式存取政策並調查、關閉風險

03 — 🛰️ MDI 架構與部署

感應器裝在哪、靠什麼看見攻擊

MDI 沒有雲端 API 可以直接讀你的網域，必須把感應器（sensor）裝進伺服器——架構題的第一個考點：感應器直接安裝在網域控制站上，另外支援 AD FS（同盟服務）、AD CS（憑證服務）與 Entra Connect 伺服器。裝在 DC 是因為所有 Kerberos／NTLM 驗證、LDAP 查詢與目錄複寫都要經過它；裝在 AD FS 是為了看見同盟登入的暴力破解；AD CS 則盯憑證範本濫用。感應器輕量、自我更新，不必另備伺服器或做網路埠鏡像（早期的 standalone sensor 與 port mirroring 已淘汰）。

感應器吃三種訊號：本機網路流量（解析 Kerberos、NTLM、DNS、LDAP）、Windows 安全性事件（需開進階稽核，例如物件存取稽核產生的 4662 是 DCSync 偵測關鍵）、以及對目錄的 LDAP 查詢（把帳戶群組解析成實體、判斷誰是敏感帳戶）。第三種需要能唯讀查詢網域的目錄服務帳戶（DSA），官方建議用 gMSA，密碼由 AD 自動輪替。資料上傳雲端後，警示落進 Defender 入口網站並關聯成 XDR 事件；原始活動進入進階搜捕的 IdentityLogonEvents、IdentityQueryEvents、IdentityDirectoryEvents 三張表。

一句話架構圖：感應器（DC／AD FS／AD CS）解析驗證流量與事件 → 用 DSA 補查目錄 → 上傳雲端 → 警示進 XDR 事件、活動進 Identity* 搜捕表 → 分析師在使用者實體頁面調查與回應。
🎯 考點聚焦

部署題三陷阱：（1）「要偵測橫向移動與票證攻擊，感應器裝哪？」→ 網域控制站，不是防火牆或用戶端；裝在端點的是 MDE。（2）「已全面部署 MDE，還需要 MDI 嗎？」→ 需要，MDE 看不見 DC 上的票證異常與目錄複寫請求。（3）「MDI 需要什麼帳戶？」→ DSA（建議 gMSA）做目錄查詢；它與下一節的「動作帳戶」是兩件事——DSA 只要讀取權限，停用帳戶與重設密碼要另外委派寫入權限。

04 — ⛓️ 身分攻擊鏈

從偵察到網域支配的四級台階

MDI 的警示按攻擊階段編排。背下這張表，看到任何警示名稱都能立刻回答「攻擊者走到哪一步、下一步要做什麼」——這正是情境題要測的能力。

階段攻擊者目的代表技術典型偵測訊號
① 偵察
Reconnaissance		畫網域地圖：有哪些帳戶群組、誰有特權SMB／Kerberos 帳戶列舉、SAMR 群組查詢、LDAP 主體偵察（BloodHound）、DNS 區域傳輸MDI：帳戶列舉偵察、使用者與群組成員資格偵察、安全性主體偵察、網路對應偵察
② 認證竊取
Credential Access		把密碼變成可重用的憑證密碼噴灑、AS-REP Roasting、Kerberoasting、pass-the-hash／ticket、overpass-the-hashMDI：可疑暴力破解、可疑 AS-REP Roasting、Kerberos SPN 曝光、可疑身分竊取、加密降級
③ 橫向移動
Lateral Movement		拿憑證跳到更有價值的主機PsExec／WMI 遠端執行、以竊得票證存取伺服器MDI：可疑遠端程式碼執行、資源存取異常、橫向移動路徑（LMP）；MDE：可疑處理程序建立
④ 網域支配
Domain Dominance		取得長期偽造身分的能力DCSync、黃金票證 golden ticket、skeleton key、DCShadowMDI：可疑 DCSync（目錄服務複寫）、可疑黃金票證使用、可疑 skeleton key、可疑 DCShadow
⑤ 雲端延伸
Cloud Expansion		用同一個身分登入雲端與 SaaS權杖竊取、AiTM 中間人釣魚、惡意 OAuth 同意Entra ID Protection：異常權杖、AiTM、不可能的移動、匿名 IP

四個最易混淆的技術用「偷到什麼」來記：pass-the-hash 偷 NTLM 雜湊，直接拿雜湊做驗證；pass-the-ticket 偷已簽發的 Kerberos 票證搬到別台機器用，MDI 抓的就是「同一張票證出現在兩台機器」；overpass-the-hash 拿 NTLM 雜湊換合法的 Kerberos TGT，常伴隨加密降級（硬要用 RC4）；黃金票證是偷到 krbtgt 雜湊後自己簽票，票裡的授權資料與存留時間不合常理。

MDI 的活動資料也能自己搜捕，下面找 pass-the-hash 的足跡：

// 一組認證同時在多台機器上活動＝憑證被複製使用的訊號
IdentityLogonEvents
| where Timestamp > ago(7d)
| where Protocol == "Ntlm" and ActionType == "LogonSuccess"
| summarize Sources = dcount(DeviceName), SourceList = make_set(DeviceName, 10),
            Targets = dcount(TargetDeviceName), Logons = count()
        by AccountUpn, bin(Timestamp, 1h)
| where Sources >= 3 and Targets >= 5
| sort by Targets desc

第 2–3 行：IdentityLogonEvents 是 MDI 送進進階搜捕的驗證事件表，只留過去 7 天成功的 NTLM 驗證（NTLM 才是雜湊重放的主場）。第 4–6 行：以「帳戶＋每小時」為單位，統計它從幾台來源裝置發起、打到幾台目標裝置。第 7 行：真人帳戶通常只從一兩台機器登入，同一小時橫跨 3 台來源、5 台目標就是憑證被搬走的形狀（服務帳戶請先建白名單）。

05 — 🚑 MDI 回應與態勢

按哪個按鈕，與 ISPM 的預防面

MDI 的回應動作掛在使用者實體頁面上，三類都針對身分本身：停用 Active Directory 中的使用者是最快的止血，帳戶當場無法驗證；要求使用者重設密碼強制下次登入變更密碼、讓被偷走的雜湊失效，適合要讓人盡快回到工作又得斷掉攻擊者；暫停 Entra ID 中的使用者則在混合情境把雲端那一半一起關掉。

高頻考點藏在後面：這些動作不會自己生效。MDI 是雲端服務，要回頭改地端 AD 物件，必須配置具權限的動作帳戶（action account）——可沿用 gMSA，但要另外委派重設密碼與停用帳戶的寫入權限。把使用者標記為遭入侵（confirm compromised）則會把訊號送進 Entra ID Protection，使該帳戶的使用者風險直接升為高。

別記錯歸屬：MDI 能停用帳戶、重設密碼，但不能隔離裝置——裝置隔離是 MDE 的動作；「包含使用者（contain user）」屬於 XDR 的自動攻擊中斷。考題描述「無人核准就自動停用了受害帳戶」→ 自動攻擊中斷，不是 MDI 的手動回應。

回應是止血，身分安全態勢管理（ISPM）才是止痛。MDI 持續評估 AD 組態並把問題寫成建議，呈現在安全分數與曝險管理清單裡：明文傳輸認證的舊協定、不安全的 Kerberos 委派、敏感群組中的閒置帳戶、AD CS 憑證範本弱點、風險最高的橫向移動路徑。考題問「如何主動降低身分攻擊面」，答案在 ISPM，不在警示。

💼 實戰情境

週四 15:20，XDR 跳出中度事件：MDI 警示「Suspected identity theft (pass-the-ticket)」，主體是財務部 k.wang，來源 FIN-WS041、目標 SRV-FILE02。① 先看事件全貌——同時關聯了兩小時前 MDE 的「LSASS 記憶體讀取」，故事成形：先在工作站偷票證，再拿票證打檔案伺服器。② 打開使用者實體頁面，同一張票證在兩台工作站都出現過，排除單機誤判。③ 查橫向移動路徑：k.wang 非特權帳戶，卻在三台工作站是本機管理員，其中一台曾有網域管理員登入——離網域支配只剩兩步，嚴重性當場調高。④ 止血：要求密碼重設並撤銷工作階段、由 MDE 隔離 FIN-WS041、把帳戶標記為遭入侵讓 Entra 側升為高風險。⑤ 用上一節的查詢確認沒有第三台機器牽涉。⑥ 把「本機管理員權限過度發放」開成 ISPM 待辦——這條 LMP 不砍掉，下次還是同一齣戲。

06 — ☁️ Entra ID Protection

使用者風險與登入風險的分野

雲端這側邏輯完全不同。Entra ID Protection 不需部署元件，直接坐在驗證流程上，用威脅情報與機器學習替每次登入、每個帳戶評分。它產出的不是攻擊技術，而是風險偵測（risk detection），再匯總成兩種風險——這是全考科最常見的觀念題：

比較面向登入風險（sign-in risk）使用者風險（user risk）
它在問什麼「這一次登入是本人嗎？」「這個帳號是不是已經被盜了？」
評估對象單一次驗證要求帳戶的長期狀態，會持續累積
代表偵測匿名 IP、不可能的移動、不熟悉的登入屬性、AiTM外洩認證、Entra 威脅情報、可疑的更新權杖存取、管理員確認遭入侵
評估時機即時與離線兩種，即時的才擋得下當次離線匯總，升高後維持到被修復
對應政策登入風險政策 → 要求 MFA（多為中以上）使用者風險政策 → 要求安全密碼變更（多為高）
修復後果通過 MFA → 該次登入風險關閉安全密碼變更 → 風險歸零、更新權杖失效
記錄欄位SigninLogs 的 RiskLevelDuringSignInRiskLevelAggregated、AADRiskyUsers

風險等級只有低、中、高三級，代表模型的信賴度而非損失大小；調查靠三份報表：有風險的使用者、有風險的登入、風險偵測。手動處置的副作用要記牢：確認遭入侵把使用者風險拉到高並回饋模型；關閉使用者風險（dismiss）把風險清為零卻不做任何修復，密碼沒換、權杖沒撤，只適合已確認的誤判——真要救回帳戶得重設密碼並撤銷工作階段。

把風險變成防線靠風險型條件式存取：以使用者風險或登入風險當條件套用授與控制，這也是自動修復（self-remediation）的關鍵。兩個常考前置條件：要求安全密碼變更的前提是使用者已完成 MFA 註冊；完整風險明細與風險型政策需要 Microsoft Entra ID P2。

// 風險登入成功了，而且沒有任何條件式存取政策套用到它
SigninLogs
| where TimeGenerated > ago(24h)
| where ResultType == 0
| where RiskLevelDuringSignIn in ("high", "medium")
| where ConditionalAccessStatus == "notApplied"
| project TimeGenerated, UserPrincipalName, IPAddress, Location, AppDisplayName,
          RiskLevelDuringSignIn, RiskLevelAggregated, RiskEventTypes_V2
| sort by TimeGenerated desc

第 3 行：ResultType 為 0 代表登入成功。第 4 行：RiskLevelDuringSignIn 是當次登入風險，帳戶層級的長期風險看 RiskLevelAggregated。第 5 行：notApplied＝沒命中任何條件式存取政策，就是政策範圍的破口。注意 SigninLogs 屬 Sentinel（Entra ID 連接器）那側，XDR 進階搜捕對應的是 AADSignInEventsBeta。

🎯 考點聚焦

「該用哪個風險政策」是必考題型，關鍵在題幹描述的是「一次事件」還是「一個帳戶的狀態」。看到不可能的移動、匿名 IP、不熟悉的登入屬性→ 登入風險政策，要求 MFA。看到認證外洩、管理員已確認遭入侵→ 使用者風險政策，要求安全密碼變更。想清楚為什麼：密碼都外洩了，只要求 MFA 不能讓那組密碼作廢；而正常使用者出差登入，強迫改密碼是過度反應。次考點：緊急存取帳戶必須排除在所有風險政策之外。

07 — 🧭 ITDR 分工對照

地端與雲端，兩張網一個事件

ITDR（identity threat detection and response）是這兩個產品共同撐起的能力：把身分當成獨立的偵測面，而不只是存取控制的設定項。分工很單純——地端 AD 歸 MDI，雲端 Entra 歸 ID Protection，訊號在 XDR 匯合成同一起事件。混合身分環境兩邊都要。

面向Defender for Identity（MDI）Entra ID Protection
守護對象地端 Active Directory、AD FS、AD CS雲端 Entra ID 的帳戶與每一次登入
訊號來源伺服器上的感應器：驗證流量、Windows 事件、LDAPEntra 驗證流程＋威脅情報與 ML（免部署）
偵測方式攻擊技術特徵＋行為基準，認得出 AD 專屬手法機率式風險評分，輸出低／中／高等級
輸出單位依攻擊階段分類的警示，關聯進 XDR 事件風險偵測，匯總為登入風險與使用者風險
代表偵測黃金票證、pass-the-hash／ticket、DCSync、LDAP 偵察外洩認證、不可能的移動、匿名 IP、AiTM、異常權杖
回應動作停用使用者、要求密碼重設、暫停 Entra 帳戶（需動作帳戶）風險型條件式存取：MFA、安全密碼變更、封鎖
自助修復無，由分析師或自動攻擊中斷執行有，過 MFA 或改密碼即可關閉風險
搜捕資料IdentityLogonEvents／QueryEvents／DirectoryEventsSigninLogs、AADUserRiskEvents、AADSignInEventsBeta
一句話收束：MDI 回答「攻擊者在網域裡用了什麼手法」，Entra ID Protection 回答「這個帳號還能不能相信」。前者是技術特徵、靠分析師按鈕；後者是機率信賴度、靠政策自動擋。
08 — 🧩 考綱補洞

影片沒講到的考綱角落

  • 誘餌帳戶（honeytoken）：可把閒置帳戶或群組標記為 honeytoken 實體，正常情況絕不會有人碰，一旦出現驗證或查詢就產生警示——零誤報的偵察偵測器。相關的還有實體標籤（敏感、VIP），標為敏感會提高警示嚴重性並納入 LMP 分析。
  • LMP 需要權限才算得出來：MDI 必須能查詢各機器的本機系統管理員群組成員；若環境限制了遠端 SAM-R 呼叫又沒把 MDI 的帳戶加進允許清單，LMP 會是空的。考題說「LMP 頁面沒資料」，方向是權限與組態。
  • 持續存取評估（CAE）：條件式存取原本只在發權杖時判定一次，權杖有效期內即使帳戶被停用也可能仍可存取。CAE 讓支援的服務近乎即時重新評估，帳戶停用、密碼重設、風險升高時就地終止工作階段——這是「已經停用帳戶了，他為什麼還在讀信」的答案。
  • MDI 與 Sentinel 的關係：MDI 警示透過 Defender XDR 連接器一併流進 Sentinel，不需要單獨的 MDI 連接器。
  • 2026 新考點 Security Copilot 的身分調查輔助：內嵌在 Defender 入口網站的體驗可對身分事件產生自然語言摘要——攻擊鏈走到哪、涉及哪些帳戶與裝置、建議下一步，也能把自然語言問句轉成搜捕查詢。考試層級只需知道定位：加速分診，不取代你的判斷。
