03 — 🏔️ 雙層架構全景

分析層 vs data lake 層：冰箱與冷凍庫 2026 新考點

Sentinel data lake 是建在 Defender 入口網站統一平台上的低成本安全資料湖，把「儲存」與「運算」拆開計價。啟用（onboard）之後，工作區的每張資料表都能選擇要進哪一層；你可以把它想成廚房：分析層是冰箱——常開常拿、隨手就用，但空間貴；lake 層是冷凍庫——便宜、能塞、放得久，要吃之前多一道解凍工序。

分析層（analytics tier）資料湖層（data lake tier）
定位即時偵測與調查的工作面全量、長期、低成本的安全資料湖
成本模型按 GB 擷取計費（隨用隨付或承諾層級折扣），查詢不另計費低價擷取＋儲存費，查詢／jobs／筆記本按用量計費（pay-per-use）
查詢能力完整 KQL、互動即時、進階搜捕與活頁簿（Workbook）直接可用lake exploration 互動 KQL、KQL jobs、Jupyter 筆記本（Notebook），延遲較高
偵測能力分析規則／NRT 規則只在這層執行不能直接餵分析規則——要靠 KQL jobs 升階或 summary rules 彙總回分析層
保留互動保留（Sentinel 資料表含 90 天）總保留最長 12 年
典型資料身分識別登入、端點警示、SecurityEvent 等高價值訊號netflow、防火牆、Proxy、DNS 等高量 verbose 記錄；合規保留資料

還有一個關鍵設計：鏡射（mirrored data）。凡是進了分析層的資料，都會自動鏡射一份到 lake，不另收擷取費。所以 lake 永遠擁有「全量」——你用筆記本或 KQL jobs 做跨資料分析時，不必擔心分析層的資料缺席；反過來不成立，只進 lake 的資料不會出現在分析層。

💡 一句話記架構：「分析層管『現在』，lake 管『全部』。」分析層是偵測引擎唯一看得到的地方；lake 是所有資料（含分析層鏡射）的長期家。資料只會「由湖升階回分析層」，不會自動反向流動。
04 — 🧭 資料該進哪層

分層決策：先問「這份資料要拿來做什麼」

資料表層級的層選擇（table management）是新考綱的操作重點。決策只看兩個問題：①這份資料需要驅動即時偵測嗎？②它的查詢頻率配得上分析層的擷取單價嗎？

  • 進分析層：分析規則、NRT 規則要用的表（登入記錄、端點事件、警示類）；SOC 每天互動查詢的表；需要跑 UEBA、進階搜捕的高價值訊號。
  • 進 lake 層：量大、單筆價值低、偶爾才查的 verbose 記錄（netflow、防火牆 allow 流量、DNS、TLS/CDN 記錄）；純合規保留（「留三年備查」但平常沒人看）；要供 AI／筆記本做歷史建模的資料。
  • 兩邊都要？不必重複擷取——進分析層就自動鏡射進 lake。真正的組合技是：原始資料進 lake、用 summary rules 把摘要送進分析層，偵測與儀表板用摘要，回溯獵捕用原始。
🎯 考點聚焦：分層決策題心法

題幹關鍵字直接對映答案：出現「real-time detection／analytics rule 要用」→ 分析層，沒有第二個選擇，因為偵測引擎不讀 lake。出現「high-volume／rarely queried／compliance retention／minimize cost」→ lake 層。出現「既要長期保留、又要偶爾能查、成本最低」→ lake 層（不要選 archive／匯出到儲存體帳戶——那些是舊解法，查詢體驗差）。陷阱選項常是「全部進分析層＋調高承諾層級」（付不起，違反 minimize cost）與「全部進 lake」（偵測斷炊）。記住：雙層不是二選一，是各司其職。

05 — ⚙️ 在 lake 上查詢與 KQL jobs

lake 的三種打開方式與 KQL jobs 深入 2026 新考點

冷凍庫裡的資料怎麼吃？lake 提供三條路：①lake exploration——在 Defender 入口網站直接對 lake 資料表下互動 KQL（適合臨時查證，按查詢用量計費）；②Jupyter 筆記本（Notebook）——用 Python＋Spark 對湖中全量資料做大規模分析與機器學習；③KQL jobs——把 KQL 查詢設成一次性或排程執行的工作，在 lake 上跑完後，把結果升階（promote）寫回分析層的自訂資料表。先看互動查詢：

// Lake exploration：臨時查證——去年 9 月是否有主機解析過可疑網域
DnsEvents
| where TimeGenerated between (datetime(2025-09-01) .. datetime(2025-10-01))
| where Name has_any ("update-check.badcdn.example", "telemetry.evil.example")
| summarize Hits = count(), FirstSeen = min(TimeGenerated) by Name, ClientIP
逐行解說：這條查詢跑在 lake 層的 DnsEvents 上——資料早已超出分析層的互動保留，但不需要還原（restore）就能直接查。between 限定歷史時間窗（lake 查詢務必收窄範圍，因為按用量計費）；has_any 一次比對多個 IoC 網域；summarize 收斂成「哪台主機、第一次解析是何時」——回溯獵捕的起手式。

互動查詢適合「查一次」；當你需要定期在湖裡撈東西、而且撈到的要能觸發偵測，就升級成 KQL job：

// KQL job（每日排程）：掃描 lake 中 180 天防火牆記錄，比對已知 C2 位址
CommonSecurityLog
| where TimeGenerated > ago(180d)
| where DestinationIP in ("203.0.113.10", "203.0.113.77", "198.51.100.23")
| project TimeGenerated, SourceIP, DestinationIP, DestinationPort,
          DeviceAction, DeviceVendor
逐行解說：這是 KQL job 的查詢本體，支援完整 KQL（join、summarize 都可以，這點與 search jobs 不同）。ago(180d) 的時間窗遠超分析層保留——這正是 job 存在的理由；in() 比對威脅情報給的 C2 清單；job 執行後，project 出的結果會升階寫入分析層的自訂資料表（例如 RetroHuntC2_CL），接著你就能對這張表開分析規則、進事件佇列走正常分診流程。「湖裡撈到的魚，放回冰箱才能上菜。」
💡 KQL jobs 的考試指紋：「lake 資料」＋「排程／定期」＋「結果要供偵測或分析規則使用」三個條件同時出現，答案就是 KQL job＋promote。少了「定期」是一次性 job 或 search job；少了「餵偵測」可能互動查詢就夠。
06 — 🧃 Summary rules

Summary rules：把 verbose 洪流濃縮成偵測可用的果汁 2026 新考點

Summary rules（摘要規則）解決另一半問題：防火牆、netflow 這種每天數百 GB 的資料，就算進了 lake，偵測與儀表板還是需要「即時可查的統計面」。summary rule 以固定間隔（bin，20 分鐘到 24 小時）持續執行你定義的彙總查詢，把結果寫進分析層的自訂資料表——原始資料留在低成本層，分析層只付「摘要」的擷取費，量級常常差百倍。

// Summary rule（每小時 bin）：防火牆連線彙總
CommonSecurityLog
| where DeviceVendor == "Fortinet"
| summarize ConnCount = count(),
            DeniedCount = countif(DeviceAction == "deny"),
            SentBytes = sum(SentBytes)
  by SourceIP, DestinationIP, DestinationPort, bin(TimeGenerated, 1h)
逐行解說：summarize ... by bin(TimeGenerated, 1h) 把每小時的原始流量壓成一列統計；countif(deny) 順手算出封鎖數——「單一來源、大量 deny」正是掃描行為的特徵。規則存檔後指定目的資料表（例如 FirewallSummary_CL，分析層方案），之後分析規則就對這張輕量表寫偵測（例如 DeniedCount > 500 告警）、活頁簿拿它畫趨勢，完全不必碰原始洪流。

與 KQL jobs 的分工要抓準：summary rules 是「持續進行式」——資料一邊進來一邊濃縮，低延遲、永遠跑下去，服務「日常偵測與儀表板」；KQL jobs 是「回頭看」——對湖中歷史大範圍做一次或排程分析，服務「回溯獵捕與歷史研究」。一個向前看、一個向後看。

🎯 考點聚焦：三選一裁決順序

拿到題目先抓三個訊號詞。①持續性：題幹說「ongoing／每小時彙總／供儀表板與偵測長期使用」→ summary rule。②歷史＋排程＋餵偵測：「scan the data lake／過去 N 個月／結果要能建立分析規則」→ KQL job（promote 回分析層）。③一次性撈記錄：「one-time／找出某 IP 出現過的所有記錄／不需複雜查詢」→ search job。兩個高頻陷阱：把 search job 選給「需要 join 的複雜歷史分析」（它的 KQL 受限，正解是 KQL job）；把 summary rule 選給「回掃過去六個月」（它只從啟用後向前彙總，回不了頭，正解也是 KQL job）。最後記一條鐵律：三兄弟的產出全都落在分析層——因為只有分析層能餵偵測、能被日常互動查詢。

🧪 實戰情境：一年份防火牆記錄的低成本合規保留＋回溯獵捕設計

你所在的金融業 SOC 每天產生約 300 GB 防火牆與 netflow 記錄。法遵要求保留 12 個月備查；SOC 只需要對連線統計做偵測；預算擋不住全量進分析層。設計如下——

  1. 分層：CommonSecurityLog 等防火牆表設為 data lake 層，總保留 12 個月（需要的話最長可到 12 年）。高價值的身分識別與端點表留在分析層，反正會自動鏡射入湖，不用二選一。
  2. 偵測面：建 summary rule 每小時彙總連線數、deny 數、傳輸量寫入 FirewallSummary_CL；對摘要表建立分析規則（異常連線量、大量 deny）與活頁簿。分析層每天只多付摘要那幾 GB。
  3. 回溯獵捕：威脅情報發布新 C2 清單時——先用 lake exploration 互動查證熱點；確認要持續監控後，建每日排程 KQL job 回掃 180 天並把命中升階回分析層開規則；法遵要求「調出某 IP 十二個月內全部原始記錄」時，跑一次 search job 產出 _SRCH 表交件。
  4. 成本檢核：對比舊解法（全量分析層＋archive）：擷取費從「每 GB 全價」變成「湖價＋摘要」，查歷史從「先還原再查」變成「直接查湖」。三個工具各自出現在該出現的位置——這一段就是考試想看你做的完整決策。
08 — 🧩 考綱補洞

Auxiliary logs 與傳統 archive：舊詞彙怎麼對映新架構

  • Auxiliary logs（輔助記錄）與 lake 的關係：auxiliary 是 Log Analytics 的低成本資料表方案，可視為 lake 層的「前身與入口」——同樣主打便宜擷取、受限查詢、verbose 資料。工作區接入 data lake 後，auxiliary 方案資料表的資料就存放於 lake 層，並獲得 lake 的完整查詢工具（exploration／jobs／筆記本）。考題看到 auxiliary logs，就往「低成本層」歸類，與分析層對舉。
  • 與傳統 archive（長期封存）的差異：舊模型裡超過互動保留的資料進入封存狀態——不能直接查詢，必須先跑 search job 或還原（restore）成暫存表，才碰得到。lake 的關鍵進步是「長期資料維持可查」：互動 KQL、筆記本、KQL jobs 直接打在湖上，不需還原程序。接入 lake 後，長期保留即由 lake 提供；「archive＋restore」在考題中若與 lake 並列，通常是被淘汰的干擾項。
  • Restore（還原）還會考嗎：仍可能以舊題型出現——「需要對封存資料做高效能完整 KQL 調查」的傳統答案是 restore。但在標明「已接入 data lake」的題幹裡，直接查 lake 或跑 KQL job 幾乎總是更省事的正解。
  • 前提條件：Sentinel data lake 建立在 Defender 入口網站統一平台上——工作區要先連入 Defender 入口網站（第四天講過的統一 SOC 平台），才能接入 lake。這也解釋了為什麼 2026 考綱把「入口統一」與「data lake」綁在同一波更新。

QUESTION 1 · D1-0056
Your workspace is onboarded to the Microsoft Sentinel data lake. Sign-in logs are kept in the analytics tier so that near-real-time rules can use them. A compliance officer asks whether those same sign-in records will still be available for a historical investigation 12 months from now, and management insists that you must not pay to ingest the same records twice. What should you tell the compliance officer?
（貴公司的工作區已接入 Microsoft Sentinel data lake。登入記錄留在分析層（analytics tier），供近乎即時（NRT）規則使用。法遵人員詢問：12 個月後做歷史調查時，這些登入記錄是否還查得到？管理層同時要求不得為同一批記錄付兩次擷取費用。你應該怎麼回答？）
A. Data that lands in the analytics tier is automatically mirrored into the data lake at no additional ingestion cost, so it remains available for long-term investigation.
進入分析層的資料會自動鏡射一份到資料湖，不另收擷取費用，因此長期調查時仍然查得到。

必須建立 summary rule（彙總規則）把登入記錄複製到資料湖層。

12 個月後必須先執行 search job 把記錄還原，才能再次查詢。

看正解與解析
正解：A

data lake 的關鍵設計是鏡射（mirrored data）：凡是進入分析層的資料，都會自動鏡射一份到資料湖且不另收擷取費，所以資料湖永遠擁有「全量」。反過來不成立——只進資料湖的資料不會出現在分析層。記住一句話：「分析層管『現在』，lake 管『全部』」，資料只會由湖升階回分析層，不會自動反向流動。

  • B：summary rule 的用途是把高量資料排程彙總成摘要，寫進「分析層」的自訂資料表供偵測與儀表板使用，方向與本題相反，也不是把原始記錄搬進資料湖的機制。
  • C：search job 與還原（restore）是舊的封存模型才需要的程序；接入 data lake 之後，長期資料維持可查，用互動查詢、KQL job 或筆記本可以直接打在湖上，不必先還原。
  • D：再建一條 DCR 複製寫入等於重複擷取、重複付費，正好違反題幹「不得付兩次擷取費」的要求；鏡射已經免費做到這件事。

QUESTION 5 · D1-0060

（工作區接入 Microsoft Sentinel data lake 之後，你要為每一張資料表指定所屬的層級。資料表具備下列哪一項特性時，就必須留在分析層（analytics tier）？）
A. The table must be retained for 12 years to satisfy a compliance mandate.
該資料表為了滿足合規要求必須保留 12 年。
B. The table is queried only a few times a year, during audits.
該資料表一年只在稽核時查詢幾次。
C. Scheduled analytics rules and near-real-time (NRT) rules run against the table.
有排程分析規則與近乎即時（NRT）規則會針對該資料表執行。
D. The table holds high-volume verbose netflow records.
該資料表存放高量的詳細（verbose）netflow 記錄。
看正解與解析
正解：C

分層決策只問兩個問題：這份資料要不要驅動即時偵測？它的查詢頻率配不配得上分析層的擷取單價。偵測引擎只讀分析層——排程分析規則與 NRT 規則都只在這一層執行，所以只要有規則要吃這張表，它就沒有第二個選擇。其餘特性（長期保留、極少查詢、高量 verbose）都是資料湖層的指紋；需要偵測面時，再用 summary rules 或 KQL jobs 把摘要／命中結果送回分析層。

  • A：最長 12 年的總保留正是資料湖層提供的能力，長期保留需求本身反而是往湖層放的理由。
  • B：一年只查幾次代表查詢頻率配不上分析層的擷取單價，應該放進資料湖層，需要時再用互動查詢或 KQL job 撈。
  • D：高量、單筆價值低的 verbose 記錄（netflow、防火牆 allow 流量、DNS）是資料湖層的典型資料，全部塞進分析層會直接違反成本最小化。
