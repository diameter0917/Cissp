01 — 📌 本日導讀

五週的最後一哩：把 24 課接成一條線

五週速成的最後一天。前 24 課你是一課一個主題地讀，但考試不會這樣問——它給你一段 SOC 情境，同時牽涉資料怎麼進來、警示怎麼產生、事件怎麼處理、盲區怎麼補，然後只問一句「下一步該做什麼」。今天要把 24 塊拼圖接成一條因果鏈，練一次端到端攻擊鏈演練，把最容易在考場上打架的概念分乾淨，最後談答題思路。

今日目標（跨三大領域，不對應單一考綱條目）：
  • ☐ 說出 D1 環境 → D2 回應 → D3 搜捕 的因果關係，以及任一層失效時的後果
  • ☐ 對一條完整攻擊鏈的每一步，答出「哪個產品偵測、在哪張表看到、下一步做什麼」
  • ☐ 分辨七組最易混淆的概念，並說出各自的判準問句
  • ☐ 建立 best-answer 的解題流程：先抓限定詞、再比範圍、最後刪選項
  • ☐ 完成五週回顧檢查表，標出還要回頭補的課次
💡 這封信談的是思路串接；三大領域速記表與考試當天的行政攻略排在考前最後一天（Day 40），事實性記憶留到那時再壓縮，今天先把因果關係想通。
02 — 📺 影片伴讀

EP9 沒有字幕，EP10 的收尾正好是總複習

本單元掛的是 EP9「Create detections and perform investigations in Microsoft Sentinel」與 EP10「Perform threat hunting in Microsoft Sentinel」兩支影片。先誠實說明：本專案抓不到 EP9 的字幕檔（其他集有 .en.txt，EP9 只有影片資訊），所以下面不會出現任何 EP9 的時間碼——沒有字幕就不編時間碼，這是本專案的底線。EP9 請自行複習分析規則、自動化與調查三段，重點已整理在 Day 17–19。

EP10 有完整字幕，而它的開場與收尾恰好是最好的總複習素材——那兩段講的不是功能，是整個 SOC 的世界觀：

  • EP10 00:33「如果你只依賴已經被偵測到的東西，等你發現時往往已經擴散」——這句話就是三大領域因果鏈的起點：偵測永遠有盲區，所以才需要搜捕。
  • EP10 03:27 起講搜捕的定義：不同團隊講法不一，但共通點是03:34「主動搜尋環境中尚未被偵測到的威脅」；03:51 明講這正是搜捕與事件回應的分界——回應從「已經被標記的東西」開始，搜捕從「還沒被標記」開始。這條界線是 D2 與 D3 的分水嶺，考題很愛在這裡設陷阱。
  • EP10 04:01「搜捕是持續性的」；04:25 起列出好假說的五個條件：可完成、04:30 範圍夠窄能被證實或推翻、04:38 有時間邊界、04:50 有用且有效率、04:59 貼合你要防的威脅模型。這五條是 D3 的送分題。
  • EP10 05:53–07:50 是搜捕工作流濃縮版：查詢 →06:08 迭代提問 →06:34 書籤保存證據 →07:10 Livestream 對照即時活動 →07:38 MITRE ATT&CK 矩陣，07:50 點出矩陣顏色圖例對應你的偵測涵蓋度——哪裡沒顏色，哪裡就是要補的能見度。
  • EP10 25:12 起是整個系列的總回顧，26:14 勉勵「保持好奇、持續探索」，26:25 直接建議你去考 SC-200——你今天剛好走到他說的那一步。
03 — 🗺️ 三大領域知識地圖

三層因果：沒有資料就沒有偵測

三大領域不是三個並列主題，而是一條有方向的生產線：D1 決定「你看得到什麼」，D2 決定「看到之後怎麼處理」，D3 負責「回頭撿沒看到的」。這個方向感是很多情境題的隱藏判準——題目問「為什麼分析規則沒觸發」，答案常常不在 D2，而在 D1 的資料根本沒進來。

領域（權重）回答的問題主要產品／能力這一層失效的後果對應課次
D1 管理安全性作業環境
（40–45%）		資料從哪來、收多少、存多久、誰能看？環境怎麼設定才防得住？資料連接器、DCR、ASIM、data lake、MDE 上線與裝置群組、ASR、威脅情報、統一 RBAC、Security Copilot看不見：表沒資料，規則寫得再好也不觸發；成本失控被迫砍記錄，砍掉的正好是關鍵證據Day 1、4–11
D2 回應安全性事件
（35–40%）		訊號怎麼變成警示與事件？誰先處理？怎麼止血、怎麼自動化？XDR 事件分診、MDE 隔離／Live Response、MDO 郵件補救、MDI／Entra ID Protection、分析規則四型、自動化規則與劇本看得見但動不了：警示淹沒佇列、誤報吃光人力，真事件淹在雜訊裡Day 12–20
D3 執行威脅搜捕
（20–25%）		還有什麼是沒被偵測到的？怎麼把發現變成長期偵測？KQL、進階搜捕、Hunts／書籤／Livestream、MITRE 對應、自訂偵測、Graph／MCP／湖上回溯 2026盲區留著：低調緩慢的攻擊長期潛伏，等觸發規則時已到最後一步Day 2–3、21–24
💡 這條線是雙向的：搜捕的產出要變成自訂偵測或分析規則回頭餵養 D2；搜捕發現「這張表根本沒資料」時，則要回頭改 D1 的連接器與 DCR。三個領域是一個閉環，不是三個抽屜。
04 — 🧪 端到端攻擊鏈演練

一封釣魚信走完四個階段

今天的主菜。每一步都問同樣三個問題：誰偵測到、在哪裡看到、下一步做什麼。讀之前先蓋住答案自己講一次，講不出來的那一步就是你的弱項。

🧪 情境：從一封發票釣魚信到 40 GB 資料外洩

T0｜投遞　行銷部 12 人收到偽裝成供應商的發票信，連結投遞當下乾淨，兩小時後才換成假登入頁。
誰偵測：Defender for Office 365（MDO）的 Safe Links 在點擊當下重新驗證目的地。在哪看：Threat Explorer、進階搜捕的 EmailEvents 與 UrlClickEvents。下一步：以寄件網域與主旨撈出同批郵件，未讀的 soft delete、確認惡意的 hard delete，並確認 ZAP 是否已動作。

T1｜認證竊取　兩位使用者輸入了帳密，攻擊者 40 分鐘後從境外匿名 IP 成功登入。
誰偵測：Entra ID Protection 的登入風險偵測（匿名 IP、不可能的旅行）；接了 Sentinel 也會被 Fusion 關聯成多階段事件。在哪看：XDR 的身分警示、SigninLogs／IdentityLogonEvents。下一步：撤銷工作階段與權杖、強制安全密碼變更；用風險型條件式存取讓後續高風險登入自動被擋，而不是等人工。

T2｜雲端立足　攻擊者建立收件匣規則，把含「invoice」的信自動轉寄外部並封存。
誰偵測：Defender for Cloud Apps 的可疑收件匣操作原則。在哪看：CloudAppEvents。下一步：移除轉寄規則、盤點該帳號近期同意的 OAuth 應用程式——被遺留的同意權限是最常漏掉的後門。

T3｜橫向移動　該帳號密碼與地端 AD 相同，攻擊者以 VPN 進內網做帳號列舉，再用竊得的票證存取檔案伺服器。
誰偵測：Defender for Identity（MDI）——偵察、pass-the-ticket、異常資源存取；端點側由 MDE 補上。在哪看：IdentityDirectoryEvents／IdentityLogonEvents、MDI 實體頁時間軸。下一步：停用或強制重設帳號（需先設好 MDI 動作帳戶）、隔離跳板裝置；先止血再取證——隔離後 Live Response 通道仍在，取證不受影響。

T4｜外洩　攻擊者在檔案伺服器壓出 40 GB 壓縮檔，分批上傳個人雲端儲存。
誰偵測：MDE 的檔案與網路事件、Purview 的資料外流訊號。在哪看：DeviceFileEvents／DeviceNetworkEvents、Action center。下一步：以指標（indicator）封鎖外傳網域與檔案雜湊，確認範圍後啟動通報流程。

T5｜收攏成一件事　上述警示分散在四個產品，但在 XDR 佇列裡應該是一個事件。分診從事件層看時間軸，不逐條追警示；用自動化規則指派給身分小組並拉高嚴重性，用劇本發 Teams 通知與開工單——改屬性用前者、跟外部互動用後者。

T6｜補盲區（最像 D3 考題的一步）　真正的問題是：另外 10 個收信的人呢？沒觸發警示不代表沒點。這時要離開事件、進搜捕：以「收到這批信 → 點了連結 → 4 小時內成功登入」為假說寫跨表查詢，命中存成書籤，值得長期監控的轉自訂偵測，要往前追一年的用 data lake 回溯。

T7｜回頭修 D1　覆盤發現 VPN 記錄沒接進工作區，所以 T3 晚了六小時才看見——這不是規則的錯，是資料接入的洞。補連接器、用 DCR 過濾雜訊控成本，閉環回到 D1。

// T6 的跨領域搜捕：收到釣魚信 → 點了連結 → 4 小時內出現成功登入
let Window = 7d;
let Phish = EmailEvents
    | where Timestamp > ago(Window)
    | where SenderMailFromDomain has "invoice-portal-secure"
    | project NetworkMessageId, RecipientEmailAddress;
let Clicks = UrlClickEvents
    | where Timestamp > ago(Window)
    | where ActionType == "ClickAllowed"
    | project NetworkMessageId, AccountUpn, Url, ClickTime = Timestamp;
Phish
| join kind=inner Clicks on NetworkMessageId
| join kind=inner (
    IdentityLogonEvents
    | where Timestamp > ago(Window)
    | where ActionType == "LogonSuccess"
    | project AccountUpn, LogonTime = Timestamp, DeviceName, IPAddress
  ) on AccountUpn
| where LogonTime between (ClickTime .. ClickTime + 4h)
| project RecipientEmailAddress, Url, ClickTime, LogonTime, DeviceName, IPAddress
| order by ClickTime asc
逐行解說：一支查詢跨了兩個產品、三張表——郵件與點擊來自 MDO、登入來自身分側，這正是進階搜捕的價值。兩個 join kind=inner 分別用 NetworkMessageId（同一封信）與 AccountUpn（同一個人）當接點，選對接點欄位是跨表題的關鍵。最後 between (ClickTime .. ClickTime + 4h) 是靈魂：把點擊與登入綁進一個因果時間窗，避免把日常登入誤判成入侵。命中的列要對應實體再存書籤，之後才能接進事件調查。
05 — 🔀 最容易混淆的概念

七組雙胞胎與它們的判準問句

下面七組是最常被選錯的配對。不要只記定義，要記判準問句——考場上沒時間回憶整章，只能靠一個問題把兩個選項分開。

易混配對一句話差別判準問句（題幹出現什麼就選它）常見陷阱
自動化規則 vs 劇本（Playbook）前者改事件本身的屬性與流程；後者是 Logic Apps 流程，去跟外部互動事情做在 Sentinel 內（指派、標記、關閉）→ 自動化規則；要發通知、開工單、打 API → 劇本忘了劇本要靠自動化規則觸發，且需先授予 Sentinel 執行劇本的權限
Scheduled vs NRT vs Fusion排程＝自寫 KQL＋自訂間隔與回顧期；NRT＝約每分鐘、查詢受限（單表為主）；Fusion＝內建 ML 跨階段關聯「自訂邏輯與時間窗」→ Scheduled；「延遲最小、幾乎即時」→ NRT；「把分散的低嚴重警示串成多階段攻擊」→ Fusion拿 NRT 寫需要 join 的複雜關聯；或以為 Fusion 能改查詢（只能啟用／停用與排除）
DCR vs ASIM vs 監視清單DCR＝寫入前決定收什麼與轉換；ASIM＝查詢時把不同來源正規化；監視清單＝你自備的參考資料表「降成本／遮罩敏感欄位」→ DCR；「一支查詢跨多廠牌來源」→ ASIM；「比對 VIP 或已知 IP 清單」→ 監視清單把 ASIM 當省錢手段——它不減少擷取量，省錢的是 DCR
分析層 vs data lake 2026分析層貴、可即時查、能被分析規則讀取；湖層便宜存得久，適合大範圍長時間「要觸發偵測／即時調查」→ 分析層；「保存數年、回溯歷史、法遵調閱」→ data lake忘記湖裡的發現要升階回分析層才能變成偵測
使用者風險 vs 登入風險使用者風險＝這個身分已遭入侵的機率；登入風險＝這一次登入不是本人的機率「憑證可能外洩」→ 使用者風險，修復是強制安全密碼變更；「這次登入來自匿名 IP／不可能的旅行」→ 登入風險，修復是要求 MFA 或封鎖兩個都選「封鎖使用者」——考題要的是對應風險的最小必要修復
soft delete vs hard deletesoft＝移到可復原項目，仍救得回；hard＝標記永久清除，一般復原流程救不回「先移除但保留可復原性」→ soft；「確定惡意、要徹底清除」→ hard沒注意題幹是否要求保留取證能力——要取證就別急著 hard delete
自訂偵測 vs 分析規則自訂偵測建在 XDR 進階搜捕上，只跑 XDR 資料；分析規則建在 Sentinel，跑工作區所有來源「只用到 Device／Email／Identity 表」→ 自訂偵測；「要關聯防火牆、第三方或自訂記錄」→ 分析規則忘了自訂偵測查詢必須輸出 Timestamp、ReportId 等欄位，且要對應實體才能自動採取動作
🎯 考點聚焦：二選一時的三個判準

選項刪到剩兩個而兩個都像對的，依序問這三題：
① 範圍對不對？資料來源決定產品：只提 Microsoft 365 與端點 → XDR 就夠；一旦出現防火牆、第三方或自訂記錄 → 必須是 Sentinel。
② 時機對不對？同一個動作在不同階段有不同答案——擷取前是 DCR、查詢時是 ASIM、事件發生後才是自動化。
③ 成本／努力對不對？只要出現 minimize cost、minimize administrative effort，就是在問「有沒有內建、不用自己造的做法」——選內建功能，不選自寫指令碼。

06 — 🎯 答題策略

Best-answer 不是選對的，是選最對的

SC-200 幾乎不考「哪個是錯的」，它給你四個都是真功能的選項，其中兩三個確實做得到，只有一個最貼題幹。所以做題的動作順序要反過來：先讀最後那句問句，再回頭找限定詞，最後才看情境細節。情境是用來提供限定條件的，不是拿來讀爽的。

💡 限定詞就是答案的座標：first（先做什麼）通常選最能止血又最不破壞證據的動作；least privilege 選剛好夠用的角色，不選 Global Administrator；minimize 系列選內建、自動、免額外建置的；continuously／ongoing 指向規則或排程，one-time 指向手動查詢或 search job。

🎯 考點聚焦：微軟題的四種標準干擾項

認出干擾項的長相，比記住正解更快：
① 對的產品、錯的功能——產品名讓你安心（都是 Defender），但功能解決的是別的問題（例如問偵測卻給你回應動作）。
② 對的功能、錯的時機——動作本身沒錯，但發生在錯的階段（事件都成立了才想用 DCR 過濾）。
③ 做過頭——重建工作區、寫自訂劇本、部署新代理程式；當題幹說「minimize effort」時，做過頭一定不是答案。
④ 做不夠——只做了一半（只停用帳號卻不撤銷權杖、只刪郵件卻不查同批收件者）。
兩題都通過這四關還是選不出來，就回到題幹最後一句再讀一次——那句話的動詞（detect／investigate／respond／prevent／identify）通常直接指定了領域。

💡 配速練習：考試約 55–60 題／100 分鐘，平均一題 100 秒。從明天的刷題開始就用這個節奏練，並把每題分成三堆——秒答（不到 30 秒）、猶豫（想超過 60 秒但選出來了）、不會。真正要花時間檢討的是「猶豫」那堆：那是你知識有但界線模糊的地方，也是最容易在考場上被干擾項吃掉的分數。
