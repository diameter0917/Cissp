01 — 📌 本日導讀

五週的最後一哩：把 24 課接成一條線

五週速成的最後一天。前 24 課你是一課一個主題地讀，但考試不會這樣問——它給你一段 SOC 情境，同時牽涉資料怎麼進來、警示怎麼產生、事件怎麼處理、盲區怎麼補，然後只問一句「下一步該做什麼」。今天要把 24 塊拼圖接成一條因果鏈，練一次端到端攻擊鏈演練，把最容易在考場上打架的概念分乾淨，最後談答題思路。

今日目標（跨三大領域，不對應單一考綱條目）：

02 — 📺 影片伴讀

EP9 沒有字幕，EP10 的收尾正好是總複習

本單元掛 EP9「Create detections and perform investigations in Microsoft Sentinel」與 EP10「Perform threat hunting in Microsoft Sentinel」。先誠實說明：本專案抓不到 EP9 的字幕檔（只有影片資訊），所以下面不會出現任何 EP9 時間碼——沒有字幕就不編時間碼，這是底線。EP9 請自行複習分析規則、自動化與調查三段，重點已整理在 Day 17–19。

EP10 有完整字幕，而它的開場與收尾恰好是最好的總複習素材——那兩段講的不是功能，是整個 SOC 的世界觀：

  • EP10 00:33「如果你只依賴已經被偵測到的東西，等你發現時往往已經擴散」——這句話就是三大領域因果鏈的起點：偵測永遠有盲區，所以才需要搜捕。
  • EP10 03:34 給搜捕下定義：「主動搜尋環境中尚未被偵測到的威脅」；03:51 明講這正是搜捕與事件回應的分界——回應從「已被標記」開始，搜捕從「還沒被標記」開始。這條線就是 D2 與 D3 的分水嶺。
  • EP10 04:25 起列出好假說的五個條件：可完成、04:30 範圍夠窄能被證實或推翻、04:38 有時間邊界、04:50 有用且有效率、04:59 貼合你要防的威脅模型——這五條是 D3 送分題。
  • EP10 05:53–07:50 是搜捕工作流濃縮版：查詢 →06:08 迭代提問 →06:34 書籤保存證據 →07:10 Livestream 對照即時活動 →07:38 MITRE ATT&CK 矩陣，07:50 點出矩陣顏色圖例對應你的偵測涵蓋度——哪裡沒顏色，哪裡就是要補的能見度。
  • EP10 25:12 起是本學習路徑的總回顧，26:14 勉勵「保持好奇、持續探索」，26:25 直接建議你去考 SC-200——你今天剛好走到他說的那一步。
03 — 🗺️ 三大領域知識地圖

三層因果：沒有資料就沒有偵測

三大領域不是三個並列主題，而是一條有方向的生產線：D1 決定「你看得到什麼」，D2 決定「看到之後怎麼處理」，D3 負責「回頭撿沒看到的」。這個方向感是情境題的隱藏判準——題目問「為什麼分析規則沒觸發」，答案常常不在 D2，而在 D1 的資料根本沒進來。

領域（權重）回答的問題主要產品／能力這一層失效的後果對應課次
D1 管理安全性作業環境
（40–45%）		資料從哪來、收多少、存多久、誰能看？資料連接器、DCR、ASIM、data lake、MDE 上線與裝置群組、ASR、威脅情報、統一 RBAC、Security Copilot看不見：表沒資料，規則寫再好也不觸發；成本失控被迫砍記錄，砍掉的正好是關鍵證據Day 1、4–11
D2 回應安全性事件
（35–40%）		訊號怎麼變成事件？誰先處理？怎麼止血與自動化？XDR 分診、MDE 隔離／Live Response、MDO 郵件補救、MDI／Entra ID Protection、分析規則四型、自動化規則與劇本看得見但動不了：誤報吃光人力，真事件淹在雜訊裡Day 12–20
D3 執行威脅搜捕
（20–25%）		還有什麼沒被偵測到？怎麼把發現變成長期偵測？KQL、進階搜捕、Hunts／書籤／Livestream、MITRE 對應、自訂偵測、Graph／MCP／回溯 2026盲區留著：低調緩慢的攻擊長期潛伏，等觸發規則時已到最後一步Day 2–3、21–24
💡 這條線是雙向的：搜捕的產出要變成自訂偵測或分析規則回頭餵養 D2；搜捕發現「這張表根本沒資料」時，則要回頭改 D1 的連接器與 DCR。三個領域是一個閉環，不是三個抽屜。
04 — 🧪 端到端攻擊鏈演練

一封釣魚信走完四個階段

今天的主菜。每一步都問同樣三個問題：誰偵測到、在哪裡看到、下一步做什麼。先蓋住答案自己講一次，講不出來的那一步就是弱項。

🧪 情境：從一封發票釣魚信到 40 GB 資料外洩

T0｜投遞　行銷部 12 人收到偽裝成供應商的發票信，連結投遞當下乾淨，兩小時後才換成假登入頁。
誰偵測：Defender for Office 365（MDO）的 Safe Links 在點擊當下重驗目的地。在哪看：Threat Explorer、EmailEvents 與 UrlClickEvents。下一步：用寄件網域與主旨撈出同批郵件，未讀的 soft delete、確認惡意的 hard delete，並檢查 ZAP 是否已動作。

T1｜認證竊取　兩位使用者輸入了帳密，攻擊者 40 分鐘後從境外匿名 IP 成功登入。
誰偵測：Entra ID Protection 的登入風險偵測（匿名 IP、不可能的旅行）；接了 Sentinel 也會被 Fusion 關聯成多階段事件。在哪看：SigninLogs／IdentityLogonEvents。下一步：撤銷工作階段與權杖、強制安全密碼變更；用風險型條件式存取讓後續高風險登入自動被擋，而不是等人工。

T2｜雲端立足　攻擊者建立收件匣規則，把含「invoice」的信自動轉寄外部並封存。
誰偵測：Defender for Cloud Apps 的可疑收件匣操作原則。在哪看：CloudAppEvents。下一步：移除轉寄規則、盤點該帳號同意過的 OAuth 應用程式——被遺留的同意權限是最常漏掉的後門。

T3｜橫向移動　該帳號密碼與地端 AD 相同，攻擊者以 VPN 進內網做帳號列舉，再用竊得的票證存取檔案伺服器。
誰偵測：Defender for Identity（MDI）——偵察、pass-the-ticket、異常資源存取。在哪看：IdentityDirectoryEvents／IdentityLogonEvents、MDI 實體頁時間軸。下一步：停用或強制重設帳號（需先設好 MDI 動作帳戶）、隔離跳板裝置；先止血再取證——隔離後 Live Response 通道仍在，取證不受影響。

T4｜外洩　攻擊者在檔案伺服器壓出 40 GB 壓縮檔，分批上傳個人雲端儲存。
誰偵測：MDE 的檔案與網路事件、Purview 的資料外流訊號。在哪看：DeviceFileEvents／DeviceNetworkEvents。下一步：以指標（indicator）封鎖外傳網域與檔案雜湊，確認範圍後啟動通報流程。

T5｜收攏成一件事　上述警示分散在四個產品，但在 XDR 佇列裡應該是一個事件。分診從事件層看時間軸，不逐條追警示；自動化規則指派給身分小組並拉高嚴重性，劇本發 Teams 通知與開工單。

T6｜補盲區（最像 D3 考題的一步）　真正的問題是：另外 10 個收信的人呢？沒觸發警示不代表沒點。此時離開事件、進搜捕：以「收到這批信 → 點了連結 → 4 小時內成功登入」為假說寫跨表查詢，命中存書籤，值得長期監控的轉自訂偵測，要追一年的用 data lake 回溯。

T7｜回頭修 D1　覆盤發現 VPN 記錄沒接進工作區，T3 晚了六小時才被看見——這不是規則的錯，是資料接入的洞。補連接器、用 DCR 控成本，閉環回到 D1。

// T6 的跨領域搜捕：收到釣魚信 → 點了連結 → 4 小時內出現成功登入
let Window = 7d;
let Phish = EmailEvents
    | where Timestamp > ago(Window)
    | where SenderMailFromDomain has "invoice-portal-secure"
    | project NetworkMessageId, RecipientEmailAddress;
let Clicks = UrlClickEvents
    | where Timestamp > ago(Window)
    | where ActionType == "ClickAllowed"
    | project NetworkMessageId, AccountUpn, Url, ClickTime = Timestamp;
Phish
| join kind=inner Clicks on NetworkMessageId
| join kind=inner (
    IdentityLogonEvents
    | where Timestamp > ago(Window)
    | where ActionType == "LogonSuccess"
    | project AccountUpn, LogonTime = Timestamp, DeviceName, IPAddress
  ) on AccountUpn
| where LogonTime between (ClickTime .. ClickTime + 4h)
| project RecipientEmailAddress, Url, ClickTime, LogonTime, DeviceName, IPAddress
| order by ClickTime asc
逐行解說：一支查詢跨三張表、兩個產品——郵件與點擊來自 MDO、登入來自身分側，這正是進階搜捕的價值。兩個 join kind=inner 分別用 NetworkMessageId（同一封信）與 AccountUpn（同一個人）當接點，選對接點欄位是跨表題的關鍵。最後 between (ClickTime .. ClickTime + 4h) 是靈魂：把點擊與登入綁進因果時間窗，避免把日常登入誤判成入侵。命中的列要對應實體再存書籤，才能接進事件調查。
05 — 🔀 最容易混淆的概念

七組雙胞胎與它們的判準問句

下面七組最常被選錯。不要只記定義，要記判準問句——考場上沒時間回憶整章，只能靠一個問題把兩個選項分開。

易混配對一句話差別判準問句（題幹出現什麼就選它）常見陷阱
自動化規則 vs 劇本（Playbook）前者改事件本身的屬性與流程；後者是 Logic Apps 流程，去跟外部互動事情做在 Sentinel 內（指派、標記、關閉）→ 自動化規則；發通知、開工單、打 API → 劇本忘了劇本要靠自動化規則觸發，且需先授予 Sentinel 執行權限
Scheduled vs NRT vs Fusion排程＝自寫 KQL＋自訂間隔與回顧期；NRT＝約每分鐘、查詢受限；Fusion＝內建 ML 跨階段關聯「自訂邏輯與時間窗」→ Scheduled；「延遲最小、幾乎即時」→ NRT；「把分散的低嚴重警示串成多階段攻擊」→ Fusion拿 NRT 寫需要 join 的複雜關聯；或以為 Fusion 能改查詢（只能啟用／停用與排除）
DCR vs ASIM vs 監視清單DCR＝寫入前決定收什麼與轉換；ASIM＝查詢時把不同來源正規化；監視清單＝你自備的參考資料表「降成本／遮罩敏感欄位」→ DCR；「一支查詢跨多廠牌來源」→ ASIM；「比對已知 IP 清單」→ 監視清單把 ASIM 當省錢手段——它不減少擷取量，省錢的是 DCR
分析層 vs data lake 2026分析層貴、可即時查、能被分析規則讀取；湖層便宜存得久「要觸發偵測／即時調查」→ 分析層；「存數年、回溯歷史、法遵調閱」→ data lake忘記湖裡的發現要升階回分析層才能變成偵測
使用者風險 vs 登入風險使用者風險＝這個身分已遭入侵的機率；登入風險＝這一次登入不是本人的機率「憑證可能外洩」→ 使用者風險，修復是強制密碼變更；「這次登入來自匿名 IP／不可能的旅行」→ 登入風險，修復是要求 MFA 或封鎖兩個都選「封鎖使用者」——考題要的是對應風險的最小必要修復
soft delete vs hard deletesoft＝移到可復原項目，仍救得回；hard＝標記永久清除，一般復原流程救不回「先移除但保留可復原性」→ soft；「確定惡意、要徹底清除」→ hard沒注意題幹是否要求保留取證能力——要取證就別急著 hard delete
自訂偵測 vs 分析規則自訂偵測建在 XDR 進階搜捕上，只跑 XDR 資料；分析規則建在 Sentinel，跑工作區所有來源「只用到 Device／Email／Identity 表」→ 自訂偵測；「要關聯防火牆或自訂記錄」→ 分析規則忘了查詢必須輸出 Timestamp、ReportId 等欄位，且要對應實體才能自動採取動作
🎯 考點聚焦：二選一時的三個判準

選項刪到剩兩個而兩個都像對的，依序問這三題：
① 範圍對不對？資料來源決定產品：只提 Microsoft 365 與端點 → XDR 就夠；一旦出現防火牆、第三方或自訂記錄 → 必須是 Sentinel。
② 時機對不對？同一件事在不同階段有不同答案——擷取前是 DCR、查詢時是 ASIM、事件發生後才是自動化。
③ 成本／努力對不對？出現 minimize cost、minimize administrative effort，就是在問「有沒有內建、不用自己造的做法」——選內建功能，不選自寫指令碼。

06 — 🎯 答題策略

Best-answer 不是選對的，是選最對的

SC-200 幾乎不考「哪個是錯的」，它給四個都是真功能的選項，其中兩三個確實做得到，只有一個最貼題幹。所以做題順序要反過來：先讀最後那句問句，再找限定詞，最後才看情境細節。

💡 限定詞就是答案的座標：first 通常選最能止血又最不破壞證據的動作；least privilege 選剛好夠用的角色，不選 Global Administrator；minimize 系列選內建、免額外建置的；continuously 指向規則或排程，one-time 指向手動查詢或 search job。
🎯 考點聚焦：微軟題的四種標準干擾項

認出干擾項的長相比記住正解更快：
① 對的產品、錯的功能——產品名讓你安心，但那個功能解決的是別的問題（問偵測卻給你回應動作）。
② 對的功能、錯的時機——動作本身沒錯，但發生在錯的階段（事件都成立了才想用 DCR 過濾）。
③ 做過頭——重建工作區、寫自訂劇本、部署新代理程式；當題幹說「minimize effort」時，做過頭一定不是答案。
④ 做不夠——只做一半（停用帳號卻不撤銷權杖、刪郵件卻不查同批收件者）。
過完四關還是選不出來，就回頭讀題幹最後一句——那句的動詞（detect／investigate／respond／prevent）通常已指定了領域。

💡 配速練習：考試約 55–60 題／100 分鐘，平均一題 100 秒；從明天刷題就用這個節奏，並把題目分三堆——秒答、猶豫（超過 60 秒但選出來了）、不會。最該檢討的是「猶豫」那堆：知識有但界線模糊，正是最容易被干擾項吃掉的分數。

  • 第 7–8 週｜混合與模擬：錯題第一輪 → 依權重抽樣的隨機 50 題 → 三次計時模擬考（各 55 題／100 分鐘），每次考完隔天都排檢討日，再用統計頁挑最弱領域重練。
  • 怎麼用儀表板：首頁看進度與各領域正確率，領域頁對照第 03 節地圖找洞；刷題三種模式分清楚——領域練熟、隨機練切換、模擬練配速，錯題模式留給檢討日。
  • 唯一的紀律：正確率低於 60% 的主題當天就回頭讀那封信，別拖到考前一週——那時只剩速記表的時間了。

QUESTION 1 · D1-0016
You are a security operations analyst. A scheduled analytics rule that is meant to detect password-spray attempts against your VPN concentrator has raised no incidents in six weeks, although the identity team confirmed three spray campaigns during that period. The rule is enabled, its query validates without errors, and identical logic works in your lab workspace. What should you verify first?
（你是資安維運分析師。一條用來偵測 VPN 集中器密碼噴灑攻擊的排程分析規則，六週來一件事件都沒產生，但身分小組確認這段期間確實發生過三次噴灑。規則是啟用的、查詢語法驗證無誤，同樣的邏輯在實驗工作區也跑得出來。你應該最先確認什麼？）
A. Whether the VPN concentrator records are actually arriving in the workspace table that the rule queries, by checking the data connector and its data collection rule.
檢查資料連接器與其資料收集規則（DCR），確認 VPN 集中器的記錄真的有進到規則所查詢的那張資料表。
B. Whether the rule threshold is too high, and lower it while shortening the lookback period.
確認規則門檻是否設得太高，把門檻調低並縮短回顧期。
C. Whether an automation rule is closing the incidents automatically as benign positives.
確認是不是有自動化規則把事件當成良性正確結果自動關閉了。
D. Whether UEBA is enabled so that the workspace can build a behavioural baseline for the VPN accounts.
確認是否已啟用 UEBA，讓工作區為 VPN 帳號建立行為基線。
看正解與解析
正解：A

這題考的是三大領域的因果順序：D1 的資料接入是 D2 偵測的前提。查詢語法正確、在別的工作區跑得出來，代表邏輯沒問題；那麼最可能的原因就是這個工作區的目標資料表根本沒有資料，或欄位對不上。排除法的第一步永遠是「資料有沒有進來」——確認連接器狀態、DCR 有沒有把該來源寫入該表、是否被擷取時轉換過濾掉了。先確認資料，再談規則調校，這也是考試「What should you verify first」這類問句的標準思路。

  • B：調門檻與回顧期是在「規則有觸發但太少或太多」時才做的微調。目前是完全沒有事件，先動門檻只會浪費時間，也無法解釋為何相同邏輯在實驗工作區有效。
  • C：自動化規則若自動關閉事件，事件仍會被建立並留在佇列中（狀態為已關閉），你會在事件清單看得到。題幹說的是「沒有產生事件」，兩者現象不同。
  • D：UEBA 提供實體行為分數與異常偵測，是額外的分析能力，並不是排程分析規則執行的前提；沒有 UEBA，規則一樣會依查詢結果觸發。

QUESTION 2 · D1-0017
A post-incident review shows that your VPN appliance never sent its Syslog records to the Microsoft Sentinel workspace, which is why lateral movement was noticed six hours late. You must onboard the appliance, but about 70 percent of its records are keep-alive messages with no detection value and the ingestion budget is fixed. The hunting team also wants to query the new VPN source together with the existing third-party firewall logs by using one query. Which combination should you use?
（事後覆盤發現，你們的 VPN 設備從未把 Syslog 記錄送進 Microsoft Sentinel 工作區，這正是橫向移動晚了六小時才被發現的原因。你必須把這台設備接入，但它約有 70% 的記錄是沒有偵測價值的保持連線訊息，而擷取預算是固定的。搜捕小組另外希望能用一支查詢同時查新的 VPN 來源與既有的第三方防火牆記錄。你應該採用哪一種組合？）
A. Create a watchlist for the VPN address ranges, and add a summary rule that aggregates the firewall table every hour.
為 VPN 位址範圍建立監視清單，並加上每小時彙總防火牆資料表的摘要規則（summary rule）。
B. Ingest every record into the analytics tier, then use an automation rule to close the noisy incidents automatically.
把所有記錄都擷取進分析層，再用自動化規則自動關閉吵雜的事件。
C. Send the appliance records to the data lake tier only, and restore them into the analytics tier whenever a hunt needs them.
把設備記錄只送進 data lake 層，等搜捕需要時再還原（restore）回分析層。
D. Drop the keep-alive records with an ingestion-time transformation in the data collection rule (DCR), and query both sources through ASIM normalization parsers.
在資料收集規則（DCR）用擷取時轉換丟掉保持連線記錄，並透過 ASIM 正規化剖析器查詢這兩個來源。
看正解與解析
正解：D

題幹有兩個明確限定條件，各自對應一個能力。「70% 是雜訊、預算固定」→ 成本要在「寫入前」處理，那是 DCR 的擷取時轉換（transformKql），資料被丟掉就不計費。「一支查詢跨不同廠牌來源」→ 那是「查詢時」的正規化，也就是 ASIM 剖析器把不同來源對應到同一套結構描述。認出「時機」是解這類題的關鍵：省錢在擷取前、跨來源統一在查詢時。

  • A：監視清單是參考資料表，摘要規則是把大量原始資料聚合成小表，兩者都不會減少 VPN 記錄的擷取量，也無法讓兩個不同廠牌的來源用同一套欄位查詢。
  • B：全量擷取正好違反固定預算的限制；自動化規則處理的是「事件」而不是「擷取成本」，而且事件產生後再關閉，錢早就付了。
  • C：只放 data lake 層雖然便宜，但分析規則讀不到湖層資料，會讓偵測延遲的問題原封不動；而且還原是為了特定調查的臨時做法，不是常態接入設計。

QUESTION 3 · D2-0046
A user submitted credentials to a phishing page. You confirmed a successful sign-in from an anonymous IP address, reset the user's password and blocked the sender domain. Three hours later the attacker is still reading the mailbox and creating inbox rules from the same session. Which required step was missed?
（一位使用者在釣魚頁面輸入了帳密。你已確認有一次來自匿名 IP 的成功登入，重設了該使用者的密碼，也封鎖了寄件網域。三小時後，攻擊者仍在用同一個工作階段讀取信箱並建立收件匣規則。少做了哪一個必要步驟？）
A. Zero-hour auto purge (ZAP) was not triggered against the original phishing message.
沒有對原始釣魚郵件觸發零時差自動清除（ZAP）。
B. The user's existing sessions and refresh tokens were never revoked, so the stolen token still authenticates.
沒有撤銷該使用者現有的工作階段與更新權杖，被竊的權杖仍然通得過驗證。
C. Safe Attachments was not configured with the Dynamic Delivery action for the mailbox.
沒有為該信箱把 Safe Attachments 設定成 Dynamic Delivery 動作。
D. The user's device was not isolated in Microsoft Defender for Endpoint.
沒有在 Microsoft Defender for Endpoint（MDE）把該使用者的裝置隔離。
看正解與解析
正解：B

攻擊鏈第二段最常見的漏洞：重設密碼只擋住「下一次用舊密碼登入」，攻擊者手上已經拿到的存取權杖與更新權杖仍然有效，可以繼續存取信箱直到權杖過期。正確的身分回應是重設密碼＋撤銷工作階段與更新權杖，必要時再用風險型條件式存取讓後續高風險登入自動被擋。考試很愛用「做不夠」型的干擾項——動作方向對，但只做了一半。

  • A：ZAP 處理的是已投遞到信箱的惡意郵件本身，能把後來判定為惡意的信件從信箱移除；但它完全不影響攻擊者手上的存取權杖，也阻止不了現有工作階段。
  • C：Safe Attachments 的 Dynamic Delivery 針對的是附件引爆與投遞體驗，本題的攻擊媒介是連結與認證竊取，且事件已經發生，調整郵件防護設定救不了進行中的工作階段。
  • D：本次入侵發生在雲端身分與信箱層，攻擊者是以權杖存取 Exchange Online，不是從該使用者的端點。隔離裝置對雲端工作階段沒有作用，也不符合最小必要處置。

QUESTION 4 · D2-0047
A scheduled analytics rule that detects mass file downloads opens roughly 15 incidents every night. Every one of them comes from a single backup service account doing its normal work, but the same rule also caught two genuine data-staging attempts by user accounts this quarter. You must remove the recurring noise, keep the detection effective for user accounts, and minimize ongoing administrative effort. What should you do?
（一條偵測大量檔案下載的排程分析規則，每晚產生約 15 件事件。這些事件全部來自同一個備份服務帳號的例行工作，但這一季同一條規則也抓到兩次使用者帳號真實的資料集結行為。你必須消除這些反覆出現的雜訊、保留對使用者帳號的偵測效力，並讓後續的管理工作量最小。你應該怎麼做？）
A. Modify the analytics rule query so that the known backup service account is excluded from the results.
修改分析規則的查詢，把這個已知的備份服務帳號從結果中排除。
B. Disable the analytics rule and rely on Fusion multistage attack detection to surface the behaviour instead.
停用這條分析規則，改由 Fusion 多階段攻擊偵測來浮出這類行為。
C. Create an automation rule that closes every incident produced by this rule as a false positive.
建立自動化規則，把這條規則產生的所有事件都當成誤報自動關閉。
D. Delete the rule now and rebuild it later as a near-real-time (NRT) rule with a higher threshold.
現在先刪掉這條規則，之後再用較高門檻改建成近即時（NRT）規則。
看正解與解析
正解：A

誤報處理有固定順序：先調規則、再自動關閉、最後才考慮抑制，永遠不刪規則。本題雜訊來源單一且明確（一個已知服務帳號），最乾淨的做法就是在查詢裡排除它——雜訊從源頭消失，使用者帳號的偵測完全不受影響，之後也不必再人工處理。題幹的「keep the detection effective」與「minimize ongoing administrative effort」兩個限定詞，就是把答案指向「調查詢」而不是「事後補救」。

  • B：停用規則會連使用者帳號的真實偵測一起關掉，本季那兩次資料集結就抓不到了。Fusion 是關聯多個既有訊號的 ML 偵測，不能拿來替代一條特定的自訂偵測邏輯。
  • C：自動關閉能讓佇列變乾淨，但事件仍會被建立，噪音只是被藏起來；更危險的是，若哪天該服務帳號真的被冒用，事件也會被一併自動關閉。它是無法修改查詢時的次佳做法，不是本題最佳解。
  • D：刪除規則會失去偵測與其歷史脈絡，改成 NRT 也解決不了問題——雜訊來自特定帳號而非執行頻率，NRT 的查詢限制反而讓這類邏輯更難實作。

QUESTION 5 · D3-0031
After closing a phishing incident you write a hunting query that correlates EmailEvents, UrlClickEvents and IdentityLogonEvents to list recipients who clicked the malicious link and then signed in successfully within four hours. The query finds two additional victims that never generated an alert. Going forward the same pattern must raise an alert automatically, with the least administrative effort. What should you create?
（結案一起釣魚事件後，你寫了一支搜捕查詢，關聯 EmailEvents、UrlClickEvents 與 IdentityLogonEvents，找出點了惡意連結、且在四小時內成功登入的收件者，結果多找到兩位從未產生警示的受害者。從現在起，同樣的樣式必須自動產生警示，而且要用最少的管理工作量。你應該建立什麼？）
A. A Microsoft Sentinel watchlist that stores the affected recipients so that later queries can reference them.
建立 Microsoft Sentinel 監視清單（Watchlist）保存受影響的收件者，供後續查詢引用。
B. A near-real-time (NRT) analytics rule in Microsoft Sentinel that runs the same three-table query every minute.
在 Microsoft Sentinel 建立近即時（NRT）分析規則，每分鐘執行同一支三張表的查詢。
C. A custom detection rule in Microsoft Defender XDR that is based on the hunting query and returns Timestamp, ReportId and the entity columns.
在 Microsoft Defender XDR 依這支搜捕查詢建立自訂偵測規則，並讓查詢輸出 Timestamp、ReportId 與實體欄位。
D. A search job that replays the query over the retained data once a week.
建立搜尋作業（search job），每週對保留的資料重跑一次這支查詢。
看正解與解析
正解：C

判準是「查詢用到哪些資料」：EmailEvents、UrlClickEvents、IdentityLogonEvents 全部都是 Defender XDR 進階搜捕的資料表，所以把已驗證的搜捕查詢直接升級成 XDR 自訂偵測規則最省事——查詢只要輸出 Timestamp、ReportId 與可對應的實體欄位，就能定期執行、產生警示，甚至自動採取回應動作。這正是 D3 搜捕回饋 D2 偵測的閉環：搜捕補到的盲區，要變成長期偵測。

  • A：監視清單是你自備的參考資料表，用來在查詢中比對名單，本身不會執行、也不會產生警示。它可以輔助查詢，但無法滿足「自動產生警示」的需求。
  • B：NRT 規則的查詢有明顯限制，並不適合這種需要關聯多張表的邏輯；而且這些是 XDR 資料表，要在 Sentinel 用還得先確保已串流進工作區，管理工作量反而更大。
  • D：搜尋作業是一次性、針對大範圍或長時間資料的檢索工具，結果寫成資料表供人檢視，不會持續執行也不會產生警示，無法滿足「從現在起自動偵測」。
