01 — 📌 本日導讀

本日導讀：接住「沒有現成連接器」的那一群

昨天我們把有服務對服務連接器的來源接上了；今天處理比較「野」的三類：講 syslog 的 Linux 與網路設備、講 CEF（Common Event Format）的資安設備、只會吐 JSON 的自研應用程式。三條路徑都繞著同一套機制轉——Azure Monitor Agent（AMA，Azure 監視代理程式）與資料收集規則（DCR）。接完之後還有一個大魔王：十種來源十種欄位格式，偵測規則難道要寫十份？這就輪到 ASIM（Advanced Security Information Model，進階安全性資訊模型）出場，把所有來源翻譯成同一套結構描述，讓一支查詢跨所有來源。今天是 kql_focus 單元，ASIM 查詢請務必動手跑。

學習目標（對應官方考綱 D1「管理安全性作業環境」條目）：
  • ☐ 規劃並設定 Syslog 與 Common Event Format（CEF）事件收集（plan and configure Syslog and CEF event collections），含轉送器（log forwarder）架構

  • ☐ 監視並最佳化資料擷取（monitor and optimize data ingestion）：健康檢查查詢與去重複策略

03 — 📡 Syslog 與 CEF 收集架構

AMA＋DCR：Syslog 與 CEF 的兩條進貨路線

先把地基講清楚。AMA 是目前唯一支援的收集代理程式——舊版 Log Analytics 代理程式（MMA）已於 2024 年 8 月退場，考題選項出現 MMA 一律是干擾項。AMA 自己不帶設定，行為完全由資料收集規則（DCR）定義：收哪些 facility、幾級以上的嚴重性、送到哪個工作區，甚至在擷取前先做 KQL 轉換過濾。地端或其他雲的機器要先用 Azure Arc 註冊，才能安裝 AMA 並關聯 DCR。

Syslog 與 CEF 是兩條不同的進貨路線，考試最愛比較它們：

面向Syslog（原始）CEF（Common Event Format）
格式／協定標準 syslog 訊息，內文自由格式架在 syslog 之上的結構化格式：標頭＋key=value 延伸欄位
目的資料表Syslog（內文整段塞在 SyslogMessage，用時自己剖析）CommonSecurityLog（DeviceVendor、SourceIP 等欄位已拆好）
代理程式AMA 裝在 Linux 機器本機，或集中收多台的轉送器上AMA 一律裝在 Linux 轉送器（rsyslog／syslog-ng）上，設備本身不裝
DCR 設定選 facility＋最低嚴重性等級同樣選 facility／等級，但走 CEF via AMA 連接器的 DCR
典型場景Linux 伺服器系統日誌、網路設備原生 syslog防火牆、Proxy、WAF 等資安設備（Palo Alto、Fortinet、Check Point…）

轉送器（log forwarder）架構是本節核心：防火牆這類 appliance 裝不了代理程式，所以你要架一台 Linux 機器當集散中心——上面跑 rsyslog 或 syslog-ng 監聽 514 連接埠（TCP/UDP），再裝 AMA。官方提供安裝指令碼，會自動把 syslog 精靈的轉送設定接到 AMA。所有設備把 CEF over syslog 指向轉送器，AMA 依 DCR 送上 CommonSecurityLog。量大時依 EPS（每秒事件數）規劃多台轉送器與負載平衡。

💡 去重複陷阱：同一台轉送器同時收原始 Syslog 與 CEF 時，若兩條 DCR 勾了重疊的 facility，同一則訊息會同時寫進 Syslog 與 CommonSecurityLog——資料重複、費用雙倍。正解是讓兩條 DCR 的 facility 互不重疊。
CommonSecurityLog
| where TimeGenerated > ago(1h)
| summarize Events = count(), LastSeen = max(TimeGenerated)
    by DeviceVendor, DeviceProduct, Computer
| order by LastSeen desc
接完 CEF 後的健康檢查：DeviceVendor／DeviceProduct 來自 CEF 標頭，能一眼看出哪些設備在回報；Computer 是轉送器主機名稱，多台轉送器時可分辨哪條管線斷了；LastSeen 若停在幾小時前，代表設備端或轉送器端出了問題。這條查詢也是考綱「監視資料擷取」的實作起手式。
🎯 考點聚焦

「選 Syslog 還是 CEF？AMA 裝哪裡？」判斷公式：題幹說設備支援 CEF 輸出（資安設備幾乎都支援）→ 走 CEF via AMA、查 CommonSecurityLog；只有原生 syslog → 走 Syslog 連接器、查 Syslog 表。架構題的鐵律：AMA 永遠裝在轉送器（或 Linux 主機本身），不裝在 appliance 上；地端轉送器要先 Azure Arc 註冊。陷阱選項常見三種：把 AMA 裝上防火牆（裝不了）、用 MMA（已退場）、叫防火牆直接呼叫 API（appliance 做不到）。

04 — 📥 自訂記錄擷取路徑

自研應用的日誌：Logs Ingestion API 全路徑

自研應用程式沒有 syslog 也沒有 CEF，只會透過 HTTPS 吐 JSON——這時走 Logs Ingestion API（記錄擷取 API），它取代了舊版 HTTP Data Collector API。完整路徑五個零件：

Logs Ingestion API 擷取管線：
  1. Entra 應用程式註冊：應用程式以 Entra ID 權杖驗證身分，並被授與對 DCR 送資料的角色。
  2. 資料收集端點（DCE）：API 的收件地址，應用程式把 JSON POST 到這裡。
  3. DCR：定義結構描述與 KQL 轉換（transformKql）——過濾雜訊、拆欄位、遮罩敏感資料，再指定目標表。
  4. 自訂資料表：表名結尾固定是 _CL（custom log），結構描述需事先建立。
  5. 驗證查詢：資料落地後用 KQL 抽查筆數與欄位。

兩個補充路徑：機器上的自訂文字／JSON 檔案（應用程式寫本機 log 檔）可由 AMA＋DCR 直接尾隨收集，不必自己呼叫 API；而無程式碼連接器框架（Codeless Connector Framework）則是給 SaaS 來源用的——用 JSON 宣告式定義 API 輪詢邏輯，由微軟代管的基礎結構去拉資料，完全不需要代理程式或程式碼，內容中樞裡許多合作夥伴連接器就是這樣做的。方向要分清楚：CCF 是 Sentinel 去「拉」SaaS 的 API；Logs Ingestion API 是你的應用程式主動「推」資料進來。

2026 新考點 自訂表現在可以選層級：SOC 常查的放分析（Analytics）層；量大、很少查、但合規要求可查的 verbose 記錄，改放 Sentinel data lake（資料湖層），擷取成本大幅降低，需要調查時再以 KQL 查詢或用 KQL job 撈回分析層。考題給「200 GB／日、偶爾調查、成本最小化」這種條件組合，就是在考層級選擇。

💡 一句話收斂：設備走轉送器、應用走 API、SaaS 走 CCF——三條路的終點都是「DCR 決定形狀、資料表決定家」。
05 — 🧬 ASIM 正規化

ASIM：讓一支查詢跨所有來源

資料都進來了，新問題浮現：同樣是「來源 IP」，Infoblox 叫一個名字、Azure Firewall 叫另一個、Windows DNS 又不一樣。沒有正規化，一條 DNS 偵測規則就得為每個來源各寫一份、來源一換就全部重寫。ASIM 的解法是在查詢時套一層標準結構描述（schema）：欄位統一叫 SrcIpAddr、DvcHostname、EventResult，偵測內容「一次寫、處處用」，微軟內建的許多分析規則與搜捕查詢也直接建在 ASIM 上，並向開源的 OCSF 標準靠攏。常考的 schema 家族：

Schema涵蓋事件unifying 剖析器（內建）
Network Session防火牆／NSG 等網路工作階段_Im_NetworkSession
DNSDNS 查詢與回應_Im_Dns
Authentication各來源的登入成功／失敗_Im_Authentication
Process Event處理程序建立／終止_Im_ProcessCreate 等
Web SessionProxy／WAF 的 HTTP 工作階段_Im_WebSession
File Event、Registry Event、Audit Event…檔案、登錄、稽核等其餘家族依 schema 命名

翻譯工作由剖析器（parser）完成，命名規則是考點：vim 開頭＝來源特定剖析器（如 vimDnsInfoblox，只翻一個產品）；im 開頭＝unifying 剖析器，把該 schema 所有來源的 vim 剖析器 union 起來——查一支等於查全部。底線開頭（_Im_／_ASim_）是內建版，隨工作區提供並由微軟自動更新；無底線版本（imDns、ASimDns）是你自己從 GitHub 部署到工作區的。

🎯 考點聚焦：im／vim／ASim 三兄弟怎麼選

im 與 vim 都是 filtering 剖析器：接受 starttime、endtime、srcipaddr、domain_has_any 等參數，把過濾條件推進剖析階段之前執行，效能最好。ASim 開頭是無參數（parameter-less）剖析器，先翻完全部資料才讓你 where，適合互動探索、不適合大範圍排程查詢。答題公式：跨來源→im；單一來源→vim；效能要求→帶參數的 filtering 剖析器。陷阱：題目要跨來源卻放 vimDnsInfoblox 當選項（只涵蓋一家）；或把「改用 ASim 無參數版」包裝成效能解法（其實更慢）。另外可用 ASimDisabledParsers 監視清單（Watchlist）把用不到的來源剖析器排除在 unifying 剖析器之外，進一步省時間。

_Im_Dns(starttime=ago(1d),
        domain_has_any=dynamic(["contoso-c2.net", "evil-cdn.io"]))
| summarize Queries = count(), Sources = make_set(EventProduct)
    by SrcIpAddr, DnsQuery
| order by Queries desc
unifying 剖析器實戰：_Im_Dns(...) 用「函數呼叫」的寫法把 starttime 與 domain_has_any（可疑網域清單）當參數傳入——過濾在剖析前發生，掃描量大減；make_set(EventProduct) 列出命中事件來自哪些產品（Infoblox？Azure Firewall？），親眼驗證「一支查詢、多個來源」；SrcIpAddr、DnsQuery 都是 DNS schema 的標準欄位，不管來源是誰，名字都一樣。
imAuthentication(starttime=ago(7d))
| where EventResult == "Failure"
| summarize Failures = count(), SrcIPs = dcount(SrcIpAddr),
    Products = make_set(EventProduct)
    by TargetUsername
| where Failures > 50 and SrcIPs > 10
| order by Failures desc
跨來源密碼噴灑（password spray）搜捕：imAuthentication 是工作區部署版的 unifying 剖析器（內建版叫 _Im_Authentication），一次涵蓋 Windows、Linux、Entra ID、VPN 等所有登入來源；EventResult == "Failure" 是正規化後的標準值，不必記各來源的失敗代碼；dcount(SrcIpAddr) > 10 抓「同一帳號被大量不同 IP 嘗試」的特徵。同一條邏輯若不用 ASIM，你得為每個登入來源各寫一版。

自訂剖析器的概念也要會：新來源沒有現成剖析器時，照 schema 規格寫一支 KQL 函數，把自家欄位對應成標準名稱（輸出欄位、值的正規化都要照規格），再掛進 unifying 剖析器——之後所有建立在 ASIM 上的偵測內容自動涵蓋你的來源，不必逐條改規則。

🧪 實戰情境：Fortinet 防火牆（CEF）＋自研訂單系統（API）完整接入

你是 SOC 工程師，今天要把地端 Fortinet 防火牆與自研訂單應用程式接進 Sentinel。走兩條路：

  1. 防火牆——CEF 路線：建一台 Linux VM 當轉送器 → 以 Azure Arc 註冊（地端機器）→ 安裝 AMA 與 rsyslog → 執行官方安裝指令碼接通 syslog 精靈與 AMA → 在 Sentinel 啟用 CEF via AMA 連接器、建 DCR 選 facility 與嚴重性 → 防火牆管理介面把 CEF 日誌輸出指向轉送器 514 埠 → 用第 03 節的 CommonSecurityLog 健康查詢驗證 → 因為 Fortinet 有現成 vim 剖析器，_Im_NetworkSession 立刻涵蓋這批資料，既有 ASIM 分析規則零修改直接生效。
  2. 訂單應用——API 路線：與開發團隊定義 JSON 欄位 → 建自訂表 OrderAudit_CL（依查詢頻率決定分析層或資料湖層）→ 建 DCE 與 DCR，轉換中先濾掉 debug 雜訊、遮罩卡號欄位 → Entra 註冊應用程式並授與 DCR 送資料的角色 → 開發者把日誌 POST 到 DCE → KQL 抽查落地資料 → 訂單系統的登入事件另寫一支自訂剖析器對應 Authentication schema，讓密碼噴灑搜捕查詢自動涵蓋它。
  3. 收尾檢查：確認轉送器上 Syslog 與 CEF 的 DCR facility 不重疊（防重複計費）；把兩條管線的健康查詢存成排程告警，資料斷流時主動通知，而不是等事件漏接才發現。

QUESTION 1 · D1-0046
You are a security operations analyst. Your organization must bring logs from on-premises Palo Alto firewall appliances that support Common Event Format (CEF) output into Microsoft Sentinel. Where must the Azure Monitor Agent (AMA) run, and how should the appliances deliver their events?
（你是安全性作業分析師。貴組織必須把地端 Palo Alto 防火牆設備（支援 Common Event Format，CEF 輸出）的記錄送進 Microsoft Sentinel。Azure Monitor Agent（AMA）應該安裝在哪裡？設備又該如何送出事件？）
A. Install AMA on each firewall appliance so that it sends events directly to the workspace.
在每一台防火牆設備上安裝 AMA，讓它直接把事件送到工作區。
B. Install AMA on a Linux log forwarder that runs rsyslog or syslog-ng, and configure the firewalls to send CEF over syslog to that forwarder.
在一台執行 rsyslog 或 syslog-ng 的 Linux 轉送器（log forwarder）上安裝 AMA，並設定防火牆以 CEF over syslog 把事件送到該轉送器。
C. Install the Log Analytics agent (MMA) on a Windows collector and forward the events from there.
在一台 Windows 收集器上安裝 Log Analytics 代理程式（MMA），再由它轉送事件。
D. Install no agent and use the Codeless Connector Framework to poll the firewall management API.
不安裝任何代理程式，改用無程式碼連接器框架（CCF）輪詢防火牆管理 API。
看正解與解析
正解：B

CEF 架構題的鐵律：防火牆這類 appliance 裝不了代理程式，因此要架一台 Linux 機器當集散中心，上面跑 rsyslog／syslog-ng 監聽 514 連接埠並安裝 AMA；設備把 CEF over syslog 指向轉送器，AMA 再依資料收集規則（DCR）把事件送進 CommonSecurityLog 資料表。地端的轉送器必須先用 Azure Arc 註冊，才能安裝 AMA 並關聯 DCR。量大時再依 EPS 規劃多台轉送器與負載平衡。

  • A：防火牆 appliance 是封閉的專用系統，無法安裝 AMA；這是 CEF 架構題最常見的干擾項。
  • C：Log Analytics 代理程式（MMA／OMS）已於 2024 年 8 月退場，目前唯一支援的收集代理程式是 AMA，選項出現 MMA 一律淘汰。
  • D：無程式碼連接器框架（CCF）是 Sentinel 主動去「拉」SaaS 服務 API 的宣告式連接器，地端防火牆並不提供這種可輪詢的雲端 API，收集路徑對不上。

QUESTION 2 · D1-0047
Your SOC uses one Linux log forwarder that collects raw Syslog messages from Linux servers and CEF messages from security appliances at the same time. One month later you notice that many identical messages are stored in both the Syslog table and the CommonSecurityLog table, and the ingestion charges for the workspace have almost doubled. What should you do?
（貴 SOC 使用同一台 Linux 轉送器，同時收集 Linux 伺服器的原始 Syslog 訊息與資安設備的 CEF 訊息。一個月後你發現許多相同訊息同時寫進 Syslog 與 CommonSecurityLog 兩張資料表，工作區的擷取費用幾乎翻倍。你應該怎麼做？）
A. Move the CommonSecurityLog table to the Auxiliary table plan.
把 CommonSecurityLog 資料表改為 Auxiliary（輔助）表方案。
B. Deploy a second log forwarder and load balance the incoming events between the two forwarders.
再部署一台轉送器，把進入的事件在兩台轉送器之間做負載平衡。
C. Replace the Azure Monitor Agent on the forwarder with the Log Analytics agent.
把轉送器上的 Azure Monitor Agent 換成 Log Analytics 代理程式。
D. Edit the two data collection rules so that the facilities they collect do not overlap.
修改這兩條資料收集規則（DCR），讓它們收集的 facility 互不重疊。
看正解與解析
正解：D

同一台轉送器同時服務 Syslog 與 CEF 兩條管線時，兩條 DCR 若勾到重疊的 facility，同一則訊息會被收兩次——一份進 Syslog、一份進 CommonSecurityLog，資料重複、費用雙倍。AMA 本身沒有設定檔，收什麼完全由 DCR 決定，所以正解是回頭把兩條 DCR 的 facility 範圍調成互斥（例如 CEF 專用的 facility 只留在 CEF 的 DCR 裡）。這也是考綱「監視並最佳化資料擷取」的典型情境。

  • A：改表方案只是把重複資料換成比較便宜的重複資料，根源的雙重收集沒有消失，而且 Auxiliary 不支援排程分析規則，會連帶讓 CEF 偵測失效。
  • B：多台轉送器是為了因應 EPS（每秒事件數）過高的效能瓶頸，對「同一則訊息被兩條 DCR 各收一次」的重複問題沒有幫助。
  • C：Log Analytics 代理程式（MMA）已退場，不能用來取代 AMA；而且代理程式換誰做，重疊的 facility 設定依然存在。

QUESTION 3 · D1-0048
You must build a single scheduled analytics rule that detects DNS queries to a list of command-and-control domains. The rule has to cover Infoblox, Azure Firewall, and Windows DNS sources at the same time, and the filtering must happen as early as possible so that the scheduled query stays efficient over a long lookback. Which parser should the rule call?
（你必須建立單一排程分析規則，偵測對一批命令與控制（C2）網域的 DNS 查詢。這條規則必須同時涵蓋 Infoblox、Azure Firewall 與 Windows DNS 三種來源，且過濾要盡可能提早發生，讓長時間回看的排程查詢維持效率。規則應該呼叫哪一種剖析器（parser）？）
A. _Im_Dns, called with the starttime and domain_has_any parameters
_Im_Dns，並傳入 starttime 與 domain_has_any 參數
B. vimDnsInfoblox, called with the same parameters
vimDnsInfoblox，並傳入相同的參數
C. ASimDns, followed by a where clause that filters on the domain
ASimDns，之後再用 where 子句過濾網域
D. One source-specific parser per product, combined with the union operator
每個產品各用一支來源特定剖析器，再以 union 運算子合併
看正解與解析
正解：A

ASIM 剖析器的命名規則就是答題公式：im 開頭是 unifying（統一）剖析器，會把該 schema 所有來源的 vim 剖析器 union 起來，一支查全部；vim 開頭是來源特定剖析器，只翻一個產品；底線開頭（_Im_）是隨工作區提供、由微軟自動更新的內建版。而 im／vim 都是 filtering 剖析器，接受 starttime、domain_has_any 等參數，把過濾條件推到剖析之前執行，效能最好。跨來源＋要效能＝帶參數的內建 unifying 剖析器 _Im_Dns。

  • B：vim 開頭是來源特定剖析器，vimDnsInfoblox 只涵蓋 Infoblox 一家，Azure Firewall 與 Windows DNS 的事件完全查不到，不符合跨來源要求。
  • C：ASim 開頭是無參數（parameter-less）剖析器，會先把全部資料正規化完才讓你 where 過濾，掃描量大、效能最差，適合互動探索而非大範圍排程查詢。
  • D：為每個來源各寫一支再 union，正是 ASIM 要消除的重工：來源一增加就得改規則，而 unifying 剖析器已經內建這個 union，且能享有 filtering 參數的效能優勢。

QUESTION 4 · D1-0049
A development team must send JSON logs from an in-house order application to Microsoft Sentinel over HTTPS. Debug entries have to be discarded and a credit card field has to be masked before the records are stored, and the data must land in a table that the SOC can query with KQL. Which ingestion path should you build?
（開發團隊必須把自研訂單應用程式的 JSON 記錄透過 HTTPS 送進 Microsoft Sentinel。資料存入前必須先濾掉 debug 雜訊並遮罩信用卡欄位，最後要落在 SOC 能用 KQL 查詢的資料表。你應該建立哪一條擷取路徑？）
A. A CEF via AMA connector with a Linux log forwarder that receives the application logs.
使用 CEF via AMA 連接器，並架一台 Linux 轉送器接收應用程式記錄。
B. A Codeless Connector Framework (CCF) connector that polls the application's REST API.
建立一個無程式碼連接器框架（CCF）連接器，輪詢應用程式的 REST API。
C. A data collection endpoint (DCE) plus a DCR whose KQL transformation filters and masks the data and writes to a custom _CL table, with the application posting to the Logs Ingestion API.
建立資料收集端點（DCE）與 DCR，在 DCR 的 KQL 轉換中過濾並遮罩資料後寫入自訂 _CL 資料表，由應用程式將資料 POST 到 Logs Ingestion API。
D. An application that posts the records to the HTTP Data Collector API and a custom table in the workspace.
由應用程式把記錄 POST 到 HTTP Data Collector API，並在工作區建立自訂資料表。
看正解與解析
正解：C

自研應用程式主動「推」JSON 進 Sentinel 的正規路徑是 Logs Ingestion API（記錄擷取 API），完整管線有五個零件：Microsoft Entra 應用程式註冊（取得權杖並被授與對 DCR 送資料的角色）、資料收集端點（DCE，收件地址）、DCR（定義結構描述與 transformKql 轉換，可過濾雜訊與遮罩敏感欄位）、結尾為 _CL 的自訂資料表，最後用 KQL 驗證落地。過濾與遮罩發生在擷取前，所以敏感資料根本不會入庫，同時也省下 debug 雜訊的擷取費。

  • A：CEF via AMA 是給支援 CEF over syslog 的資安設備用的路徑，自研應用程式吐的是 HTTPS JSON，格式與傳輸方式都對不上，也不會落在 CommonSecurityLog。
  • B：CCF 的方向相反：它是 Sentinel 去「拉」SaaS 服務 API 的宣告式連接器；本題是應用程式主動「推」資料進來，而且 CCF 也不提供擷取時遮罩欄位的轉換能力。
  • D：HTTP Data Collector API 是舊版路徑且已退場，由 Logs Ingestion API 取代；它也沒有 DCR 轉換，無法在入庫前過濾與遮罩。

QUESTION 5 · D1-0050
While reviewing hunting content in your workspace, you notice that some queries call _Im_ProcessCreate while others call ASimProcessCreate. A junior analyst asks what the leading underscore in the parser name means. What should you tell the analyst?
（你在檢閱工作區的搜捕內容時，發現有些查詢呼叫 _Im_ProcessCreate，有些則呼叫 ASimProcessCreate。一位資淺分析師問你剖析器名稱開頭的底線代表什麼。你應該怎麼回答？）
A. Parsers whose name starts with an underscore are source-specific parsers that cover a single product.
名稱以底線開頭的剖析器是來源特定剖析器，只涵蓋單一產品。
B. Parsers whose name starts with an underscore are deployed into the workspace from GitHub; the others are the built-in versions.
名稱以底線開頭的剖析器是從 GitHub 部署進工作區的版本，其他則是內建版本。
C. Parsers whose name starts with an underscore are unifying parsers; the others are always source-specific parsers.
名稱以底線開頭的剖析器是 unifying（統一）剖析器，其他一律是來源特定剖析器。
D. Parsers whose name starts with an underscore are the built-in versions that Microsoft maintains and updates; the others are versions that were deployed into the workspace.
名稱以底線開頭的剖析器是微軟維護並自動更新的內建版本，其他則是被部署到工作區的版本。
看正解與解析
正解：D

ASIM 剖析器名稱有兩個獨立的維度，別混在一起：（1）底線開頭（_Im_、_ASim_）＝隨工作區提供的內建版本，由微軟自動更新；無底線（imDns、ASimDns）＝你自己從 GitHub 部署到工作區的版本。（2）im＝unifying（跨來源）、vim＝來源特定、ASim＝無參數版。所以 _Im_ProcessCreate 與 ASimProcessCreate 的底線差異談的是「內建 vs 工作區部署」，不是涵蓋範圍。

  • A：來源特定剖析器的識別字是 vim 開頭（例如 vimDnsInfoblox），與底線無關；底線只表示這是內建版本。
  • B：方向剛好相反：底線開頭才是內建版，無底線版本才是從 GitHub 部署到工作區的。
  • C：unifying 與來源特定的分界是 im 與 vim 這兩個字首，而不是底線；沒有底線的 imDns 同樣是 unifying 剖析器。
