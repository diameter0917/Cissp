01 — 📌 本日導讀

本日導讀：雲端工作負載也會發警示

前三天我們把端點、郵件、身分三條線走完了，今天換第四個入口：Microsoft Defender for Cloud。這個產品有點分裂——一半在做「你的雲端組態有沒有漏洞」（CSPM，雲端安全態勢管理），一半在做「你的虛擬機、儲存體、資料庫現在有沒有被打」（CWPP，雲端工作負載保護）。SC-200 考的是 SOC 分析師，重心永遠落在後面那一半：警示怎麼查、怎麼回應、怎麼消誤報、怎麼流進 Defender XDR 與 Microsoft Sentinel。D2 占 35–40%，Defender for Cloud 幾乎必出情境題，而且很愛考「該用抑制規則、還是把方案關掉」這種取捨。今天把方案地圖、調查流程、回應工具與誤報治理一次收齊。

學習目標（對應官方考綱 D2「回應安全性事件」條目）：
  • ☐ 調查 Microsoft Defender for Cloud 的警示與事件（investigate alerts and incidents），讀懂警示詳細資料、嚴重性與 MITRE ATT&CK 對應
  • ☐ 說明各雲端工作負載保護方案（Servers／Storage／SQL／Containers／App Service／Key Vault／Resource Manager／APIs）保護什麼、產生什麼警示
  • ☐ 對雲端資源執行回應動作：JIT VM 存取、資源隔離停用、以工作流程自動化串接 Logic Apps
  • ☐ 以警示抑制規則（suppression rules）管理誤報，並與豁免（exemption）、停用方案區分
  • ☐ 將警示連線至 Defender XDR 與 Microsoft Sentinel，並理解多雲（AWS／GCP）連接器的角色
02 — 📺 影片伴讀

EP5 觀看重點指引

本單元對應官方影片 EP5「Mitigate threats using Microsoft Defender for Cloud」（字幕尚未到位，先提供觀看指引；字幕匯入後會回補含時間碼的伴讀整理）。這集橫跨態勢與工作負載兩半，請刻意把注意力調到「警示」那一側，帶著這五個問題看：

  • 總覽儀表板：畫面同時有 secure score（安全分數）與 security alerts（安全性警示），先分清哪一塊來自建議、哪一塊來自威脅偵測——這就是 CSPM 與 CWPP 的分界線。
  • 方案開關頁：環境設定裡逐一列出的 Defender 方案。注意方案是按訂用帳戶啟用、計價單位各不相同，以及 Servers 有 Plan 1／Plan 2 兩種。
  • 警示詳細資料頁：點進一則警示後看它顯示什麼——描述、嚴重性、受影響資源、MITRE 戰術、相關實體，以及「採取動作」（Take action）分頁。
  • Take action 的四段式：檢查資源內容 → 降低威脅（手動處置步驟）→ 防止未來攻擊（相關建議）→ 觸發自動回應／抑制類似警示。這四段幾乎就是考題的選項來源。
  • JIT 與自動化：示範即時（just-in-time）VM 存取請求時，注意「要哪個連接埠、來源 IP、多久」；示範工作流程自動化時，注意觸發條件與後端接的 Logic App。
03 — 🧭 兩個半邊

CSPM 與 CWPP：分析師該顧哪一半

Defender for Cloud 的功能可以乾淨地切成兩半，考試也是照這條線出題：

  • CSPM（雲端安全態勢管理）＝預防面。輸出物是建議（recommendations）與安全分數（secure score）、法規合規儀表板、攻擊路徑分析。基礎 CSPM 免費內建於所有 Azure 訂用帳戶；Defender CSPM 是付費強化版（攻擊路徑分析、資料感知態勢）。它回答的是「我哪裡沒關好」。
  • CWPP（雲端工作負載保護）＝偵測回應面。輸出物是安全性警示，由各個付費的 Defender 方案產生，回答的是「我現在正在被打」。
💡 一句話分界：建議與分數＝CSPM，警示＝CWPP。安全分數是加權百分比，衡量你完成了多少項建議、用來排修補優先順序——它不是威脅嚴重性指標，也不會因為冒出一則高嚴重性警示而下降。
🎯 考點聚焦

題幹關鍵字決定你走哪一半。看到「降低攻擊面」「提升法規合規狀態」「哪台 VM 沒開磁碟加密」→ 建議／安全分數／豁免，屬 CSPM。看到「偵測到」「疑似」「該如何回應」→ 警示，屬 CWPP，答案往方案、警示調查、抑制規則、JIT、工作流程自動化走。
常見陷阱：選項寫「提高安全分數以解決這則警示」——兩者是不同管線，改善建議不會讓已產生的警示消失。反過來，問「如何讓測試機別再出現在建議清單裡」，答案是豁免（exemption）。

04 — 🗺️ 方案地圖

Defender 方案 × 保護對象 × 典型警示

方案題的解法很機械：先認出題幹裡的資源類型，再對應到方案。下表是保護對象與最具代表性的警示樣態，考前掃一遍就夠：

Defender 方案保護對象典型警示樣態
Defender for Servers Plan 1Azure／AWS／GCP／Arc 上的 Windows 與 Linux 伺服器；核心是整合 MDE端點式威脅：惡意軟體、可疑 PowerShell 命令列、憑證竊取工具執行
Defender for Servers Plan 2Plan 1 全部，再加JIT VM 存取、檔案完整性監控（FIM）、無代理程式弱點與惡意軟體掃描Plan 1 全部＋主機層異常：SSH 暴力破解成功、加密貨幣挖礦、敏感檔案遭竄改
Defender for StorageBlob／檔案／佇列儲存體帳戶；含上傳時惡意軟體掃描與敏感資料威脅偵測上傳惡意檔案、自 Tor 離開節點存取、異常大量資料被下載外流
Defender for SQLAzure SQL Database、SQL 受控執行個體、機器上的 SQL Server疑似 SQL 資料隱碼（SQL injection）、暴力破解登入、異常資料存取模式
Defender for ContainersKubernetes 叢集（AKS／EKS／GKE／Arc）的控制平面稽核記錄＋節點執行階段與影像弱點掃描暴露在外的 Kubernetes 儀表板、建立特權容器、滲透測試工具、容器內挖礦
Defender for App ServiceApp Service 上的 Web 應用程式與其基礎結構Web 指紋探測、可疑 WordPress 佈景主題呼叫、託管釣魚內容、懸置 DNS 記錄
Defender for Key Vault金鑰、祕密與憑證的存取行為來自可疑 IP／Tor 的不尋常存取、異常的祕密列舉與大量查詢
Defender for Resource Manager控制平面：透過 ARM／入口網站／CLI 發出的管理作業雲端攻擊工具組（MicroBurst、PowerZure）、可疑的高風險執行作業
Defender for APIs發佈在 API Management 中的 APIAPI 流量異常暴增、可疑參數操弄、疑似敏感資料經由 API 外洩
💡 最容易混淆的一組：Resource Manager 管「誰對 Azure 下了什麼管理命令」（控制平面），Servers 管「VM 裡面發生什麼事」。題幹說「有人用可疑工具列舉整個訂用帳戶的資源」→ Resource Manager；說「VM 上跑起挖礦程序」→ Servers。
05 — 🔍 調查與回應

警示調查：從詳細資料到按下按鈕

一則警示點開後，你要在三十秒內抓到五件事：嚴重性（高／中／低／資訊，決定插隊順序）、受影響資源（哪個訂用帳戶下的哪台機器）、MITRE ATT&CK 戰術與技術對應（攻擊者走到哪一階段）、相關實體與證據（IP、帳戶、處理程序、檔案），以及相關警示的關聯——Defender for Cloud 會把時間相近、資源相關的多則警示關聯成一個安全性事件，這是判斷「單點誤報」還是「攻擊鏈」的關鍵。

接著是 Take action（採取動作）分頁，它把回應選項排成四段，也就是考題的選項池：

  • 檢查資源內容：跳到該資源的活動記錄，確認誰在什麼時間做了什麼。
  • 降低威脅：警示自帶的處置步驟，例如停止可疑處理程序、輪替外洩金鑰、停用或隔離受影響資源（收回網路安全性群組規則、停止 VM、撤銷儲存體金鑰、停用帳戶）。
  • 防止未來攻擊：對應的安全性建議，把設定面補起來（跨回 CSPM）。
  • 觸發自動回應／抑制類似警示：接 Logic App，或建抑制規則（下一節專講）。

JIT VM 存取（just-in-time VM access）是最常單獨出題的工具，屬 Defender for Servers Plan 2：平時以拒絕規則把 RDP（3389）、SSH（22）、WinRM 等管理埠完全關閉；要維運時由使用者請求，指定連接埠、來源 IP 範圍與時間長度，核准後暫時開一條規則，到期自動收回並留下稽核紀錄。它解的是「管理埠長期暴露在網際網路上被暴力破解」這個經典題型。

工作流程自動化（workflow automation）則把回應變成反射動作：以警示產生、建議變更或法規合規狀態改變為觸發條件，套用篩選（例如只針對高嚴重性），後端呼叫 Logic Apps 寄信、開工單、發 Teams 訊息或隔離資源。旁路是連續匯出（continuous export），把警示與建議持續送到 Log Analytics 工作區或事件中樞供第三方 SIEM 取用。

警示流入 Microsoft Sentinel 後會落在 SecurityAlert 資料表，用一段查詢就能看出「哪個方案在吵、吵哪個資源」：

SecurityAlert
| where TimeGenerated > ago(7d)
| where ProviderName has "Azure Security Center" or ProductName has "Defender for Cloud"
| extend Resource = tostring(parse_json(ExtendedProperties)["Resource"])
| summarize Alerts = count(), Last = max(TimeGenerated)
          by AlertName, AlertSeverity, Resource
| order by Alerts desc
逐行解說：SecurityAlert 是 Sentinel 統一收納各產品警示的資料表，Defender for Cloud 的警示連進來後就落在這裡；ProviderName／ProductName 兩欄都要留意，這產品改過名，歷史資料可能仍寫著舊名 Azure Security Center，考題問「為何篩不到警示」時欄位值不符是標準答案之一；ExtendedProperties 是 JSON 字串，要 parse_json 展開才取得到受影響資源；summarize … by AlertName, AlertSeverity 依名稱與嚴重性彙總，排最前面的那幾筆通常就是下一節要處理的誤報常客。
06 — 🔕 誤報治理

抑制規則 vs 豁免 vs 關閉方案

雲端最耗損分析師的不是攻擊，是每天早上那三十則一樣的誤報——弱點掃描器每晚掃全網段、備份服務固定下載大量 Blob。處理它們有三種手段，選錯就是扣分點：

手段作用對象與效果適用時機代價／風險
抑制規則（suppression rule）針對安全性警示。警示仍會產生，但依規則自動關閉／解除（dismiss），不進作用中佇列。可設範圍（管理群組／訂用帳戶）、條件（警示名稱、資源、實體、來源 IP）、到期日與啟用狀態，並可先模擬命中結果。已確認為誤報或已知良性活動的特定警示樣態，只想關那一種，其他偵測照常條件寫太寬會把真實攻擊一起吃掉；沒設到期日就永久生效，需定期複審
豁免（exemption）針對安全性建議／安全分數。把資源標記為已豁免或已由第三方緩解，不再影響分數與合規狀態，屬 Defender CSPM 能力。設定面的例外：測試資源、已有補償控制、業務上無法套用該建議與偵測無關，不會讓任何警示消失；豁免過多會讓分數失真
關閉方案把某個 Defender 方案在訂用帳戶或資源層級關掉，該範圍完全失去威脅偵測，不再產生任何警示。該資源類型確定不需保護、或成本取捨——極少是考題正解為了一種誤報關掉整片偵測，是典型「殺雞用牛刀」陷阱選項
🎯 考點聚焦

「弱點掃描器每晚觸發大量警示」的最佳解。正解是建立抑制規則，範圍限定該訂用帳戶、條件鎖定該警示名稱＋掃描器的來源 IP，並設到期日以便重新評估。干擾項的死法要背：關閉 Defender for Servers＝整個訂用帳戶失去偵測；把掃描器從 MDE 移除＝端點失去保護且與此警示無關；建立豁免＝那是給建議與分數用的，對警示無效。
高頻變體問「抑制規則建好了，昨天那些舊警示怎麼辦」——抑制規則只對之後產生的警示生效，既有警示要手動關閉；建立時的模擬只是預覽命中範圍，不會回頭清掉它們。

07 — 🧪 整合與實戰

警示流向 XDR 與 Sentinel：一次完整回應

警示不會只停在 Defender for Cloud 自己的入口網站，考試很愛問「分析師該在哪裡看到它、怎麼接進來」：

  • 流向 Defender XDR：啟用整合後，警示會進入 Defender 入口網站的事件佇列，與端點、身分、郵件、雲端應用的警示關聯成同一個事件——VM 上的挖礦警示因此能和該伺服器管理員帳戶的可疑登入自動串成完整攻擊鏈。
  • 流向 Microsoft Sentinel：以資料連接器把警示送進工作區的 SecurityAlert 資料表。現在建議走租用戶層級的 Defender XDR 連接器一次帶入；訂用帳戶層級的 Defender for Cloud 連接器是較舊路徑，可雙向同步狀態。進了 Sentinel 就由分析規則與劇本（Playbook）接手。
  • 多雲：在環境設定中以 AWS／GCP 連接器接入 AWS 帳戶或 GCP 專案（AWS 端部署 CloudFormation 範本、GCP 端跑上架指令碼），延伸 CSPM 與部分方案；地端伺服器以 Azure Arc 納管後套用 Defender for Servers。
🧪 實戰情境：對外的 Linux VM 遭入侵並外傳資料

週一上午出現三則相關警示：某台對外的 Linux VM「SSH 暴力破解嘗試成功」（中）、同一台機器「偵測到加密貨幣挖礦活動」（高），以及該訂用帳戶的儲存體帳戶「異常大量資料被擷取」（高）。你是值班分析師——

  1. 先看關聯，不要單看一則。三則警示已關聯成同一個安全性事件，時間軸顯示「暴力破解成功 → 挖礦程序 → 資料外流」，MITRE 戰術橫跨初始存取、影響與外流，判定為真實入侵。
  2. 確認來源與範圍。從警示詳細資料取出攻擊者 IP、成功登入的帳戶與挖礦處理程序名稱；到 XDR 事件頁確認同一 IP 有沒有打過其他資源。
  3. 遏制。以網路安全性群組規則切斷該 VM 對外連線（要保留記憶體證據就別急著停機）；輪替儲存體存取金鑰與 SAS 權杖；停用遭破解的帳戶。伺服器若已上線 MDE，可直接裝置隔離並用 Live Response 取證。
  4. 清除。移除挖礦程式與持續性機制（cron 排程、systemd 服務、被植入的 SSH 授權金鑰），必要時由已知良好的映像重建 VM。
  5. 防止再發生。對這台與同群組的 VM 啟用 JIT VM 存取，讓 SSH 埠平時關閉、要用才開；處理 Take action 列出的相關建議。
  6. 自動化。建立工作流程自動化：高嚴重性警示一產生就呼叫 Logic App 開工單並通知值班頻道；確認警示已流入 Sentinel，把分類與結案理由記錄完整。
🎯 考點聚焦

「要讓 Defender for Cloud 警示與端點、身分警示自動關聯成單一事件，該做什麼？」答案是啟用 Defender for Cloud 與 Defender XDR 的整合，在統一事件佇列中處理；不是「在 Sentinel 自己寫分析規則關聯」，也不是「用連續匯出送到事件中樞」。
題幹若強調要與防火牆、AWS CloudTrail 等第三方來源的記錄一起關聯分析與長期保留，才輪到 Microsoft Sentinel——用資料連接器帶入 SecurityAlert，再以分析規則與劇本自動化。連續匯出只在點名「送到第三方 SIEM 或事件中樞」時才是正解。

08 — 🧩 考綱補洞

影片之外，考綱還要你會這些

  • 範例警示：可產生範例警示（sample alerts）測試自動化與連接器是否通。考題問「如何在不製造真實攻擊的前提下驗證工作流程自動化」→ 產生範例警示。
  • 警示狀態：分為作用中（Active）／已關閉（Dismissed）／已解決（Resolved）；與 Sentinel 雙向同步時，一端關閉會反映到另一端。
  • 權限模型：走 Azure RBAC——Security Reader 只能看警示與建議，Security Admin 才能關閉警示、改方案設定與建立抑制規則；核准 JIT 請求另需該 VM 的特定權限。「看得到警示 ≠ 動得了資源」在雲端同樣成立。
  • 無代理程式掃描與 FIM：Plan 2 的無代理程式（agentless）掃描直接讀磁碟快照做弱點與惡意軟體偵測，不必在 VM 內安裝任何東西；FIM 則負責「重要系統檔案或登錄被改」這類警示。題幹說「不能在生產 VM 裝代理程式」→ 無代理程式掃描。
  • Security Copilot 與 Defender for Cloud 2026 新考點：以自然語言摘要一則雲端警示的來龍去脈、產生修復腳本，並在 Defender XDR 事件頁提供跨雲端與端點的引導式回應建議，加速 Tier 1 分診。

QUESTION 1 · D2-0021
You are a security operations analyst for an Azure estate that has every Microsoft Defender for Cloud plan enabled. An alert reports that a known cloud attack toolkit was used through the Azure Resource Manager control plane to enumerate all resources, role assignments and key vaults in a production subscription. No process was executed inside any virtual machine. Which Defender plan produced this alert?
（你是安全性作業分析師，負責的 Azure 環境已啟用所有 Microsoft Defender for Cloud 方案。一則警示指出，有人透過 Azure Resource Manager 控制平面使用已知的雲端攻擊工具組，列舉某個生產訂用帳戶下的所有資源、角色指派與金鑰保存庫，過程中沒有任何處理程序在虛擬機內執行。這則警示是由哪一個 Defender 方案產生的？）
A. Microsoft Defender for Servers Plan 2
Microsoft Defender for Servers Plan 2
B. Microsoft Defender for Resource Manager
Microsoft Defender for Resource Manager
C. Microsoft Defender for Key Vault
Microsoft Defender for Key Vault
D. Microsoft Defender for Containers
Microsoft Defender for Containers
看正解與解析
正解：B

Defender for Resource Manager 保護的是 Azure 的控制平面——透過 ARM、入口網站、Azure CLI 或 PowerShell 發出的管理作業，典型警示正是 MicroBurst、PowerZure 這類雲端攻擊工具組的列舉與偵察行為。題幹的兩個關鍵字已經把答案鎖死：「透過 Azure Resource Manager 控制平面」與「沒有任何處理程序在虛擬機內執行」，代表動作發生在管理層而不是工作負載內部。判斷句型記起來：問「誰對訂用帳戶下了什麼管理命令」走 Resource Manager；問「VM 裡面發生什麼事」才走 Servers。

  • A：Defender for Servers（含 Plan 2）看的是 VM 作業系統內部的行為：惡意軟體、可疑 PowerShell 命令列、SSH 暴力破解成功、挖礦處理程序。題幹明說沒有任何處理程序在 VM 內執行，資料平面沒有訊號，這個方案不會產生本則警示。
  • C：Defender for Key Vault 偵測的是金鑰保存庫本身的存取行為，例如來自可疑 IP 或 Tor 節點的異常存取、大量祕密列舉與查詢。攻擊者在本題列舉的是訂用帳戶的資源清單（金鑰保存庫只是清單上的一個資源物件），並沒有去讀取保存庫內的祕密。
  • D：Defender for Containers 監控 Kubernetes 控制平面稽核記錄與節點執行階段，典型警示是暴露在外的儀表板、建立特權容器、容器內挖礦；題幹完全沒有叢集或容器活動。

QUESTION 2 · D2-0022
Every night an authorized vulnerability scanner sweeps one Azure subscription, and each morning Microsoft Defender for Cloud fills your queue with about 30 identical alerts that the team has already confirmed to be benign. Threat detection must remain fully active for every other alert type in that subscription, and you want the least administrative effort. What should you do?
（每天晚上，一台獲授權的弱點掃描器會掃過某個 Azure 訂用帳戶；隔天早上 Microsoft Defender for Cloud 就會在佇列裡塞進大約 30 則一模一樣的警示，而團隊已經確認它們全是良性活動。該訂用帳戶其他所有警示類型的偵測必須維持完整，而你希望管理負擔最低。你應該怎麼做？）
A. Turn off the Defender for Servers plan on that subscription
在該訂用帳戶關閉 Defender for Servers 方案
B. Create an exemption for the scanner virtual machine
為掃描器虛擬機建立豁免（exemption）
C. Offboard the scanner from Microsoft Defender for Endpoint
把掃描器從 Microsoft Defender for Endpoint 離線移除
D. Create an alert suppression rule scoped to that subscription that matches the alert name and the source IP address of the scanner, and set an expiration date
建立警示抑制規則，範圍限定該訂用帳戶、條件比對該警示名稱與掃描器的來源 IP 位址，並設定到期日
看正解與解析
正解：D

已確認的誤報要用抑制規則（suppression rule）治理：範圍限定在該訂用帳戶、條件鎖定警示名稱加上掃描器的來源 IP，命中的警示雖然仍會產生但會被自動關閉／解除，不進作用中佇列，其他偵測完全不受影響。加上到期日則強迫團隊定期複審，避免規則永久生效而遮住真正的攻擊。以「管理負擔最低」來看也是它：一張表單幾分鐘設定完，不必變更方案、也不必動端點上線狀態。

  • A：關閉 Defender for Servers 會讓整個訂用帳戶失去工作負載威脅偵測，所有伺服器警示都不再產生。為了一種誤報關掉整片偵測是典型的「殺雞用牛刀」陷阱選項，也直接違反題幹要求其他警示類型偵測必須維持完整。
  • B：豁免（exemption）作用在安全性建議與安全分數上，把資源標記為已豁免或已由第三方緩解，屬於 CSPM 設定面的工具。它對已經產生的安全性警示完全無效——建議與警示是兩條不同的管線。
  • C：把掃描器從 Defender for Endpoint 移除只會讓那台主機失去端點保護，而這些警示是 Defender for Cloud 的方案針對被掃描的資源產生的，改變掃描器自己的 MDE 上線狀態並不會讓警示停止。

QUESTION 3 · D2-0023
Your organization runs 40 Azure virtual machines whose RDP and SSH management ports are reachable from the internet, and Microsoft Defender for Cloud keeps raising successful brute-force alerts against them. Administrators still need occasional remote access, but the ports must stay closed the rest of the time and be opened only for a limited period after a request is approved. Which Microsoft Defender for Cloud capability should you enable?
（你的組織有 40 台 Azure 虛擬機，RDP 與 SSH 管理埠可從網際網路存取，Microsoft Defender for Cloud 因此不斷產生暴力破解成功的警示。管理員仍需要偶爾遠端連線，但這些連接埠平時必須保持關閉，只有在請求獲核准後才限時開啟。你應該啟用哪一項 Microsoft Defender for Cloud 能力？）
A. Just-in-time (JIT) VM access
即時（JIT）VM 存取
B. File integrity monitoring (FIM)
檔案完整性監控（FIM）
C. Agentless vulnerability scanning
無代理程式弱點掃描
D. Workflow automation with Logic Apps
以 Logic Apps 執行的工作流程自動化
看正解與解析
正解：A

JIT VM 存取（just-in-time VM access）就是為「管理埠長期暴露在網際網路」設計的：平時以拒絕規則把 RDP（3389）、SSH（22）、WinRM 等管理埠完全關閉；要維運時由使用者提出請求，指定連接埠、來源 IP 範圍與時間長度，核准後才暫時開一條允許規則，到期自動收回並留下稽核紀錄。它屬於 Defender for Servers Plan 2 的能力，題幹「平時關閉、核准後限時開啟」正是它的專屬關鍵字。

  • B：檔案完整性監控（FIM）偵測的是重要系統檔案、登錄或設定檔遭到竄改，雖然同屬 Defender for Servers Plan 2，但它完全不會變更網路安全性群組規則，對管理埠暴露這件事沒有任何作用。
  • C：無代理程式弱點掃描直接讀取磁碟快照做弱點與惡意軟體偵測，解的是「不能在生產 VM 內安裝代理程式」的問題。它會告訴你機器上有什麼弱點，但不會關閉或開啟任何連接埠。
  • D：工作流程自動化以警示產生或建議／合規狀態變更為觸發條件去呼叫 Logic Apps 做通知、開工單或隔離資源，屬於事後回應機制；它不是預防性的存取控制，也取代不了 JIT 的請求、核准與到期自動收回流程。

QUESTION 4 · D2-0024
You have just built a workflow automation in Microsoft Defender for Cloud that calls a Logic App to open a ticket whenever a high-severity alert appears. Before the on-call team relies on it, you must prove end to end that the trigger, the severity filter and the Logic App all fire, without waiting for a real attack and without running any offensive tooling in production. What should you do FIRST?
（你剛在 Microsoft Defender for Cloud 建立了一條工作流程自動化：只要出現高嚴重性警示就呼叫 Logic App 開立工單。在值班團隊正式仰賴它之前，你必須端對端證明觸發條件、嚴重性篩選與 Logic App 都會確實運作，而且不能等真實攻擊發生，也不能在生產環境執行任何攻擊工具。你應該先做什麼？）
A. Enable continuous export of security alerts to an event hub
啟用連續匯出，把安全性警示送到事件中樞
B. Preview the matches of a suppression rule by running its simulation
執行抑制規則的模擬，預覽它會命中哪些警示
C. Generate sample security alerts for the subscription
為該訂用帳戶產生範例安全性警示
D. Run the Logic App manually from the Logic Apps designer
從 Logic Apps 設計工具手動執行該 Logic App
看正解與解析
正解：C

Defender for Cloud 內建「產生範例警示」（sample alerts）功能：在不製造真實攻擊、也不執行攻擊工具的前提下，把一批涵蓋各方案的範例警示真的送進警示佇列，因此你的工作流程自動化會依照正式路徑被觸發，嚴重性篩選與後端 Logic App 也會整串跑一次。這正是官方用來驗證自動化與連接器是否接通的做法，所以是第一步。

  • A：連續匯出是把警示與建議持續送到 Log Analytics 工作區或事件中樞供第三方 SIEM 取用，是與工作流程自動化並行的另一條旁路管線。它不會觸發你剛建立的自動化，也產生不出任何用來測試的警示。
  • B：抑制規則的模擬只是預覽「這條規則會命中哪些既有警示」的唯讀功能，屬於降噪工具的一部分，與自動化的觸發毫無關係，方向甚至相反——它的用途是讓警示不要進佇列。
  • D：從 Logic Apps 設計工具手動執行只證明 Logic App 自己的動作跑得動，完全跳過 Defender for Cloud 這一端的觸發條件與嚴重性篩選。題幹要的是端對端驗證，而手動執行恰好驗不到最容易設錯的那一段。

QUESTION 5 · D2-0025
Yesterday you created a suppression rule in Microsoft Defender for Cloud for a noisy alert type and confirmed with the rule simulation that the condition matches. This morning the 28 alerts of that type that were raised before the rule existed are still in the Active state, while newly raised alerts of the same type are being dismissed automatically. Your manager asks why the older alerts are still there and what you will do about them. Which statement is correct?
（你昨天在 Microsoft Defender for Cloud 為一種吵雜的警示類型建立了抑制規則，並用規則模擬確認條件確實會命中。今天早上，規則建立之前產生的那 28 則同類警示仍停留在「作用中」狀態，而規則建立之後新產生的同類警示則已被自動解除。主管問你舊警示為何還在、你打算怎麼處理。下列哪一項敘述正確？）
A. The rule was created with the Security Reader role, which cannot change alert state; recreate it as Security Admin
該規則是以 Security Reader 角色建立的，無法變更警示狀態；請改用 Security Admin 重新建立
B. The simulation only previews matches; switch the rule to enforce mode so that it purges the existing alerts
模擬只會預覽命中結果；把規則切換成強制執行模式，它就會清掉既有的警示
C. Suppression becomes retroactive only after the Defender plan is re-enabled; turn the plan off and on again for the subscription
抑制要等 Defender 方案重新啟用後才會回溯生效；把該訂用帳戶的方案關閉再開啟
D. Suppression rules act only on alerts generated after the rule is created; dismiss the 28 existing alerts manually
抑制規則只對規則建立之後產生的警示生效；那 28 則既有警示必須手動關閉
看正解與解析
正解：D

抑制規則只對「規則建立之後才產生」的警示生效，不會回頭處理既有警示；建立時的模擬也只是預覽命中範圍，不會清掉任何東西。因此昨天以前那 28 則仍留在作用中佇列，得由分析師手動關閉（dismiss）。這是高頻的因果題型：規則「正在生效」（新警示被自動解除）與「舊警示還在」可以同時成立，兩者並不矛盾。

  • A：權限不足會讓你根本建不出這條規則——建立與管理抑制規則需要 Security Admin，Security Reader 只能檢視警示與建議。題幹已說新產生的警示正被自動解除，代表規則存在且正常運作，因此不是權限造成的。
  • B：模擬是建立規則時預覽「若套用此條件會命中哪些警示」的唯讀功能，抑制規則並沒有所謂的強制執行模式可切換，模擬本身也不會變更任何警示的狀態。
  • C：停用再啟用 Defender 方案只會讓該範圍在停用期間完全失去威脅偵測，抑制規則並不會因此回溯套用；為了清 28 則舊警示而關掉整個方案更是本末倒置。
