01 — 📌 本日導讀

資料連接器 I：先把水管接好，順便裝上濾水器

昨天把工作區（workspace）這個「蓄水池」設計好了，今天開始接水管：資料連接器（data connector）是 Microsoft Sentinel 一切偵測的前提——沒有資料，再漂亮的分析規則也是空轉。連接器內容很多，我們拆成兩天：今天講「微軟自家」的部分——Content Hub 解決方案怎麼一鍵打包安裝、第一方連接器（Defender XDR、Entra ID、Office 365、Azure Activity）各自帶進哪些資料表與授權前提；再深入資料收集規則（Data Collection Rule，DCR）的三段式架構，以及考試新寵擷取時轉換（ingestion-time transformation）——在資料入庫前過濾雜訊、遮罩敏感欄位、瘦身省成本。明天才輪到 Syslog／CEF／自訂記錄與 ASIM。

學習目標（對應官方考綱 D1「管理安全性作業環境」）：
  • ☐ 能用 Content Hub 找到並安裝解決方案，說出一個解決方案打包了哪幾類內容（對應考綱 identify data sources to be ingested for Microsoft Sentinel 與內容中樞相關條目）
  • ☐ 背出四大第一方連接器各自帶進的資料表與授權需求，並判斷哪些資料類型免擷取費（對應考綱 configure and use Microsoft connectors for Azure resources, including Azure Policy and diagnostic settings）
  • ☐ 畫出 DCR「資料來源 → 轉換 → 目的地」結構，說明 DCR 與 AMA 代理程式的關聯方式（對應考綱 plan and configure collection of Windows Security events by using data collection rules）
  • ☐ 分辨標準 DCR 與工作區轉換 DCR（workspace transformation DCR）各管哪條資料路徑
  • ☐ 會寫一段 transformKql：過濾、遮罩、砍欄位，並說出成本上的效果與 50% 過濾費用細則
  • ☐ 知道連接器健康狀態去哪裡看、斷線時的排查順序

03 — 🛒 Content Hub 與解決方案

內容中樞：不是逐個接連接器，是逐個裝解決方案

舊時代的 Sentinel 是「連接器清單」思維：找到連接器、接上、再自己去找規則跟儀表板。現在的入口是內容中樞（Content Hub）：所有現成內容（out-of-the-box content）的單一商店，以解決方案（solution）為單位打包。一個解決方案通常包含：

  • 資料連接器——把該產品的記錄接進工作區；
  • 分析規則（analytics rule）範本——針對該資料源的現成偵測；
  • 活頁簿（Workbook）——視覺化儀表板；
  • 搜捕查詢、劇本（Playbook）、剖析器（parser）、監視清單（Watchlist）——視解決方案而定。

來源分三類：Microsoft 官方、合作夥伴（provider 是廠商，支援也找廠商）、社群。除了成包的解決方案，內容中樞也有「獨立內容（standalone content）」可單獨安裝。安裝後的內容集中在「管理（Manage）」檢視裡做版本更新——解決方案更新時，內容中樞會標示有新版可裝。

三個容易混淆的動詞：「安裝」解決方案＝把內容放進工作區；「設定／連線」連接器＝真正開始擷取資料；「啟用」分析規則範本＝從範本建立作用中的規則。考題若說「已安裝解決方案但沒有資料進來」，答案方向就是：連接器還沒設定連線。
04 — 🔌 第一方連接器巡禮

四大金剛：帶什麼表、要什麼權限、花不花錢

第一方（服務對服務，service-to-service）連接器不裝代理程式，雲端對雲端直接串——設定門檻低，但每個都有自己的授權與權限前提。下表是本單元最重要的背誦資產：

連接器帶進哪些資料表授權／權限需求與成本重點
Microsoft Defender XDR事件與警示（SecurityIncident、SecurityAlert）；可加選進階搜捕原始資料表：DeviceEvents、DeviceProcessEvents、EmailEvents、IdentityLogonEvents、CloudAppEvents⋯⋯設定需租用戶層級高權限角色（如 Security Administrator 等級）；事件與警示免擷取費，原始事件表要收費——量大，接之前先估成本
Microsoft Entra IDSigninLogs、AuditLogs；可加選非互動式登入、服務主體登入、佈建記錄、RiskyUsers 等匯出登入記錄需 Entra ID P1／P2 授權；設定走診斷設定，需足夠的租用戶安全性管理角色；擷取要收費（登入記錄量可觀）
Office 365OfficeActivity（Exchange、SharePoint／OneDrive、Teams 的管理活動記錄）需租用戶的全域／安全性管理層級權限授權同意；免擷取費——CP 值極高，必接
Azure ActivityAzureActivity（訂用帳戶控制平面稽核：誰建了 VM、誰改了 NSG、誰刪了資源）新版連接器透過 Azure Policy 把診斷設定套到各訂用帳戶——需要在目標範圍指派原則的權限（Owner 等級）；免擷取費
Microsoft Defender for CloudSecurityAlert（雲端工作負載保護警示）需訂用帳戶層級權限；警示免擷取費
🎯 考點聚焦
Defender XDR 連接器的兩層資料是高頻陷阱：題目問「把 XDR 事件同步進 Sentinel 做統一分診」→ 接連接器即可（事件／警示，免費、雙向同步狀態）；題目問「要在工作區裡對 DeviceProcessEvents 寫自訂分析規則、或保留超過 30 天做長期搜捕」→ 必須額外勾選進階搜捕事件收集，而且這部分要付擷取費。另一個常考組合：「哪些資料免費接」——記口訣「活動、辦公、警示免費；登入、原始事件收費」（Azure Activity、Office 365、各 Defender 警示免費；Entra 登入記錄、XDR 原始事件表計費）。題目要你「以最低成本取得基本可見度」時，先把免費三寶全接。
05 — 🧱 DCR 深入

資料收集規則：資料來源 → 轉換 → 目的地

代理程式類收集（下表中的 Windows 安全性事件、明天的 Syslog／CEF）背後都是同一個機器：資料收集規則（DCR）。Azure Monitor Agent（AMA）本身「無腦」——它不帶本機設定檔，收什麼、怎麼處理、送去哪，全部由雲端的 DCR 定義。一條 DCR 是三段式結構：

區段回答的問題範例
① 資料來源（data sources）收什麼？Windows 事件記錄（事件集：全部／通用／最小／自訂 XPath）、效能計數器、Syslog facility 與層級
② 轉換（transformKql，可選）入庫前怎麼加工？過濾雜訊事件、遮罩敏感欄位、砍掉肥大欄位（§06 詳講）
③ 目的地（destinations)送去哪？一個或多個 Log Analytics 工作區

DCR 與機器的關係是「關聯（association）」：一條 DCR 可以關聯到成百上千台機器；一台機器也可以同時關聯多條 DCR（例如一條收安全性事件、一條收效能資料）。大規模環境用 Azure Policy 自動幫新機器裝 AMA 並建立關聯。Sentinel 的「透過 AMA 的 Windows 安全性事件」連接器，本質就是幫你建 DCR：選「通用（Common）」事件集是多數 SOC 的起點——比「全部」省量，又比「最小」保留了足夠的調查脈絡；進階需求用自訂 XPath 精準點名事件。

還有一種特殊 DCR 要單獨記：工作區轉換 DCR（workspace transformation DCR）。它每個工作區只有一條，管的是「不走標準 DCR 的資料路徑」——也就是第一方服務對服務連接器送進來的表（SigninLogs、OfficeActivity⋯⋯）。你在裡面按「表」定義轉換，資料入庫前一樣會先過這道關。

🎯 考點聚焦
「該用哪種 DCR」二選一公式：先問一句「這筆資料是代理程式收的，還是服務對服務連接器送的？」——AMA 收的（Windows 事件、Syslog、CEF）→ 轉換寫在該資料流的標準 DCR 裡；連接器直送的（SigninLogs、OfficeActivity、AzureActivity 等）→ 只能寫在工作區轉換 DCR。陷阱選項常把兩者對調，或塞入「ASIM 剖析器」——記住 ASIM 是查詢時正規化，資料原封不動入庫，既不省擷取費也遮罩不了儲存下來的欄位。
06 — ✂️ 擷取時轉換實戰

transformKql：過濾、遮罩、瘦身一次做完

擷取時轉換（ingestion-time transformation）是一段寫在 DCR 裡的 KQL，對即將入庫的資料流逐筆執行。輸入固定叫 source，只能用 KQL 的子集（where、extend、project 系列、parse 等；不能 join 其他資料表）。一段典型的「三合一」轉換長這樣：

source
| where EventID !in (5156, 5158)
| extend IpAddress = iif(EventID == 4624,
    replace_regex(IpAddress, @"\.\d+$", ".***"), IpAddress)
| project-away EventData

第 1 行：source 是固定關鍵字，代表流進來的原始資料流（這裡是 SecurityEvent）。第 2 行「過濾雜訊」：5156／5158 是 Windows 篩選平台的連線允許事件，量大而偵測價值低，入庫前直接丟——這行就是省錢的主力。第 3 行「遮罩敏感欄位」：對登入成功事件（4624）把來源 IP 最後一段換成 ***，滿足隱私要求，而且遮罩發生在入庫前，工作區裡從頭到尾不存在完整 IP。第 4 行「瘦身」：project-away 砍掉肥大的原始 XML 欄位，每筆少存幾 KB，長期就是真金白銀。

💰 50% 細則：轉換本身不另外收費，但若你的過濾丟掉了超過 50% 的進料量，超過 50% 的那部分會被收取資料處理費。啟示：轉換適合「修剪」，若要丟掉九成的量，正確做法是回到來源端別收（調整 DCR 資料來源、事件集或來源設備的轉送策略）。
🎯 考點聚焦
省成本題的選項鑑別。題幹說「某表擷取成本過高，想在資料進工作區之前減量」→ 正解是 DCR 的 transformKql（擷取時轉換）。干擾項逐一擊破：縮短保留期——只省儲存、不省擷取費，資料照樣全額入庫計費；summary rules 2026 新考點——把已入庫（或進 data lake）的資料「事後」彙總成小表，適合長期趨勢與大量 Verbose 記錄的彙整，但不改變原始擷取；基本記錄（basic logs）／data lake 層 2026 新考點——是「換便宜方案」（低價擷取、查詢受限），不是「減量」，適合量大低查詢頻率的表；ASIM——查詢時正規化，與成本無關。四個都是真功能，考的就是你知不知道它們各自作用在資料生命週期的哪一段。
07 — 🩺 連接器健康與疑難排解

水管會漏：健康狀態監控與排查順序

連接器接上只是開始——真實 SOC 最怕「資料默默斷了三天沒人發現」，偵測直接開天窗。監控有三層：

  • 連接器頁面速查：資料連接器頁會顯示連線狀態與最近收到記錄的時間，適合手動抽查。
  • 健康監控功能：在 Sentinel 設定中啟用稽核與健康監控後，連接器與其他資源的健康事件會寫進 SentinelHealth 資料表——這才是可以自動化的來源：對它寫分析規則，連接器一失敗就開事件通知值班。
  • 資料收集健康監控活頁簿：現成活頁簿呈現各表擷取量趨勢與異常（斷流、暴量），適合每週巡檢。

「沒資料進來」排查順序：① 授權——Entra 登入記錄沒 P1／P2 就是不會來；② 權限——設定連接器的人當時角色夠不夠、同意有沒有給；③ 代理程式路徑——AMA 有沒有心跳（Heartbeat 表）、DCR 關聯還在不在；④ 轉換——transformKql 是不是把資料全過濾掉了（寫錯 where 條件是經典事故）；⑤ 擷取延遲——尖峰時段有分鐘級延遲屬正常，先別當故障報修。

🛡️ 實戰情境：新 SOC 第一週，五種資料來源的接入優先序

你是新成立 SOC 的 Sentinel 工程師，第一週要讓偵測「從零到能用」，預算有限。接入排序與理由：

  1. Day 1：Microsoft Defender XDR 連接器（事件＋警示）——免費、十分鐘見效，微軟生態的偵測成果直接進佇列；原始事件表先不要勾，等估完量再說。
  2. Day 1：Office 365 與 Azure Activity——兩個免費連接器順手接上：郵件協作稽核與訂用帳戶控制平面稽核，是日後幾乎每場調查都要查的背景資料。Azure Activity 記得用 Azure Policy 把診斷設定套到全部訂用帳戶，漏一個就是盲區。
  3. Day 2：Microsoft Entra ID（SigninLogs＋AuditLogs）——要花錢但不能省：身分識別是現代攻擊的第一入口，沒有登入記錄，帳號入侵偵測全歸零。先確認 P1／P2 授權到位。
  4. Day 3：透過 AMA 的 Windows 安全性事件——對網域控制站與重要伺服器建 DCR，事件集選「通用」，並在 DCR 裡先放好 transformKql 把 5156 這類雜訊擋掉——成本控制從第一天做，不要等帳單來了才回頭救火。
  5. Day 4–5：防火牆／網路設備（CEF via AMA）——非微軟來源靠 CEF 轉送（明天主題）。先只接邊界防火牆的 deny／threat 記錄，量最大的 allow 流量記錄用轉換修剪或暫緩。

決策邏輯：免費且高價值 → 先接；要錢但關鍵（身分）→ 確認授權後接；量大的 → 帶著 DCR 轉換一起上。每接一個，隔天到健康活頁簿確認量有進來、且在預估範圍內。

活頁簿（Workbook）範本庫

從 GitHub 部署的社群範本
看正解與解析
正解：B

內容中樞（Content Hub）以解決方案（solution）為單位打包現成內容：資料連接器、分析規則範本、活頁簿，視方案還包含搜捕查詢、劇本（Playbook）、剖析器等。安裝一次即全部進工作區，並可在「管理」檢視集中更新版本，正是題目要的「單一套件、可集中更新」。

  • A：存放庫（repositories）是把「你自訂的內容」透過 CI/CD 從原始碼庫部署到多個工作區的機制，不是取得微軟現成打包內容的入口。
  • C：活頁簿範本庫只涵蓋活頁簿一種內容類型，帶不進連接器與分析規則範本。
  • D：從 GitHub 手動部署社群範本是逐項、非受管的做法，沒有打包與集中更新機制，已被內容中樞取代為次要路徑。

QUESTION 2 · D1-0022
Your SOC uses Microsoft Defender XDR and Microsoft Sentinel. The Microsoft Defender XDR data connector is connected with its default configuration, so incidents and alerts are synchronized. Analysts now need to create custom scheduled analytics rules in Microsoft Sentinel that query the DeviceProcessEvents and EmailEvents tables, and the raw events must be retained in the workspace for longer than 30 days. What should you do?
（你的 SOC 使用 Microsoft Defender XDR 與 Microsoft Sentinel。Microsoft Defender XDR 資料連接器已用預設設定連線，事件與警示會同步。分析師現在需要在 Sentinel 建立查詢 DeviceProcessEvents 與 EmailEvents 資料表的自訂排程分析規則，且原始事件必須在工作區保留超過 30 天。你應該怎麼做？）
A. In the Microsoft Defender XDR connector, enable the collection of the required advanced hunting event tables
在 Microsoft Defender XDR 連接器中，啟用所需進階搜捕事件資料表的收集
B. Connect the standalone Microsoft Defender for Endpoint alerts connector
另外連接獨立的 Microsoft Defender for Endpoint 警示連接器
C. Onboard the Microsoft Sentinel workspace to the Microsoft Defender portal
將 Microsoft Sentinel 工作區連入（onboard）Microsoft Defender 入口網站
D. Create summary rules for the DeviceProcessEvents and EmailEvents tables
為 DeviceProcessEvents 與 EmailEvents 資料表建立 summary rules
看正解與解析
正解：A

Defender XDR 連接器有兩層資料：預設同步的事件與警示（免擷取費），以及可加選的進階搜捕原始事件表（DeviceProcessEvents、EmailEvents 等，需付擷取費）。要在 Sentinel 對原始表寫自訂分析規則並保留超過 XDR 原生的 30 天，必須在連接器中啟用這些事件表的收集，把資料真正擷取進工作區。

  • B：各產品的獨立警示連接器只帶警示，拿不到 DeviceProcessEvents 這類原始事件表，也無法滿足長期保留原始資料的需求。
  • C：連入 Defender portal 提供統一事件佇列與統一進階搜捕介面，但不會把 XDR 原始事件表擷取進 Sentinel 工作區，無法用工作區保留原始事件超過 30 天。
  • D：Summary rules 是對已擷取（入庫）的資料做事後彙總；資料表根本還沒進工作區，沒有東西可以彙總。

QUESTION 3 · D1-0023
You collect Windows Security events from your servers by using the Azure Monitor Agent (AMA) and a data collection rule (DCR). The SecurityEvent table is dominated by event ID 5156, which has high volume and low detection value. You must reduce ingestion costs by dropping these events before they are stored in the workspace. What should you do?
（你透過 Azure Monitor Agent（AMA）與資料收集規則（DCR）收集伺服器的 Windows 安全性事件。SecurityEvent 資料表被事件識別碼 5156 佔滿——量大而偵測價值低。你必須在這些事件存入工作區之前把它們丟棄，以降低擷取成本。你應該怎麼做？）
A. Shorten the retention period of the SecurityEvent table
縮短 SecurityEvent 資料表的保留期
B. Change the SecurityEvent table to the basic logs plan
把 SecurityEvent 資料表改為基本記錄（basic logs）方案
C. Add a transformKql transformation to the DCR that filters out event ID 5156
在 DCR 中加入 transformKql 轉換，過濾掉事件識別碼 5156
D. Create an ASIM parser that excludes event ID 5156
建立排除事件識別碼 5156 的 ASIM 剖析器
看正解與解析
正解：C

擷取時轉換（ingestion-time transformation）寫在 DCR 的 transformKql 裡，對入庫前的資料流逐筆執行；用 where 條件把 5156 丟掉，這些事件就完全不入庫、不計費，正好符合「存入工作區之前丟棄以省成本」。附帶細則：過濾量若超過進料的 50%，超出部分會收資料處理費。

  • A：保留期只影響儲存成本，資料仍然全額擷取並計費，無法達成「入庫前丟棄」。
  • B：基本記錄是把整張表換成低價擷取、查詢受限的方案，事件仍然全部入庫，不是「減量」；且該表要供分析規則使用時並不適合。
  • D：ASIM 剖析器是查詢時（query-time）正規化，資料原封不動入庫，不會減少任何擷取費用。

QUESTION 4 · D1-0024
Your compliance team requires that client IP addresses in the SigninLogs table be partially masked before the records are stored in your Microsoft Sentinel workspace. SigninLogs is ingested through the Microsoft Entra ID service-to-service connector. Your servers also send Windows Security events through the Azure Monitor Agent (AMA) using a standard DCR. What should you do to meet the masking requirement?
（法遵團隊要求：SigninLogs 資料表中的用戶端 IP 位址必須在記錄存入 Microsoft Sentinel 工作區之前部分遮罩。SigninLogs 是經由 Microsoft Entra ID 服務對服務連接器擷取的；你的伺服器另外透過 Azure Monitor Agent（AMA）與標準 DCR 傳送 Windows 安全性事件。要滿足遮罩要求，你應該怎麼做？）
A. Add the masking transformation to the standard DCR that is associated with your AMA servers
把遮罩轉換加到與 AMA 伺服器關聯的標準 DCR 中
B. Create an ASIM parser that masks the IP address field
建立會遮罩 IP 位址欄位的 ASIM 剖析器
C. Enable customer-managed keys for the workspace
為工作區啟用客戶自控金鑰（customer-managed keys）
D. Add a transformation for the SigninLogs table in the workspace transformation DCR
在工作區轉換 DCR（workspace transformation DCR）中為 SigninLogs 資料表加入轉換
看正解與解析
正解：D

SigninLogs 走服務對服務連接器直送工作區，不經過任何代理程式或標準 DCR。這條路徑的擷取時加工只有一個掛載點：工作區轉換 DCR——每個工作區僅一條，按資料表定義轉換。在其中對 SigninLogs 寫遮罩（例如 replace_regex 換掉 IP 最後一段），資料入庫前即被遮罩，工作區內從未存在完整 IP，正面滿足法遵要求。

  • A：與 AMA 關聯的標準 DCR 只作用於代理程式收集的資料流（如 SecurityEvent）；SigninLogs 根本不流經它，加了也沒有效果。這是本題主要陷阱。
  • B：ASIM 剖析器是查詢時正規化：查詢結果可以呈現遮罩後的值，但工作區裡儲存的仍是完整 IP，不符合「存入前遮罩」。
  • C：客戶自控金鑰是靜態加密的金鑰治理，資料解密後分析師照樣看得到完整 IP，與欄位遮罩是不同層次的控制。

QUESTION 5 · D1-0025
During an investigation, your SOC discovers that the Office 365 data connector silently stopped ingesting data three weeks ago. You must ensure that, in the future, the SOC is automatically notified through an incident whenever any data connector fails or stops ingesting. What should you do?
（你的 SOC 在一次調查中才發現：Office 365 資料連接器三週前就默默停止擷取資料。你必須確保未來任何資料連接器失敗或停止擷取時，SOC 都會透過事件自動收到通知。你應該怎麼做？）
A. Enable health monitoring in the Microsoft Sentinel settings, and create an analytics rule that queries the SentinelHealth table
在 Microsoft Sentinel 設定中啟用健康監控，並建立查詢 SentinelHealth 資料表的分析規則
B. Review the data collection health monitoring workbook every week
每週檢視資料收集健康監控活頁簿（Workbook）
C. Create an automation rule that runs when new incidents are created
建立在新事件產生時執行的自動化規則
D. Create an analytics rule that queries the Heartbeat table for missing agents
建立查詢 Heartbeat 資料表、找出失聯代理程式的分析規則
看正解與解析
正解：A

啟用 Sentinel 的稽核與健康監控後，資料連接器等資源的健康事件會寫入 SentinelHealth 資料表；對這張表建立分析規則，連接器一失敗或斷流就會產生事件通知 SOC——這是唯一涵蓋所有連接器（含服務對服務類型）且全自動的做法。

  • B：健康監控活頁簿是很好的巡檢工具，但屬於人工、週期性檢視，無法在故障當下自動產生事件通知，正是本題要避免的「三週後才發現」模式。
  • C：自動化規則的觸發前提是「有事件產生」；連接器斷流時通常不會有相關事件，等於永遠不會觸發，無法偵測擷取中斷本身。
  • D：Heartbeat 只反映代理程式（如 AMA）的存活狀態；Office 365 是服務對服務連接器，沒有代理程式，這個做法涵蓋不到它。
