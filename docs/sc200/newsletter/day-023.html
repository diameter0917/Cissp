01 — 📌 本日導讀

從「查得到」升級成「想得到」

前兩天你已經會用 Microsoft Sentinel 的搜捕介面跑查詢、存書籤、開 Livestream——那是手；今天補上腦：這個查詢究竟要回答什麼問題？D3「執行威脅搜捕」占 20–25%，考題不問按鈕在哪，而是丟給你一份威脅情報或一個 ATT&CK 技術，問下一步該搜捕什麼、範圍怎麼訂、結果記在哪。三條主線：三種驅動方式各從哪裡起跑、MITRE ATT&CK 怎麼當地圖用、筆記本（Notebook）何時才划算。

學習目標（對應官方考綱 D3「執行威脅搜捕」）：
  • ☐ 說明搜捕與事件回應、警示分診的差別，並定義可驗證的假說（對應 hunt for threats by using Microsoft Sentinel）
  • ☐ 從威脅情報、ATT&CK 技術、環境弱點與近期事件生出假說，寫成有時間窗、有資料表、有預期特徵的敘述

  • ☐ 把有效的假說排程化，用書籤與紀錄累積團隊知識

03 — 🧭 三種驅動方式

搜捕不是只有一種跑法

「威脅搜捕」在考題裡有三種面貌，起跑點不同，搞混就選錯工具。

驅動方式起點怎麼跑產出侷限
情資驅動
（IoC）		具體指標：雜湊、網域、IP、寄件者指標放進監視清單（Watchlist）或威脅情報，跨表比對並回溯歷史明確的是／否：出現過沒、在哪台、何時第一次只抓得到已知；對手換基礎設施就失效
假說驅動一句可驗證的推測，多半來自 ATT&CK 技術或威脅模型拆成可觀察特徵 → 選資料表 → 訂時間窗 → 查詢 → 依結果轉向成立／不成立／資料不足，外加新偵測構想與能見度缺口吃知識與時間；寫太大跑不完
異常驅動統計或機器學習指出的離群：UEBA 分數、異常規則從離群反推情境：平常長什麼樣、這次哪裡不同、有無旁證值得升級的少數異常，與調整基準線的依據離群不等於惡意，需環境知識篩

成熟 SOC 是三者接力：情資驅動找到一台中招主機 → 假說驅動問「同一手法還有誰中」→ 異常清單再變成下一輪假說。今天主攻中間這段。

🎯 考點聚焦
「這是搜捕嗎」只有一個判準：起點是不是「先前未被偵測到」的東西。題幹寫「佇列出現高嚴重性事件，請調查」→ 那是分診；寫「懷疑有尚未觸發警示的行為，請主動尋找」→ 才是搜捕。陷阱選項常把「調降規則門檻」或「檢視自動調查結果」當成搜捕，兩者都從既有警示出發。
04 — 🧪 假說怎麼生出來

四個來源，一個句型，三種結局

最卡的一步是「我知道要寫假說，可是要假設什麼？」假說有四個穩定來源：威脅情報（某群組用合法遠端管理工具做持續性 → 我這裡有沒有非 IT 主機裝了這類工具）、ATT&CK 技術（挑一個沒有規則覆蓋的格子當題目）、環境弱點（共用本機管理員密碼、沒 MFA 的服務帳號）、近期事件（上次沒查完的線頭）。

假說句型：如果〔對手行為／ATT&CK 技術〕正在我的環境發生，那麼在〔資料表／訊號來源〕應可觀察到〔具體特徵〕，範圍限定〔時間窗〕與〔資產〕。
例：如果有人用 DCSync（T1003.006）竊取憑證，目錄複寫紀錄應出現「非網域控制站帳號發起複寫請求」，範圍近 30 天、全部網域控制站。

寫完拿影片那五條檢查，最常被違反的是「範圍夠窄」——「找出所有橫向移動」不是假說，是願望。也要接受三種結局都算成功：成立（存書籤、升級成事件）、不成立（存下查詢並記錄「查過、乾淨」）、資料不足（要看的欄位沒收，等於挖出能見度缺口）。沒抓到人不等於白做。

🎯 考點聚焦
四個選項都像合理假說時怎麼刷：依序刪掉——沒有時間窗或範圍的、用現有資料無法證實或推翻的、與威脅模型無關的、大到跑不完的。剩下的通常是「限定時間窗＋限定資產＋指名一個技術」那個。另一轉折題：查完什麼都沒有，下一步？正解多半是保存查詢並記錄結論。
🛡️ 實戰情境：一次完整的假說驗證（DCSync）

週一 09:40 情資進來：某鎖定製造業的群組慣用手法是先取得有複寫權限的服務帳號，再用 DCSync 拉出全網域雜湊。你們正是製造業，對得上威脅模型。

  1. 寫假說（09:50）：即上面那句 DCSync 假說，五條檢核全過。
  2. 選資料（09:55）：首選 Microsoft Defender for Identity（MDI）的身分目錄事件；只有 Windows 安全性事件記錄時就看物件存取事件（4662）與複寫控制存取碼。先確認資料有在收，否則結論只會是「資料不足」。
  3. 第一次查詢（10:05）：看有誰做過複寫，排除網域控制站電腦帳號。
IdentityDirectoryEvents
| where Timestamp > ago(30d)
| where ActionType == "Directory Services replication"
| where AccountName !endswith "$"
| summarize FirstSeen = min(Timestamp), LastSeen = max(Timestamp),
            Attempts = count(), Sources = make_set(DeviceName, 10)
        by AccountName, AccountDomain
| order by Attempts desc

30 天時間窗呼應假說；只留「目錄服務複寫」動作；!endswith "$" 濾掉電腦帳號，因為網域控制站彼此複寫是正常的；summarize 算出首見／末見與來源主機——首見時間最關鍵，它區分「一直都有」與「這週才冒出來」。

  1. 結果（10:12）：svc-backup 十四個月來每天出現、來源固定是備份伺服器，屬於基準線；svc-print 只在上週四凌晨 02:11 出現 3 次，來源是財務部工作站——印表服務帳號、半夜、從使用者工作站發起複寫，三個條件同時不合理。
  2. 轉向（10:20）：pivot 到那台工作站，看前後發生了什麼。
let SuspectWindow = datetime(2026-08-13 01:30) .. datetime(2026-08-13 03:30);
DeviceProcessEvents
| where Timestamp between (SuspectWindow)
| where DeviceName startswith "FIN-WS"
| project Timestamp, DeviceName, AccountName, FileName,
          InitiatingProcessFileName, ProcessCommandLine
| order by Timestamp asc

用 let 命名時間區間再以 between 套用，是轉向時最省事的寫法；只投影必要欄位讓時間軸讀得順，父程序與命令列往往就是判斷惡意與否的關鍵。

  1. 結論（10:35）：複寫前 6 分鐘，有人以遠端管理工具在該機啟動一個從暫存目錄執行的程式，父程序是瀏覽器下載。假說成立。
  2. 收尾（10:40）：關鍵結果列存成書籤，對應實體（svc-print、FIN-WS-042），戰術標憑證存取、技術標 T1003.006，升級成事件交二線；第一段查詢存起來排程每日重跑。順帶收穫是建立「哪些帳號可合法複寫」的基準線。
05 — 🗺️ ATT&CK 當地圖

戰術是目的，技術是手法

ATT&CK 是對手行為的公開知識庫，三層結構常拿來出分辨題：戰術（tactic）＝對手為什麼做，是階段性目的（初始存取、持續性、憑證存取…），企業矩陣共 14 個，Sentinel 的規則與書籤標的就是這層；技術（technique）＝怎麼做，有 T 編號（T1003 OS Credential Dumping）；子技術更細（T1003.006 DCSync）；程序是某對手的實際實作。

MITRE ATT&CK 涵蓋率檢視把矩陣畫在你的環境上：顏色深淺代表有多少偵測對應到該技術，並可切換兩種來源——已啟用的分析規則與規則範本及搜捕查詢，兩者差距就是「馬上補得起來的缺口」。缺口分兩種：沒資料（連接器沒接、記錄層級沒開）要補資料源，有資料沒規則則啟用範本或自己寫。

另一個實務重點：搜捕成果要自己標上去。影片建書籤與搜捕查詢時都做了對應實體與選戰術；沒標的查詢不會進涵蓋率統計，那張圖也就退化成裝飾品。

ATT&CK 戰術對手目的訊號來源典型搜捕假說
初始存取取得第一個立足點郵件事件、身分登入、VPN近 7 天有無使用者自陌生國家成功登入
持續性重開機後仍活著登錄機碼、排程工作、服務建立近 30 天有無非 IT 帳號建立自動啟動項目
憑證存取拿到帳密或雜湊身分目錄事件、LSASS 存取近 30 天有無非網域控制站帳號發起目錄複寫（見 §04）
橫向移動從一台擴散到多台登入事件、遠端服務、SMB／WMI近 7 天有無帳號 1 小時內登入 5 台沒登過的主機
命令與控制維持外部通道網路連線、DNS、Proxy近 14 天有無主機對同一外部位址呈固定間隔的信標連線
外洩把資料帶走雲端應用活動、上傳流量近 30 天有無帳號於離峰時段大量下載再上傳個人雲端
🎯 考點聚焦
戰術 vs 技術：訣竅是問「對手想達成什麼（戰術）」與「用什麼手段（技術）」。「傾印 LSASS 記憶體取得雜湊」→ 戰術是憑證存取、技術是 OS Credential Dumping、子技術是 LSASS Memory。陷阱是把「橫向移動」當技術、「Pass-the-Hash」當戰術。另一組必背：涵蓋率檢視回答「我對哪些技術有偵測」，不是「我被哪些技術打過」。
06 — 📓 筆記本何時划算

Notebook 不是更炫的查詢框

筆記本就是 Jupyter：文字與可執行程式碼交錯的文件，在 Sentinel 裡跑 Python，透過 Log Analytics 的 API 讀你的資料。兩個名字要記住：KQLMagic（在筆記本裡直接寫 KQL 的包裝）與 MSTICPy（微軟的資安調查 Python 工具集，含情報查詢、GeoIP、時間序列分析與視覺化）。

重點不是「它能做什麼」，而是何時值得付這個成本——它要 Azure Machine Learning 工作區與運算資源（計費）、要 Python 能力、還要維護程式碼。判準很簡單：KQL 查詢框做得到的就別開筆記本。划算的有四類：機器學習與統計（分群、離群與信標偵測）、外部資料富化（逐個 IP 查 Whois、GeoIP、多家情報再併回同一張表）、跨來源合併（Sentinel 資料＋資產清冊、HR 名單）、可重複的調查劇本（換參數重跑整套流程，過程天然就是紀錄）。

工具核心用途主要使用者選它的時機
搜捕查詢（KQL）互動式提問與轉向全體分析師問題能用一段 KQL 表達——多數情況
劇本（Playbook）自動化與修復動作SOC 工程師、分析師要「做動作」：通知、開單、封鎖、隔離
活頁簿（Workbook）視覺化與儀表板分析師、SOC 主管要給人持續看的圖表與趨勢
筆記本（Notebook）深度分析與彈性調查威脅搜捕者、二三線分析師、資料科學家機器學習、外部富化、跨來源合併、可重複的調查流程

建立方式兩條：從 Sentinel 筆記本頁面挑範本（需連結 Azure ML 工作區與運算叢集），或在 Visual Studio Code 建 Jupyter Notebook 再接回來。2026 新考點 data lake 的筆記本走 VS Code 擴充功能加 MCP（Model Context Protocol）伺服器——這條路線與 Sentinel Graph 是明天的主題。

🎯 考點聚焦
工具四選一怎麼刷：題幹出現 apply machine learning、enrich with GeoIP or Whois、combine Sentinel data with external datasets → 筆記本；automatically notify / block / isolate → 劇本；dashboard for management → 活頁簿；「快速確認這個雜湊有沒有出現過」→ 一段搜捕查詢就好。另一常錯點：使用筆記本的前置作業是 Azure ML 工作區與運算資源，不是「啟用 UEBA」或「建立監視清單」。
07 — 🪜 成熟度與紀錄

讓有效的假說變成資產

搜捕做不起來的團隊，多半不是查詢寫不好，而是每次都從零開始。成熟度階梯：臨時起意 → 有來源（依情資或 ATT&CK 挑題）→ 可重複（假說與查詢存下來，別人能重跑）→ 排程化 → 自動化（變成規則或維護監視清單）。

何時把假說變成規則？三條件同時成立時升級為排程分析規則：訊噪比夠好、邏輯能穩定用 KQL 表達、值得 24 小時盯。若只是定期回顧或要跨很長時間，走 data lake 的 KQL 作業或搜尋作業；訊噪比差但有價值的，留在搜捕查詢並排人工複查。

紀錄要留什麼？書籤存的是查詢＋結果列＋實體對應＋戰術標記；一次搜捕結束，紀錄至少要有假說原文、資料範圍與時間窗、用過的查詢、結果判定與後續動作。「不成立」的同樣要留——半年後有人問「查過 DCSync 嗎」，你要答得出「查過，範圍 30 天，乾淨」。

💡 搜捕的三種產出都要交付：(1) 發現——書籤與升級的事件；(2) 新偵測——排程規則、自訂偵測或搜捕查詢；(3) 缺口——資料沒收、記錄層級不足、涵蓋率空白格。第三項最常被漏掉，卻是考題問「搜捕價值」的標準答案之一。
08 — 🧩 考綱補洞

EP10 略過、考題卻會碰的

  • 搜捕查詢範本客製（考綱 customize content gallery hunting queries）：社群查詢的正確用法是複製後改成自己的資料表與門檻（如排除已知服務帳號），再存成自己的查詢並標戰術，而不是原封不動跑完嫌誤報高。
  • Hunts 與書籤的關係：hunt 把假說敘述、狀態（進行中／已驗證／已推翻）、多個查詢、書籤與筆記收在同一容器並指派負責人。問「如何追蹤多人協作的搜捕」→ 建立 hunt。
  • 進階搜捕 vs Sentinel 搜捕：前者查 XDR 自己的表（預設 30 天）、可直接做成自訂偵測並附回應動作；後者查工作區全部資料源、可回溯更久。跨端點＋身分＋郵件的快問快答走進階搜捕，含第三方記錄走 Sentinel。
  • 筆記本的權限與成本：需 Azure ML 工作區與 Sentinel 讀取權限；運算執行個體不用要停掉否則持續計費；MSTICPy 的工作區 ID 與 API 金鑰放設定檔，別寫死在程式碼。
  • Security Copilot 協助搜捕 2026 新考點：可用自然語言生成 KQL 查詢、摘要結果。定位照舊——它加速把想法變成查詢，假說品質與是否升級仍由分析師負責。

QUESTION 1 · D3-0021
You are a security operations analyst at Contoso. During a SOC review, your manager asks you to explain how threat hunting in Microsoft Sentinel differs from the team's daily incident response work. Which statement best describes threat hunting?
（你是 Contoso 的資安維運分析師。在 SOC 檢討會上，主管要你說明 Microsoft Sentinel 的威脅搜捕與團隊每天做的事件回應有何不同。下列哪一項最能描述威脅搜捕？）
A. It is the process of triaging incidents in the unified queue and assigning each one to the correct analyst tier.
它是在統一佇列中分診事件，並把每一件指派給正確層級分析師的流程。
B. It is the tuning of analytics rules and alert suppression so that benign alerts stop reaching the incident queue.
它是調整分析規則與抑制警示，讓良性警示不再進入事件佇列的工作。
C. It is the proactive search of the environment for threats and activity that have not previously been detected.
它是主動在環境中搜尋先前未被偵測到的威脅或活動。
D. It is the automated containment of confirmed threats by running playbooks against the affected entities.
它是對已確認的威脅執行劇本（Playbook），自動遏制受影響實體的動作。
看正解與解析
正解：C

官方定義的關鍵字是「先前未被偵測到（not previously detected）」與「主動（proactively）」。搜捕從分析師的問題或假說出發，去找還沒有任何警示的行為；事件回應與分診則從「已經被標記出來」的警示或事件開始。兩者互補：搜捕的成果（書籤、確認的可疑活動）可以升級成事件進入回應流程，有效的搜捕邏輯也可以轉成排程分析規則，變成日後的自動偵測。

  • A：分診（triage）是處理佇列中已存在的事件並排定優先順序、指派擁有者，起點是既有警示，屬於事件回應的一環，不是搜捕。
  • B：調整分析規則與抑制良性警示屬於偵測調校（alert tuning），目的在降低雜訊，同樣以既有偵測為起點，不會找出未被偵測到的行為。
  • D：以劇本自動遏制威脅是 SOAR 的自動化回應，發生在威脅已被確認之後，屬於回應階段而非搜捕。

QUESTION 2 · D3-0022
A threat intelligence report states that an adversary group targeting your industry obtains a service account with replication rights and then uses DCSync to extract domain credentials. You have Microsoft Defender for Identity data in your workspace and one afternoon to hunt. Which hunting hypothesis should you use?
（一份威脅情報報告指出，鎖定你所屬產業的對手群組會先取得具備複寫權限的服務帳號，再以 DCSync 竊取網域憑證。你的工作區已有 Microsoft Defender for Identity（MDI）資料，而你只有一個下午的時間可以搜捕。你應該採用哪一個搜捕假說？）
A. Determine whether any malicious activity is currently taking place anywhere in the environment.
判斷環境中目前是否有任何地方正在發生惡意活動。
B. In the last 30 days, did any account other than a domain controller computer account request directory replication from a domain controller?
在過去 30 天內，是否有網域控制站電腦帳號以外的帳號，向網域控制站發起目錄複寫請求？
C. Determine whether the adversary group described in the report has also attacked other companies in the same industry.
判斷報告中描述的對手群組是否也攻擊過同業的其他公司。
D. Determine whether every privileged account in the forest has been compromised at some point since the domain was created.
判斷樹系中每一個特權帳號自網域建立以來是否曾在某個時間點遭到入侵。
看正解與解析
正解：B

好的搜捕假說要同時滿足五個條件：做得完、範圍夠窄（能用手上的資料證實或推翻）、有明確時間界線、產出可行動的洞察、並且對齊你要防禦的威脅模型。選項 B 指名一個技術（DCSync／目錄複寫）、指定資料來源（MDI 的身分目錄事件）、限定 30 天時間窗與網域控制站範圍，一個下午就能跑完並得到「成立／不成立／資料不足」其中一種明確結論。

  • A：沒有時間窗、沒有範圍、沒有指名技術，無法用一次查詢證實或推翻，屬於願望而非假說。
  • C：問題的答案不在你的環境資料裡，用工作區的記錄無法驗證；那是威脅情報研究，不是對自家環境的搜捕。
  • D：範圍涵蓋整個樹系與全部歷史，既做不完，資料保留期通常也不足以回答，違反「做得完」與「有時間界線」。

QUESTION 3 · D3-0023
While hunting in Microsoft Sentinel you find a row showing a process that opened LSASS memory on a domain-joined server and wrote the contents to a file in a temporary folder. You create a bookmark for the row and must select the MITRE ATT&CK tactic for it. Which tactic should you select?
（你在 Microsoft Sentinel 搜捕時，發現一列紀錄顯示某程序在已加入網域的伺服器上開啟 LSASS 記憶體，並把內容寫入暫存資料夾的檔案。你要為這一列建立書籤，並選擇對應的 MITRE ATT&CK 戰術。你應該選哪一個戰術？）
A. Credential Access
憑證存取（Credential Access）
B. Lateral Movement
橫向移動（Lateral Movement）
C. Persistence
持續性（Persistence）
D. Command and Control
命令與控制（Command and Control）
看正解與解析
正解：A

分辨戰術與技術的訣竅是分別問「對手想達成什麼」與「他用什麼手段」。傾印 LSASS 記憶體的目的是取得帳號密碼或雜湊，因此戰術是憑證存取；手段（技術）是 OS Credential Dumping，子技術是 LSASS Memory。書籤與搜捕查詢上標好戰術與技術有兩個好處：實體與戰術會被帶進事件與 MITRE 涵蓋率統計，團隊也才看得出這格其實有人在人工搜捕。

  • B：橫向移動描述的是拿到憑證之後往其他主機擴散的階段（例如遠端服務建立、Pass-the-Hash 登入），本題的行為仍停留在取得憑證。
  • C：持續性指的是讓存取在重開機或憑證變更後仍然有效，例如建立排程工作、服務或自動啟動項目，與讀取 LSASS 記憶體無關。
  • D：命令與控制是維持與外部控制端的通道（例如信標式連線、DNS 通道），本題沒有任何對外通訊的跡象。

QUESTION 4 · D3-0024
Your SOC must plan next quarter's detection engineering work. The team needs to see which MITRE ATT&CK techniques are already covered by enabled analytics rules, which are only covered by rule templates or hunting queries, and which have no coverage at all. What should you use?
（你的 SOC 要規劃下一季的偵測工程工作。團隊需要看出哪些 MITRE ATT&CK 技術已經有「已啟用的分析規則」覆蓋、哪些只有規則範本或搜捕查詢覆蓋、哪些完全沒有覆蓋。你應該使用什麼？）
A. A workbook that charts incident counts by severity and product over the last quarter.
一份活頁簿（Workbook），依嚴重性與產品繪出上一季的事件數量圖表。
B. The Anomalies table produced by UEBA and the anomaly analytics rules.
由 UEBA 與異常分析規則產生的 Anomalies 資料表。
C. Livestream sessions for the hunting queries that the team runs most often.
為團隊最常執行的搜捕查詢建立 Livestream 工作階段。
D. The MITRE ATT&CK coverage view in Microsoft Sentinel, switching the legend between active analytics rules and rule templates or hunting queries.
Microsoft Sentinel 的 MITRE ATT&CK 涵蓋率檢視，並切換圖例在「已啟用的分析規則」與「規則範本或搜捕查詢」之間比較。
看正解與解析
正解：D

MITRE ATT&CK 涵蓋率檢視把 ATT&CK 矩陣畫在你自己的環境上，格子顏色深淺代表對應到該技術的偵測數量，並可切換來源：已啟用的分析規則代表現在真的在保護你，規則範本與搜捕查詢代表隨手就能補上的部分，兩者的差距就是可以最快補齊的缺口。要特別記住它回答的是「我對哪些技術有偵測」，而不是「我被哪些技術攻擊過」。

  • A：活頁簿呈現的是已產生事件的統計，只看得到「有偵測到什麼」，看不出哪些技術根本沒有任何規則覆蓋。
  • B：Anomalies 資料表存放 UEBA 與異常規則的離群結果，屬於異常驅動搜捕的輸入，與偵測涵蓋率盤點無關。
  • C：Livestream 是把查詢對正在發生的事件做近乎即時的比對與通知，用於驗證單一假說，不會產生技術涵蓋率的全景。

QUESTION 5 · D3-0025
A hunt produced roughly 800 external IP addresses. A tier-3 hunter must enrich every address with GeoIP and Whois data plus three external threat intelligence providers, then apply clustering to identify beacon-like groups, and keep the whole workflow repeatable and shareable for future hunts. Which approach meets the requirement, and what must be provisioned first?
（一次搜捕產出約 800 個外部 IP 位址。三線搜捕人員必須為每個位址加上 GeoIP 與 Whois 資料，再比對三家外部威脅情報，接著用分群找出疑似信標的群組，而且整套流程要能重複執行並分享給日後的搜捕使用。哪一種做法符合需求，且必須先佈建什麼？）
A. Build a workbook with parameterized queries and custom visualizations; provision a dedicated Log Analytics workspace for the workbook first.
建立一份含參數化查詢與自訂視覺化的活頁簿（Workbook）；先為該活頁簿佈建專屬的 Log Analytics 工作區。
B. Create a Microsoft Sentinel notebook that uses MSTICPy for enrichment and machine learning; provision an Azure Machine Learning workspace with compute first.
建立 Microsoft Sentinel 筆記本（Notebook），以 MSTICPy 進行富化與機器學習；先佈建含運算資源的 Azure Machine Learning 工作區。
C. Create an Azure Logic Apps playbook with an entity trigger that loops over the addresses; provision a Standard hosting plan for the playbook first.
建立以實體觸發程序逐一處理這些位址的 Azure Logic Apps 劇本（Playbook）；先為劇本佈建 Standard 主控方案。
D. Save the hunting query as a scheduled analytics rule and store the addresses in a watchlist; provision an additional commitment tier for the workspace first.
把搜捕查詢存成排程分析規則，並將這些位址放入監視清單（Watchlist）；先為工作區佈建額外的承諾層級。
看正解與解析
正解：B

同時要求外部資料富化、跨多個外部來源合併、機器學習分群，以及一套可重複、可分享的調查流程，這正是筆記本的定位：以 Python 透過 API 讀取 Sentinel 資料，用 MSTICPy 做威脅情報、GeoIP、Whois 查詢與異常分析，把程式碼、說明與圖表留在同一份文件裡。從 Sentinel 的筆記本頁面建立時，必須先有 Azure Machine Learning 工作區並配置運算資源（運算執行個體或叢集），不用時要停掉以免持續計費。

  • A：活頁簿是視覺化與儀表板工具，無法呼叫外部 API 做逐筆富化，也不能執行機器學習；而且它直接使用既有工作區，不需要另建工作區。
  • C：劇本擅長的是自動化與回應動作（通知、開單、封鎖、隔離），可做簡單富化，但不適合大量統計與分群分析；Standard 方案只是 Logic Apps 的計費與託管選項，不是本情境的關鍵。
  • D：排程分析規則與監視清單解決的是「持續偵測」與「清單比對」，無法做多來源富化與分群；承諾層級是資料擷取的計價方式，與分析能力無關。
