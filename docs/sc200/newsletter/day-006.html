Sentinel 工作區設計：先把地基打對，再談偵測

從今天起連續五天都在 Microsoft Sentinel 的主場。所有偵測、搜捕、自動化都建立在同一個地基上：Log Analytics 工作區（workspace）。地基設計錯了——區域選錯、工作區切太碎、權限給太大、成本失控——後面全部跟著痛。本日四個決策軸線：第一，架構：單一工作區還是多工作區？資料主權、租用戶邊界與 MSSP 代管怎麼影響答案；第二，角色：Microsoft Sentinel Reader／Responder／Contributor 的分界，以及 resource-context 與 table-level RBAC 兩種細粒度控制；第三，成本：承諾層級（commitment tier）、表方案（Analytics／Basic／Auxiliary）與免費資料來源三顆旋鈕；第四，保留（retention）：互動保留與長期保留的分界、search job 與還原（restore）何時登場。這些是 D1「管理安全性作業環境」（占比 40–45%）的核心題倉。

03 — 🏗️ 工作區架構決策

單一還是多個？先懂關係，再做決策

先釐清一個常被考的關係：Microsoft Sentinel 不是獨立資料庫，它是「疊」在 Log Analytics 工作區上的一組安全功能。你在某個工作區上啟用 Sentinel，該工作區就多了分析規則、事件、搜捕、自動化這些能力；所有記錄仍存放在工作區的資料表裡，用 KQL 查。一個工作區只能啟用一個 Sentinel，工作區綁定一個 Azure 區域，也隸屬於一個 Entra 租用戶——這三個「綁定」正是架構題的出題來源。

微軟的官方原則很明確：工作區數量越少越好。單一工作區讓所有資料可以直接關聯查詢、單一事件佇列、管理面最簡單。但下列因素會「逼」你切成多工作區：

決策因素傾向單一工作區需要多工作區的訊號
資料主權／區域法規全部資料可存放在同一區域法規要求記錄必須留在特定國家／區域（如歐盟資料須存放於歐盟）——工作區綁區域，只能一區一個工作區
租用戶邊界單一 Entra 租用戶多租用戶集團或 MSSP 客戶：Defender XDR 等第一方連接器只能連到同租用戶的工作區，跨租用戶必須各自建工作區＋Azure Lighthouse 代管
計費拆帳單一成本中心吸收各子公司／部門要各自負擔擷取費用，分開的工作區最乾淨
存取隔離resource-context 或 table-level RBAC 就能滿足不同團隊「連工作區的存在」都不能互看，或資料擁有權完全獨立
網路頻寬成本來源集中或跨區流量可接受大量記錄跨區傳送的頻寬費超過多工作區的管理成本

切成多工作區也不代表各自為政：同租用戶內可用 workspace() 跨工作區查詢把多個工作區的表 join 起來，事件也有跨工作區檢視；跨租用戶則交給下面補洞章節的 Azure Lighthouse。

一句話記憶：「能單一就單一；資料主權、租用戶邊界、拆帳需求三者出現任一個，才切多工作區。」考題給你一堆條件時，先掃有沒有這三個訊號。
04 — 🔐 Sentinel RBAC 角色

看、動事件、動內容：三個動詞決定角色

Sentinel 的權限走 Azure RBAC（跟昨天 Defender XDR 統一 RBAC 是兩套系統，各管各的資源）。角色建議指派在工作區所在的資源群組，讓權限同時涵蓋 Sentinel 與相關資源。四個專屬角色要背到反射：

角色能做什麼不能做什麼典型對象
Microsoft Sentinel Reader檢視資料、事件、活頁簿（Workbook）與所有 Sentinel 資源任何變更稽核、管理層、資安顧問
Microsoft Sentinel ResponderReader 的一切＋管理事件：指派、變更狀態與嚴重性、分類關閉建立／編輯分析規則、活頁簿等內容tier-1／tier-2 分析師（分診與調查）
Microsoft Sentinel ContributorResponder 的一切＋建立與編輯分析規則、活頁簿、搜捕查詢等內容指派角色、管理劇本（Playbook）的執行權限偵測工程師、SOC 工程師
Microsoft Sentinel Automation Contributor讓 Sentinel 服務本身把劇本加入自動化規則執行不是給人用的角色指派給 Sentinel 的服務身分（設定自動化時由系統要求）

兩個常見補充：執行與管理劇本另有 Microsoft Sentinel Playbook Operator（可檢視並手動執行劇本）與 Logic Apps 的角色；而 Log Analytics Contributor／Reader 這類工作區角色管的是「所有記錄資料與工作區設定」，範圍比 Sentinel 角色更廣——給了 Log Analytics Contributor，等於連非安全性的營運記錄都能動。最小權限題永遠優先選 Sentinel 專屬角色。

還有兩種「不給整個工作區」的細粒度控制：

  • Resource-context RBAC：非 SOC 的資源擁有者（例如某台 VM 的管理員）只要對「資源本身」有讀取權，就能查到「該資源產生的記錄」，完全不需要工作區權限。前提是工作區存取模式允許使用資源或工作區權限。適合「讓應用團隊看自己的記錄，但不開放整個工作區」。
  • Table-level RBAC：用自訂角色把讀取權限縮到特定資料表，例如讓稽核團隊只能查 SigninLogs，看不到端點與網路表。適合「同一個工作區裡，不同團隊只能看不同表」。
🎯 考點聚焦
最小權限選角公式：抓題幹的動詞。只「檢視／view」→ Reader；「指派事件、變更狀態、關閉事件」→ Responder；「建立或編輯分析規則／活頁簿」→ Contributor。兩個經典陷阱：（1）題目只要求分診事件，選 Contributor 就違反最小權限——Responder 才是正解；（2）Automation Contributor 看起來像「自動化工程師的角色」，其實是給 Sentinel 服務身分用的，凡是「指派給某位人員」的題目它都是干擾項。另外記住：「只能看特定資源的記錄」→ resource-context RBAC；「只能查特定資料表」→ table-level RBAC——兩個關鍵字對兩個機制，不要互換。
05 — 💰 成本三旋鈕

擷取按 GB 計費，省錢靠三顆旋鈕

Sentinel 的帳單主體是擷取量：資料進入工作區按 GB 計費（現行簡化計價已把 Log Analytics 與 Sentinel 合併成單一費率）。考試的成本題幾乎都繞著三顆旋鈕轉：

旋鈕一：承諾層級（commitment tier）。預設按用量付費（Pay-As-You-Go）；當每日擷取量穩定達 100 GB 以上，就能改選承諾層級——向微軟「承諾」每天至少吃下某個量（100、200、300⋯⋯GB/天，一路到數 TB），換取隨層級遞增的折扣。規則兩條：層級可以隨時往上調；要往下調或退出得等 31 天承諾期滿。用量低於承諾量仍按承諾量計費，所以先觀察實際量再承諾。

旋鈕二：表方案（table plan）。不是每種記錄都值得付「全功能」的價錢，按用途把表放進不同方案：

面向Analytics（分析）Basic（基本）Auxiliary（輔助）
設計用途高價值安全訊號：即時偵測與調查主力中價值、高量記錄：偶爾調查會查詳細（verbose）低價值記錄：合規留存、極少查詢
KQL 查詢完整能力、可跨表關聯受限運算子、查詢另計費最受限（單表為主）、查詢另計費
分析規則✔ 可觸發排程分析規則✘ 不支援✘ 不支援（可靠 summary rules 把聚合結果送回 Analytics 表）
互動保留預設 90 天免費（Sentinel 工作區），可延至 730 天30 天30 天
擷取單價最高低最低

旋鈕三：保留期。互動保留超過免費額度後按月計費，長期保留便宜得多——細節下一節。此外還有「根本不用錢」的來源要背：Azure 活動記錄、Office 365 稽核記錄（Exchange／SharePoint／Teams）、Microsoft Defender 系列產品的警示都免擷取費；新啟用的工作區前 31 天每天 10 GB 免費試用；Microsoft 365 E5 授權另有每人每天 5 MB 的特定資料贈與額度。

🎯 考點聚焦
「省錢題」答題心法：題幹喊「reduce cost」時，先辨認資料的性質再選旋鈕——（1）「每日擷取量大且穩定」→ 承諾層級；（2）「大量 verbose 記錄、不用於即時偵測、偶爾調查」→ Basic logs；「幾乎只為合規留存、極少查詢」→ Auxiliary logs；（3）「要留七年但不常查」→ 長期保留而非拉長互動保留。反向陷阱：把 SecurityEvent、SigninLogs 這類分析規則賴以運作的表改成 Basic/Auxiliary 是錯的——這些方案不支援排程分析規則，省了錢就瞎了偵測。免費來源（Azure 活動、O365 稽核、Defender 警示）出現在「該斷開哪個連接器省錢」的選項裡，一律不是答案——斷了也省不到錢。
06 — 🗄️ 保留與封存

兩層設定、兩種狀態、兩條回查路

保留設定有兩層：工作區預設保留期套用到所有表；表級保留可以覆寫預設——讓 SigninLogs 留兩年、讓防火牆表只留 90 天，各表各命。資料的生命週期則分兩種狀態：

  • 互動保留（interactive retention）：資料「熱」著，KQL 隨查隨到、分析規則正常吃。Analytics 表在 Sentinel 工作區預設 90 天免費，最長可設 730 天。
  • 長期保留（long-term／archive）：互動期滿後資料轉入低成本狀態，總保留期最長 12 年。資料還在，但不能直接查——要走以下兩條回查路。

兩條回查路怎麼選：search job 是非同步的大範圍掃描——用受限的 KQL 對長期保留資料跑一次搜尋，結果寫進新的 *_SRCH 表供你分析，適合「在一年前的記錄裡撈某個 IoC 的所有出現」；還原（restore）則是把某張表的特定時間範圍整段拉回互動狀態（*_RST 表），恢復完整 KQL 能力，適合「確定要對那兩週的資料做完整深度調查」，按還原的資料量與存續時間計費，查完記得刪。口訣：撈針用 search job，翻土用 restore。

🛡️ 實戰情境：三區域跨國企業＋MSSP 代管的工作區設計

Contoso 集團總部在台北，營運據點分布美國、德國、新加坡三區；德國子公司受 GDPR 與當地法規約束，記錄不得離開歐盟；夜間監控外包給 MSSP「Fabrikam SOC」。你是安全架構師，走一遍決策：

  1. 幾個工作區？資料主權訊號出現：德國資料必須留在歐盟 → 至少要在歐盟區域建一個獨立工作區。美國與新加坡若無資料駐留法規、跨區頻寬可接受，可合併成一個工作區；假設各區記錄量都大，最後落地三個工作區、各在當地區域，全數啟用 Sentinel。
  2. 怎麼統一看？三個工作區同屬 Contoso 租用戶 → 分析師用跨工作區事件檢視與 workspace() 查詢做關聯，不需要把資料搬來搬去。
  3. MSSP 怎麼進來？Fabrikam 在自己的租用戶工作，透過 Azure Lighthouse 接受 Contoso 委派——只委派三個工作區所在資源群組的 Microsoft Sentinel Responder（夜間只分診、不改偵測內容），不建來賓帳號、不給 Contributor。
  4. 成本怎麼調？美國工作區日擷取量穩定 150 GB → 選 100 GB 承諾層級觀察一個月再上調；防火牆與 Proxy 的 verbose 記錄改 Auxiliary logs，靠 summary rules 把每小時聚合統計送回 Analytics 表餵偵測。
  5. 保留怎麼設？工作區預設互動保留 90 天（免費額度內）；SigninLogs 與 SecurityAlert 表級覆寫為 180 天；全部表總保留期設 1 年滿足稽核。稽核來查舊資料 → search job；真的出事要深挖 → restore 那兩週。

複盤：資料主權決定工作區數量、Lighthouse＋Responder 解 MSSP 最小權限、承諾層級＋Auxiliary 控成本、表級保留＋search job 收尾——四個決策軸線在一題裡全用上了。

07 — 🧩 考綱補洞

EP7 沒講透、考試會考的

三個考綱明列、影片著墨有限的主題，補在這裡：

1. Azure Lighthouse：跨租用戶的正規解。MSSP 或多租用戶集團的分析師要在單一入口管理多個租用戶的 Sentinel，靠的是 Azure Lighthouse 的委派資源管理：客戶把特定範圍（訂用帳戶或資源群組）的特定 Azure 角色委派給服務商租用戶的使用者群組；服務商人員在自己租用戶登入，就能同時查詢、分診多個客戶工作區（跨工作區查詢同樣適用）。與昨天的 GDAP 區分清楚：GDAP 管 Microsoft 365／Defender XDR 的 Entra 角色委派，Lighthouse 管 Azure 資源（含 Sentinel 工作區）的 Azure RBAC 委派——題目問「代管客戶的 Sentinel 工作區」，答案是 Lighthouse。

2. SentinelHealth：環境自己的健康檢查。偵測沒觸發，是沒攻擊、還是連接器斷了？在 Sentinel 設定啟用「健康狀態與稽核」後，SentinelHealth 資料表會記錄資料連接器、分析規則、自動化規則與劇本的健康事件（另有 SentinelAudit 表記錄誰改了什麼）。搭配一段常用查詢：

SentinelHealth
| where TimeGenerated > ago(3d)
| where SentinelResourceType == "Data connector"
| where Status != "Success"
| project TimeGenerated, SentinelResourceName, Status, Description
| sort by TimeGenerated desc

查最近三天「資料連接器」的非成功健康事件：SentinelResourceType 篩資源類型、Status 抓失敗狀態、Description 給出失敗原因。把這段做成排程警示，連接器一斷你比稽核員先知道。考點：健康監控要先在設定中啟用，不是預設全開。

3. Defender portal 統一體驗 2026 新考點。工作區設計好之後，別忘了它的「新家」：把 Sentinel 工作區連入 Defender portal，事件與 XDR 進同一條佇列、進階搜捕同一個介面；多個工作區可以都連入，其中指定一個主要工作區（primary workspace）與 XDR 資料做事件關聯。2026 年 7 月起 Azure portal 的 Sentinel 體驗退場，統一入口是唯一主要體驗——但底層的 Log Analytics 工作區、Azure RBAC 角色、成本與保留設定全部不變，今天學的每一顆旋鈕在統一入口裡照轉。

QUESTION 1 · D1-0041
You are a security architect at a multinational manufacturer that is deploying Microsoft Sentinel. German regulators require that logs generated in Germany never leave the European Union, and the German entity must be invoiced separately for its own log ingestion. The US and Singapore sites have no data residency requirement, share one security budget, and want their data in a single workspace. You must meet every requirement with the smallest number of workspaces. What should you do?
（你是跨國製造商的安全架構師，正在部署 Microsoft Sentinel。德國法規要求德國產生的記錄不得離開歐盟，且德國法人必須就自己的記錄擷取量單獨計費。美國與新加坡據點沒有資料駐留要求、共用同一筆資安預算，並希望資料放在同一個工作區。你必須以最少的工作區數量滿足所有要求。你應該怎麼做？）
A. Create two workspaces: one in a European region for the German site, and one shared workspace for the US and Singapore sites.
建立兩個工作區：一個位於歐盟區域供德國據點使用，另一個由美國與新加坡據點共用。
B. Create a single workspace in a European region and onboard all three sites to it.
在歐盟區域建立單一工作區，三個據點全部接入。
C. Create three workspaces, one per site, each in the region of that site.
建立三個工作區，每個據點一個，各自位於當地區域。
D. Create a single workspace in a US region and use a data collection rule transformation to drop the records that were generated in Germany.
在美國區域建立單一工作區，並用資料收集規則（DCR）的轉換丟棄德國產生的記錄。
看正解與解析
正解：A

官方原則是「工作區數量越少越好」，但資料主權、租用戶邊界、計費拆帳三個訊號只要出現任一個，就必須切開。本題同時出現兩個訊號：德國記錄必須留在歐盟（工作區綁區域，只能在歐盟區域另建一個），以及德國法人要單獨計費（擷取費用依工作區出帳，只有分開工作區才能乾淨拆帳）。美國與新加坡沒有任何切分訊號、共用預算又要單一查詢面，合併成一個工作區即可。因此最小設計是兩個工作區；需要跨區關聯時，同租用戶內可用跨工作區事件檢視與 workspace() 查詢串起來，不必搬資料。

  • B：單一歐盟工作區雖然滿足資料駐留，但所有據點的擷取費用會落在同一個工作區帳單上，無法達成「德國法人單獨計費」的拆帳要求。
  • C：三個工作區確實滿足所有要求，但美國與新加坡沒有任何切分訊號，多切一個工作區只會增加管理與跨工作區查詢成本，違反「最少工作區」的條件。
  • D：工作區綁定單一區域，把資料放在美國區域即違反德國的資料駐留規定；用 DCR 轉換丟棄德國記錄更是直接失去該地區的偵測能力，不是資料主權問題的解法。

QUESTION 2 · D1-0042
You are a security operations analyst. Your compliance auditors must be able to run KQL queries against the SigninLogs table in the Log Analytics workspace that hosts Microsoft Sentinel. The auditors must not be able to read the endpoint, firewall, or DNS tables in the same workspace, and you cannot create an additional workspace for them. What should you configure?
（你是安全性作業分析師。稽核團隊必須能對承載 Microsoft Sentinel 的 Log Analytics 工作區中的 SigninLogs 資料表執行 KQL 查詢，但不得讀取同一工作區內的端點、防火牆與 DNS 資料表，而且你不能為他們另建工作區。你應該設定什麼？）
A. Assign the Microsoft Sentinel Reader role to the auditors on the resource group that contains the workspace.
在工作區所在的資源群組上，指派 Microsoft Sentinel Reader 角色給稽核團隊。
B. Create a custom role that grants read access only to the SigninLogs table (table-level RBAC) and assign it to the auditors.
建立只授與 SigninLogs 資料表讀取權的自訂角色（table-level RBAC），並指派給稽核團隊。
C. Configure resource-context RBAC so that the auditors can read the logs of the resources they own.
設定 resource-context RBAC，讓稽核團隊能讀取自己擁有的資源所產生的記錄。
D. Assign the Log Analytics Reader role to the auditors on the workspace.
在工作區上指派 Log Analytics Reader 角色給稽核團隊。
看正解與解析
正解：B

題幹的關鍵字是「同一個工作區裡、只能查特定資料表」——這正是 table-level RBAC（資料表層級存取控制）的定義場景：用自訂角色把讀取權縮到指定的資料表，其餘表一律看不到。記住兩個關鍵字對兩個機制：「只能看特定資源產生的記錄」→ resource-context RBAC；「只能查特定資料表」→ table-level RBAC，考題常故意互換。

  • A：Microsoft Sentinel Reader 可檢視工作區內的資料、事件與活頁簿（Workbook），範圍是整個 Sentinel，沒有辦法把讀取權限縮到單一資料表。
  • C：resource-context RBAC 的分界是「資源擁有權」——資源擁有者只能看自己那台機器產生的記錄；本題稽核團隊不擁有任何資源，需求也是依資料表切分，機制對不上。
  • D：Log Analytics Reader 的範圍比 Sentinel 專屬角色更廣，等於能讀工作區中所有資料表（含非安全性的營運記錄），完全違反題目的隔離要求與最小權限原則。

QUESTION 3 · D1-0043
A managed security service provider named Fabrikam SOC handles night-shift monitoring for your company. The Fabrikam analysts sign in to their own Microsoft Entra tenant and must triage incidents in the three Microsoft Sentinel workspaces that belong to your tenant. They must be able to assign incidents and change incident status, but not create or edit analytics rules, and your security policy forbids creating guest accounts in your tenant. What should you implement?
（一家名為 Fabrikam SOC 的受管資安服務供應商（MSSP）負責貴公司的夜間監控。Fabrikam 的分析師在自己的 Microsoft Entra 租用戶登入，必須分診你租用戶內三個 Microsoft Sentinel 工作區的事件：可以指派事件與變更事件狀態，但不得建立或編輯分析規則；而且公司政策禁止在你的租用戶中建立來賓帳戶。你應該實作什麼？）
A. Create guest accounts for the Fabrikam analysts in your tenant and assign them the Microsoft Sentinel Contributor role.
在你的租用戶為 Fabrikam 分析師建立來賓帳戶，並指派 Microsoft Sentinel Contributor 角色。
B. Configure Granular Delegated Admin Privileges (GDAP) so that Fabrikam receives delegated Microsoft Entra roles.
設定 GDAP（細微委派管理員權限），讓 Fabrikam 取得委派的 Microsoft Entra 角色。
C. Onboard the resource groups that contain the workspaces to Azure Lighthouse and delegate the Microsoft Sentinel Responder role to the Fabrikam analyst group.
將包含這些工作區的資源群組接入 Azure Lighthouse，並把 Microsoft Sentinel Responder 角色委派給 Fabrikam 的分析師群組。
D. Assign the Microsoft Sentinel Automation Contributor role to a service principal that belongs to Fabrikam.
把 Microsoft Sentinel Automation Contributor 角色指派給屬於 Fabrikam 的服務主體。
看正解與解析
正解：C

兩個條件要同時解：跨租用戶存取與最小權限。跨租用戶管理 Azure 資源（Sentinel 工作區屬於 Azure 資源）的正規解是 Azure Lighthouse 委派資源管理——客戶把資源群組範圍的特定 Azure 角色委派給服務商租用戶的使用者群組，服務商人員在自己的租用戶登入即可作業，不必建立來賓帳戶。權限則依動詞挑選：只要「指派事件、變更狀態」而不碰分析規則，Microsoft Sentinel Responder 就是剛好夠用的角色。

  • A：違反兩個條件：政策禁止建立來賓帳戶；Contributor 還能建立與編輯分析規則、活頁簿，超出夜間分診所需，違反最小權限。
  • B：GDAP 委派的是 Microsoft 365／Defender XDR 的 Microsoft Entra 角色，管不到 Azure 資源上的 Azure RBAC；Sentinel 工作區的存取要走 Lighthouse。
  • D：Microsoft Sentinel Automation Contributor 是給 Sentinel 服務本身在自動化規則中執行劇本（Playbook）用的角色，不是指派給人員或外部服務主體的分診角色，也無法解決跨租用戶存取。

QUESTION 4 · D1-0044
Your Microsoft Sentinel workspace has ingested a stable 150 GB per day for the past three months and is still billed at pay-as-you-go rates. Finance asks you to lower the monthly bill without disconnecting any data source and without weakening the scheduled analytics rules that run on the security tables. What should you do?
（貴公司的 Microsoft Sentinel 工作區過去三個月每天穩定擷取 150 GB，目前仍以隨用隨付（Pay-As-You-Go）計費。財務要求你降低月帳單，但不得斷開任何資料來源，也不得削弱在安全性資料表上執行的排程分析規則。你應該怎麼做？）
A. Disconnect the Azure Activity and Office 365 audit data connectors.
斷開 Azure 活動記錄與 Office 365 稽核記錄的資料連接器。
B. Change the SecurityEvent table to the Basic table plan.
把 SecurityEvent 資料表改為 Basic（基本）表方案。
C. Reduce the workspace default interactive retention from 90 days to 30 days.
把工作區的預設互動保留期從 90 天縮短為 30 天。
D. Select a 100 GB per day commitment tier for the workspace.
為工作區選擇每天 100 GB 的承諾層級（commitment tier）。
看正解與解析
正解：D

成本題先看資料的性質：每日擷取量「大且穩定」就是承諾層級的指紋。日擷取量穩定達 100 GB 以上即可從隨用隨付改為承諾層級，向微軟承諾每日最低量換取折扣，且不必動任何資料來源或偵測邏輯。承諾層級可隨時往上調；要往下調或退出則須等 31 天承諾期滿，所以先從保守的 100 GB 起跳、觀察後再上調是標準做法。

  • A：Azure 活動記錄與 Office 365 稽核記錄本來就是免擷取費的免費資料來源，斷開它們一毛錢也省不到，還會失去稽核可見度——這是成本題的經典反向陷阱。
  • B：Basic 表方案不支援排程分析規則，SecurityEvent 正是偵測的主力表；改成 Basic 等於讓偵測瞎掉，違反「不得削弱分析規則」的條件。
  • C：Sentinel 工作區的 Analytics 資料表本來就含 90 天免費互動保留，縮到 30 天並不會產生任何節省，卻會讓調查可用的歷史資料變少。

QUESTION 5 · D1-0045
Your organization keeps proxy and firewall logs in Microsoft Sentinel purely as compliance evidence. The tables are queried a handful of times a year, they are never used by scheduled analytics rules, and simple single-table filtering is sufficient when they are queried. Which table plan provides the lowest ingestion price for these tables?
（貴組織把 Proxy 與防火牆記錄留在 Microsoft Sentinel 純粹是為了合規舉證：這些資料表一年只查幾次，從不被排程分析規則使用，查詢時只需單表簡單篩選即可。哪一種表方案（table plan）能為這些資料表提供最低的擷取單價？）
A. Analytics
Analytics（分析）
B. Basic
Basic（基本）
C. Auxiliary
Auxiliary（輔助）
D. Analytics with a daily commitment tier discount
Analytics 加上每日承諾層級折扣
看正解與解析
正解：C

三種表方案對應三種資料性質：Analytics 給即時偵測與調查的高價值訊號、Basic 給中價值且偶爾調查的高量記錄、Auxiliary 給「詳細（verbose）、低價值、幾乎只為合規留存」的記錄。題幹三個條件——一年只查幾次、不參與分析規則、單表篩選就夠——完全命中 Auxiliary 的設計用途，其擷取單價在三者中最低。若日後仍需要偵測面，可用 summary rules 把聚合結果送回 Analytics 表。

  • A：Analytics 是三者中擷取單價最高的方案，設計給要餵排程分析規則、跨表關聯查詢的高價值安全訊號，用在一年查幾次的合規資料是浪費預算。
  • B：Basic 比 Analytics 便宜，但仍高於 Auxiliary，設計對象是「中價值、偶爾會拿來調查」的高量記錄；純合規留存的資料還有更便宜的一層可選。
  • D：承諾層級是針對整個工作區每日擷取量的折扣機制，並不會改變單一資料表的方案與單價，也無法把 Analytics 的價格壓到 Auxiliary 的水準。
