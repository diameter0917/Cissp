01 — 📌 本日導讀

搜捕的三個新軸：關係、規模、時間 2026 新考點

第五週第四天，整個單元都是 2026-07-28 考綱更新才長出來的新地。前三天你已把搜捕的傳統工法練熟——假說、KQL、書籤、Livestream、MITRE ATT&CK 對應。今天要看的是三個正在把搜捕工作流換掉的能力：Sentinel Graph 把實體與關係建成圖，讓你問「誰連到誰」；Sentinel MCP Server 用標準協定把 Sentinel 的資料與工具開放給 AI 代理，讓自然語言調查與代理式搜捕（agentic hunting）成真；data lake 進階搜捕把時間軸拉到一年以上，新的入侵指標（IoC）一到手就能回頭掃歷史。三者是同一件事的三個面向：圖負責關係、代理負責規模、湖負責時間。這類新功能題通常停在概念與適用場景層級——考你分辨哪種問題該用哪種工具，而不是背按鈕路徑。

03 — 🕸️ Sentinel Graph

從表格思維換成圖思維 2026 新考點

過去五週你所有的查詢都是表格思維：用 where 篩、summarize 算、join 併，擅長回答「有沒有、幾次、什麼時候」。但 SOC 真正卡住的問題長這樣：「這個被釣魚的帳號，順著它能走到哪台伺服器？」「這台淪陷的裝置往外還碰得到誰？」——這些是關係問題。

Sentinel Graph 把安全資料重新組織成一張圖：節點是實體（使用者、裝置、檔案、IP、信箱、雲端資源、權限指派），邊是關係與行為（登入了、執行了、外連了、擁有、可存取）。圖建好之後，兩種問題突然可以直接問：

  • 攻擊路徑（attack path）：從一個立足點（暴露的資產、被盜的帳號）出發，攻擊者可能沿著哪條關係鏈走到高價值目標。這是「往前看」的推演。
  • 爆炸半徑（blast radius）：反過來問，這個已確定被入侵的實體往外能觸及多大範圍——哪些帳號共用憑證、哪些資源它有權限。這是回應決策（隔離到什麼程度、重設哪些密碼）的直接依據。

為什麼表格做不到？因為多跳（multi-hop）。從帳號到裝置到伺服器到資料，每多一跳就多一個 join，而且你得事先知道要跳幾次。圖查詢把「跳」變成語意：KQL 的圖語意運算子（make-graph 建圖、graph-match 比對路徑樣式）讓你描述可變長度的路徑，一次問完「任意幾跳內連得到的所有目標」。

💡 一句話分工：表格回答「發生了什麼」，圖回答「誰連到誰、還會波及誰」。兩者互補不是取代——先用表格查詢找到起點，再用圖把起點展開成路徑與範圍。
🎯 考點聚焦：什麼時候該選 Graph

題幹關鍵字直接對映：出現「lateral movement path／which assets could an attacker reach／who has access to this resource／blast radius」→ Sentinel Graph 的關聯與路徑分析。出現「how many times／list all sign-ins in the last 24 hours」→ 一般 KQL 表格查詢。兩個陷阱：①把「實體圖上的單一事件關聯視圖」當成攻擊路徑分析的答案——它給的是這次調查的相鄰訊號，不是跨環境的路徑推演；②看到「圖」就選 Graph，但題幹其實一次 join 就能回答——最佳答案永遠是剛好夠用的工具。

05 — 🤖 Sentinel MCP Server

讓 AI 代理接得上 SOC 資料 2026 新考點

Model Context Protocol（MCP）是讓 AI 代理連接外部資料與工具的開放標準協定，解決整合的組合爆炸：過去每個 AI 助手接每個系統都得寫專用整合；有了 MCP，資料源那側架一台 MCP server 把能力包成標準化的「工具」，任何支援 MCP 的代理（Security Copilot、VS Code 裡的 Copilot、自寫的代理）都能直接用。

Sentinel MCP Server 就是 Sentinel 這側的標準門面，把資料探索與搜捕能力開放給代理：探索有哪些資料表與結構描述、依自然語言意圖產生並執行 KQL、查詢 data lake 資料、取得實體脈絡。落到 SOC 場景是三件事：

  • 自然語言驅動的調查：分析師問「過去 90 天哪些帳號從新國家登入、之後又存取財務共用資料夾」，代理自己找表、組 KQL、執行、整理結果，人力留給判斷。
  • 代理式搜捕（agentic hunting）：代理不只答一題，而是跑完整個搜捕迴圈——提假說、查證、依結果修正再查一輪，最後把值得升級的發現整理成書籤或事件交給人。
  • 開發與搜捕的副手：如 EP10 示範，在 VS Code 筆記本裡接上 MCP server，寫查詢、探索湖中資料、驗證邏輯都在同一介面完成。

權限與稽核是考點核心。代理透過 MCP 存取資料時，是以呼叫者的 Microsoft Entra ID 身分驗證與授權（EP10 的設定流程就是用公司帳號登入並同意授權），因此代理看不到該身分本來就看不到的資料，RBAC 與最小權限仍是主要防線。風險也就很明確：給代理用的身分若權限開太大，等於把整份 SOC 資料交給一個會自己下查詢的程式。代理發出的查詢仍留稽核軌跡，而生成式輸出必須由人覆核——它可能寫出語法對但語意錯的查詢，或從不足的證據過度推論。

🎯 考點聚焦：MCP 題的兩種問法

問法一（用途）：「要讓自訂 AI 代理／Security Copilot 以標準化方式存取 Sentinel 資料與搜捕工具，應該用什麼？」→ Sentinel MCP Server。干擾項很像：劇本（Playbook）是自動化回應流程、不是給代理查資料的協定；REST API 做得到，但要為每個代理自寫整合，正是 MCP 要取代的；資料連接器是把資料收進 Sentinel，方向相反。

問法二（治理）：「導入代理式搜捕時，如何確保代理不會存取不該看的資料？」→ 答案永遠是「代理繼承呼叫者身分，以 Entra ID 與 RBAC 最小權限控管，保留稽核並由人覆核輸出」。標準錯誤選項是「另建高權限服務帳號給代理用」與「靠提示詞限制代理別查敏感資料」——前者放大爆炸半徑，後者不是存取控制。

06 — 🕰️ 湖上的回溯獵捕

新 IoC 到手，回頭掃一年 2026 新考點

回溯獵捕（retro-hunting）是很具體的動作：威脅情報發布新 IoC（網域、雜湊、C2 位址），你回頭問「我們過去有沒有碰過它」。難處在時間——分析層互動保留常只有 90 天，入侵駐留數個月卻是常態，最該回答的問題偏偏落在保留期外。data lake 解除了這個限制：全量資料低成本留在湖裡（最長 12 年）且直接可查，不必先還原。先用互動查詢探路：

// Lake 互動查詢：新收到的 C2 網域，過去 12 個月有沒有人解析過
let NewIoCs = dynamic(["cdn-sync.badhost.example", "ota-update.badhost.example"]);
DeviceNetworkEvents
| where TimeGenerated between (ago(365d) .. now())
| where RemoteUrl has_any (NewIoCs)
| summarize Hits = count(), FirstSeen = min(TimeGenerated), LastSeen = max(TimeGenerated)
          by DeviceName, RemoteUrl, InitiatingProcessFileName
| order by FirstSeen asc
逐行解說：let 把情資清單抽成變數，換一批 IoC 只改一行。between (ago(365d) .. now()) 是回溯的核心——這段時間窗遠超分析層保留，只有湖查得到；但湖按用量計費，時間窗要有意識地收。has_any 一次比對整份清單。summarize 收斂出三個關鍵答案：哪台裝置、第一次出現在什麼時候（定位入侵起點）、由哪個處理程序發起。order by FirstSeen asc 讓最早那列排最上面——通常就是「零號病人」。

互動查詢適合「先看有沒有」。一旦確認這批 IoC 值得持續監控，就把它變成排程 KQL job，讓結果升階（promote）回分析層——分析規則只讀分析層，湖裡的發現不回去就無法觸發偵測：

// KQL job（每日排程，結果升階至分析層自訂資料表 RetroHuntIoC_CL）
let NewIoCs = dynamic(["cdn-sync.badhost.example", "ota-update.badhost.example"]);
DeviceNetworkEvents
| where TimeGenerated > ago(1d)
| where RemoteUrl has_any (NewIoCs)
| join kind=inner (
    DeviceLogonEvents
    | where TimeGenerated > ago(1d)
    | project DeviceName, AccountName, LogonTime = TimeGenerated
  ) on DeviceName
| project TimeGenerated, DeviceName, AccountName, RemoteUrl,
          InitiatingProcessFileName, LogonTime
逐行解說：KQL job 支援完整 KQL（join、summarize 都能用，這點與受限 KQL 的 search job 不同），所以這裡把命中的裝置 join 回登入記錄，直接產出「哪台裝置、哪個帳號、連到哪個 C2」。project 出的欄位就是升階後寫入分析層自訂資料表的結構——資料一落到分析層，你就能建分析規則、產生事件、走正常分診流程。鐵律：湖裡撈到的魚，要放回分析層才能上菜。
💡 成本與時間取捨三原則：①先窄後寬——先用一週驗證查詢寫得對再放大到一年；②先探後排——一次性用互動查詢，確定要長期看才排程；③只留要用的欄位——升階回分析層要付擷取費。
🧪 實戰情境：一封情資信件引發的回溯獵捕

週二早上，ISAC 發布一批供應鏈攻擊相關 IoC：兩個 C2 網域、三個檔案雜湊。環境已接入 Sentinel data lake，端點與網路記錄在湖層保留 12 個月。

  1. 先問時間（湖）：跑上面那段互動查詢，時間窗設過去 12 個月。結果：一台開發用筆電在七個月前解析過其中一個網域三次——遠在分析層保留期外，沒有湖就永遠不會被發現。
  2. 再問關係（圖）：拿這台裝置當起點做爆炸半徑評估——它登入過哪些帳號、那些帳號有哪些權限、順著權限鏈能走到哪些伺服器。圖指出其中一個帳號在某台檔案伺服器有寫入權，這條路徑決定了接下來查什麼、要不要提前重設密碼。
  3. 再問規模（MCP／代理）：把「同樣行為樣式，環境裡還有沒有第二台」交給代理式搜捕，讓它依假說在湖上跑多輪查詢，你專心處理已知那台。
  4. 保存與升階：關鍵結果存成書籤並對應實體以接進事件調查；同時建立每日排程 KQL job，把命中升階回分析層自訂資料表並建分析規則——之後再有裝置碰到這批 IoC 會直接變成事件進佇列，不必等下一封情資信。
  5. 回頭看：湖負責「七個月前」，圖負責「還有誰會被波及」，代理負責「其他地方還有沒有」——三個新能力各補上傳統搜捕的一個缺口。
07 — 🧩 考綱補洞

影片沒講的：Graph 的定位、預覽期心態與治理

  • Sentinel Graph 與既有「圖」怎麼分：你早看過兩種——調查中的實體圖（entity graph）把單一事件相關的實體與訊號攤開（EP10 20:59 就是它），以及曝險管理的攻擊路徑分析，側重「由資產設定與弱點推導出可能被走的路」。Sentinel Graph 的新意在建於 data lake 之上：吃長期全量的活動與關係資料，能把「設定上的可達性」與「實際發生過的行為」放進同一張圖。這幾個選項同時出現時，看題幹要的是單一事件的鄰居還是跨環境的路徑範圍。
  • 三者合起來改變了什麼：傳統搜捕是「假說 → 寫 KQL → 看結果 → 存書籤」的手工迴圈，受限於 KQL 熟練度與保留期長度。新工作流是湖給時間、圖給關係、代理給規模，人負責定義假說、驗證證據、決定升級。人沒被拿掉，位置往上移了。
  • 預覽期功能的應試心態：這三項都還在快速演進，介面與計費細節可能已經變了，因此考題停在能力與場景層級——問「哪個功能適合這個需求」，不問「按鈕在第幾層選單」。請記能力邊界（誰能餵偵測、誰吃長期資料、誰用什麼身分），別背 UI 路徑或價格。
  • 治理與成本不會因新工具消失：湖上的互動查詢、KQL jobs、筆記本都按用量計費，代理式搜捕更可能在無人盯著時放大用量。「誰能在湖上跑 job、範圍多大」是情境題最愛藏的取捨條件。
  • 舊工具沒被取代：書籤、Livestream、search job、還原（restore）仍是 D3 考點，常跟新工具擺同一題當干擾項。判準很單純：一次性大範圍撈記錄→ search job；需要 join 的歷史分析且要餵偵測→ KQL job；即時驗證假說→ Livestream；關係與路徑→ Graph。

QUESTION 1 · D3-0026
You are a security operations analyst. Threat intelligence confirms that a privileged user account in your tenant has been compromised. Before deciding how aggressively to contain, you must determine which devices, resources, and other accounts that identity could reach through its existing relationships and permissions. Which Microsoft Sentinel capability is designed for this assessment?
（你是資安維運分析師。情報確認租用戶中一個具權限的使用者帳號已遭入侵。在決定要隔離到什麼程度之前，你必須先評估這個身分透過既有關聯與權限「往外能觸及」哪些裝置、資源與其他帳號。哪一項 Microsoft Sentinel 能力是為這種評估而設計的？）
A. Sentinel Graph, which models entities and their relationships to support attack path and blast radius analysis.
Sentinel Graph：把實體與彼此的關係建成圖，支援攻擊路徑（attack path）與爆炸半徑（blast radius）分析。
B. A summary rule that aggregates the account's sign-in records into a custom table every hour.
建立 summary rule，每小時把該帳號的登入記錄彙總寫入自訂資料表。
C. A hunting livestream session that watches for new events generated by the account.
開啟搜捕 Livestream 工作階段，監看該帳號產生的新事件。
D. A search job that retrieves every historical record containing the account name.
執行 search job，撈出所有含該帳號名稱的歷史記錄。
看正解與解析
正解：A

「這個已被入侵的實體往外能碰到什麼」就是爆炸半徑（blast radius）問題，屬於典型的關係型提問。Sentinel Graph 把使用者、裝置、檔案、IP、權限指派等實體建成節點，把登入、執行、可存取等行為與關係建成邊，因此能一次展開多跳的可達範圍，直接支撐「要隔離到什麼程度、要重設哪些密碼」的回應決策。表格型查詢要回答同樣的問題必須逐層 join，且得事先知道跳幾次。

  • B：summary rule 是把持續流入的高量資料彙總成摘要表供偵測與儀表板使用，解決的是成本與統計面的問題，不會告訴你實體之間的可達路徑。
  • C：Livestream 是對「即將發生」的事件即時驗證假說，方向是向前看的監看，無法評估既有關聯所形成的觸及範圍。
  • D：search job 適合在巨量或長期資料中一次性撈出符合條件的記錄，產出的是事件清單而非關係圖；它回答「出現過幾次」，不回答「還會波及誰」。

QUESTION 2 · D3-0027
During a purple team exercise you must determine whether an attacker who lands on an internet-facing virtual machine could eventually reach a domain administrator account. The number of intermediate hops is unknown, the answer must cover any chain of identities, devices, and permissions, and the SOC does not want to maintain a query that has to be rewritten each time a hop is added. What is the best approach?
（在一次紫隊演練中，你必須判斷「攻擊者若拿下一台對外的虛擬機，是否最終能走到網域管理員帳號」。中間會經過幾跳並不確定，答案必須涵蓋任何由身分、裝置與權限組成的關係鏈，而且 SOC 不想維護一條每多一跳就要改寫的查詢。最佳做法是什麼？）
A. Write an advanced hunting query that chains several join operators, one per expected hop.
在進階搜捕中寫一條查詢，用多個 join 運算子串接，每一跳寫一個 join。
B. Enable UEBA and review the anomaly score of the exposed virtual machine.
啟用 UEBA，檢視這台對外虛擬機的異常分數。
C. Build a workbook that visualizes sign-in volume per device and per privileged account.
建立活頁簿（Workbook），將每台裝置與每個特權帳號的登入量視覺化。
D. Use Sentinel Graph and express the question as a variable-length path pattern over entities and relationships.
使用 Sentinel Graph，把問題寫成跨實體與關係的可變長度路徑樣式。
看正解與解析
正解：D

題幹的三個條件——跳數未知、要涵蓋任意關係鏈、不想每次改查詢——正好是圖查詢存在的理由。Sentinel Graph 以節點（實體）與邊（關係與行為）表達環境，路徑樣式比對可描述「任意幾跳之內」的可達性，一次問完整條攻擊路徑（attack path），不必為每一跳維護一個 join。這也是「往前看」的推演，與爆炸半徑的「往外看」互為一組。

  • A：多重 join 正是題幹要避免的做法：查詢會隨跳數線性增長且難以維護，更關鍵的是你必須事先知道要跳幾次，無法回答跳數未知的問題。
  • C：活頁簿負責視覺化既有統計，呈現的是量與趨勢，不會推演實體之間是否存在可行的橫向移動路徑。
  • B：UEBA 針對單一實體給出行為異常評分，回答「這個實體是否可疑」，不回答「從這裡能不能走到網域管理員」。

QUESTION 3 · D3-0028
Your SOC wants an AI agent to discover available tables, generate KQL, and query Microsoft Sentinel data through a standard protocol, without writing a custom integration for every agent. Which component provides this?
（你的 SOC 希望讓 AI 代理透過標準協定探索可用的資料表、產生 KQL 並查詢 Microsoft Sentinel 資料，而不必為每一個代理各寫一套自訂整合。應該使用哪一個元件？）
A. A data connector for the agent platform.
為代理平台建立一個資料連接器。
B. A Logic Apps playbook triggered by an automation rule.
由自動化規則觸發的 Logic Apps 劇本（Playbook）。
C. The Microsoft Sentinel MCP (Model Context Protocol) server.
Microsoft Sentinel MCP（Model Context Protocol）伺服器。
D. A workbook published to the Defender portal.
發布到 Defender 入口網站的活頁簿（Workbook）。
看正解與解析
正解：C

Model Context Protocol（MCP）是讓 AI 代理以統一方式連接外部資料與工具的開放標準。Sentinel MCP server 是 Sentinel 這一側的標準門面，把結構描述探索、KQL 產生與執行、data lake 資料查詢等能力包成代理可呼叫的工具，任何支援 MCP 的用戶端（Security Copilot、VS Code 中的 Copilot、自訂代理）都能直接使用，免除逐一自寫整合。

  • A：資料連接器負責把外部資料「收進」Sentinel，方向與本題相反；本題要的是讓外部代理讀取 Sentinel 的資料。
  • B：劇本（Playbook）是以 Logic Apps 執行的自動化回應流程，用來做通知、封鎖、擴充等動作，不是供代理查詢資料的協定介面。
  • D：活頁簿是給人看的視覺化儀表板，無法作為 AI 代理程式化存取資料與工具的標準介面。

QUESTION 4 · D3-0029
Your organization is piloting agentic hunting: analysts ask questions in natural language and an AI agent connects to Microsoft Sentinel to run the resulting queries. Management asks how you will guarantee that the agent cannot read data the requesting analyst is not allowed to see. What should you rely on?
（你的組織正在試行代理式搜捕（agentic hunting）：分析師用自然語言提問，AI 代理連到 Microsoft Sentinel 執行產生的查詢。管理層詢問你要如何確保代理無法讀取提問分析師本來就無權查看的資料。你應該依靠什麼？）
A. Create a dedicated service account with tenant-wide read permissions for the agent to use.
為代理另建一個具租用戶全域讀取權限的專用服務帳號。
B. Add instructions to the agent's prompt telling it not to query sensitive tables.
在代理的提示詞中加入指示，要求它不要查詢敏感資料表。
C. Move all sensitive tables to the data lake tier, since agents only query the analytics tier.
把所有敏感資料表移到 data lake 層，因為代理只會查詢分析層。
D. The agent authenticating with the caller's Microsoft Entra ID identity, so existing RBAC and least privilege apply, combined with audit review of the queries it runs.
代理以呼叫者的 Microsoft Entra ID 身分驗證，因此既有的 RBAC 與最小權限仍然生效，再搭配對其查詢的稽核檢視。
看正解與解析
正解：D

透過 MCP 存取 Sentinel 時，代理是以呼叫者的 Entra ID 身分進行驗證與授權，因此它能看到的資料上限就是該身分本身的 RBAC 範圍——存取控制依然由角色指派與最小權限決定，代理的查詢也會留下稽核軌跡供事後檢視。實務上真正的風險是「給代理使用的身分權限開得過大」，所以治理重點在身分權限本身，而不是額外發明一層限制。

  • A：另建高權限服務帳號會讓代理的可視範圍遠超提問者，正好放大爆炸半徑，與題目要求相反，也違反最小權限原則。
  • B：提示詞是行為引導而非存取控制，無法在技術上阻擋資料讀取；一旦身分本身有權限，任何提示層的約束都可能被繞過。
  • C：資料層的選擇是為了成本、保留與偵測需求，不是權限邊界；湖層資料同樣可被有權限的身分查詢，把敏感資料搬層並不會形成隔離。

QUESTION 5 · D3-0030
An intelligence feed publishes a list of newly attributed command-and-control domains. Your workspace is onboarded to Microsoft Sentinel data lake, where nine months of network telemetry is retained. You must check the historical data every day against the evolving list, correlate hits with logon records, and make sure any hit can raise an incident through an analytics rule. What should you implement?
（情資來源發布了一批新歸因的命令與控制（C2）網域。你的工作區已接入 Microsoft Sentinel data lake，其中保留了九個月的網路遙測資料。你必須每天以持續更新的清單比對歷史資料、將命中結果與登入記錄關聯，並確保任何命中都能透過分析規則產生事件。你應該實作什麼？）
A. A one-time search job over the historical data, reviewing the resulting _SRCH table manually.
對歷史資料執行一次性的 search job，再人工檢視產生的 _SRCH 資料表。
B. A scheduled KQL job on the data lake that joins the hits with logon records and promotes the results to a custom table in the analytics tier.
在 data lake 上建立排程 KQL job，將命中結果與登入記錄 join，並把結果升階（promote）到分析層的自訂資料表。
C. A summary rule that aggregates network telemetry hourly into a custom table.
建立 summary rule，每小時把網路遙測彙總寫入自訂資料表。
D. Restore the historical data into the analytics tier and run a hunting query against it whenever the feed is updated.
把歷史資料還原（restore）到分析層，每次情資更新時對它執行搜捕查詢。
看正解與解析
正解：B

題幹同時出現三個訊號：資料在 data lake、需要每天定期執行、命中結果必須能被分析規則使用。三者同時成立時答案就是排程 KQL job 加升階（promote）。KQL job 支援完整 KQL，因此可以在湖上直接 join 登入記錄；而分析規則只讀分析層，所以結果必須升階寫入分析層自訂資料表，之後才能建立規則、產生事件並進入正常分診流程。

  • A：search job 是一次性的大範圍搜尋，KQL 能力受限（以篩選為主，不利於 join），且結果落在 _SRCH 資料表供人工檢視，無法滿足「每天執行並自動觸發偵測」的需求。
  • C：summary rule 只會從啟用之後向前持續彙總，回不了頭去掃已經存在的九個月歷史資料，也不是為比對 IoC 清單而設計的。
  • D：還原是舊架構下處理封存資料的做法，成本與作業負擔都高；工作區已接入 data lake 時可直接查詢湖中資料，不需先還原，而且每次手動重跑也達不到排程與自動升階的效果。
