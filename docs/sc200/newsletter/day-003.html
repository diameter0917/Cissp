03 — 🔗 join 全家桶

join 全家桶：六種 kind 一次分清楚

join 的語法骨架是：左表 | join kind=種類 (右表) on 鍵——把左右兩張表依鍵值橫向拼接，輸出「欄位變多」的結果。考試最愛考的就是 kind 的選擇，先把這張表刻進腦裡：

kind輸出行為什麼時候用搜捕情境例
innerunique（預設）左表鍵值先去重，每個鍵只留一列去配右表；配得到才輸出只想知道「有哪些鍵有配對」、不在乎左表重複列快速確認哪些帳號同時出現在兩張表
inner左右所有配對組合都輸出（笛卡兒式配對）每一筆配對都要保留、要做逐筆關聯分析高風險登入 × 稽核操作逐筆對齊（見下方查詢）
leftouter左表全留；配不到的右表欄位補空值以左表為主，順便帶出右表資訊（有就填、沒有留白）裝置清單左表＋警示數右表，沒警示的裝置也要列
leftsemi只留「配得到」的左表列，右表欄位不輸出右表只當「過濾清單」用只看命中 IoC 清單的連線紀錄本身
leftanti只留「配不到」的左表列找「存在於左、不存在於右」的落差有登入紀錄但不在 MFA 已註冊清單的帳號
fullouter左右全留，配不到的互補空值兩邊都不能漏的完整對帳兩個資料來源的資產盤點差異比對
⚠️ 頭號陷阱：不寫 kind 時預設是 innerunique，不是 inner！左表同一鍵值的重複列會先被去重（隨機留一列）再配對，所以筆數可能比你預期少。搜捕查詢要逐筆關聯時，請明確寫出 kind=inner，不要靠預設。

join 效能三原則（官方 best practices，考試與實務都會用到）：① 小表放左邊——左表是驅動表，越小越快；② 先過濾再 join——where、project 盡量寫在 join 之前，兩邊都先瘦身；③ 鍵名不同時用 $left.欄位 == $right.欄位 明確對應。實戰看這段：

// 情境：高風險登入後 1 小時內，同帳號是否做了敏感的目錄變更？
let lookback = 1d;
let RiskySignins = SigninLogs
    | where TimeGenerated > ago(lookback)
    | where RiskLevelDuringSignIn == "high"
    | project SigninTime = TimeGenerated, UserPrincipalName, IPAddress;
RiskySignins
| join kind=inner (
    AuditLogs
    | where TimeGenerated > ago(lookback)
    | where Category == "UserManagement"
    | extend Actor = tostring(InitiatedBy.user.userPrincipalName)
    | project AuditTime = TimeGenerated, Actor, OperationName
) on $left.UserPrincipalName == $right.Actor
| where AuditTime between (SigninTime .. (SigninTime + 1h))
| project UserPrincipalName, IPAddress, SigninTime, OperationName, AuditTime

逐行解說：let lookback = 1d 把回看窗取名成變數，之後改一處全查詢生效；RiskySignins 用 let 存成「已過濾、已投影」的小左表（原則①②）；join kind=inner 明確要求逐筆配對；右表 AuditLogs 同樣先 where＋project 瘦身，並用 tostring(InitiatedBy.user.userPrincipalName) 從 dynamic 欄位取出操作者（下文 05 節會講）；on $left... == $right... 處理兩表鍵名不同；最後 between 限制稽核操作發生在登入後 1 小時內——時間窗條件是登入關聯查詢的靈魂，沒有它會撈到大量不相關配對。

🎯 考點聚焦
join kind 選擇題的關鍵字解題法：題幹說「找出沒有出現在另一張表的紀錄」「識別未註冊／未回報的對象」→ leftanti；「只要左表原始列、右表僅當過濾條件」→ leftsemi；「左表全部保留、沒配到的補空白」→ leftouter；「每筆配對都要」→ inner。若選項同時出現 inner 與 innerunique，回頭看題幹是否強調「重複紀錄也要各自配對」——要就選 inner。
04 — 🧺 union 與跨表狩獵

union 與跨表狩獵：縱向疊表找 IoC

join 是「橫向拼欄位」，union 則是「縱向疊資料列」：把多張結構相近（或不相近也行）的表上下疊成一張，欄位取聯集。拿到一個檔案雜湊、一個 IP 這類 IoC（入侵指標）時，你不會知道它藏在哪張表，union 就是跨表撒網的標準起手式：union withsource=SrcTable DeviceProcessEvents, DeviceNetworkEvents, DeviceFileEvents | where SHA256 == "..." or InitiatingProcessSHA256 == "..."。兩個必記參數：withsource=欄名 會多出一欄標記「這列來自哪張表」，命中時一眼定位資料來源；表名支援萬用字元，union Device* 一口氣涵蓋所有 Device 開頭的表；另外 isfuzzy=true 允許清單中某張表不存在時查詢照樣執行（跨環境共用查詢時很實用）。

🔍 SOC 實戰：identity＋device＋email 的橫向移動調查

情境：MDO（Microsoft Defender for Office 365）回報一波網釣郵件已送達多名使用者。你懷疑有帳號中招後被拿去橫向移動（lateral movement）。調查思路：郵件表找出受害名單 → 身分登入表看這些帳號登了哪些裝置 → 端點登入表關聯遠端登入行為 → 聚合出「短期內碰過多台裝置」的帳號：

// Step 1：收過網釣郵件且已送達的收件者名單
let lookback = 3d;
let PhishedUsers = EmailEvents
    | where Timestamp > ago(lookback)
    | where ThreatTypes has "Phish" and DeliveryAction == "Delivered"
    | distinct RecipientEmailAddress;
// Step 2：這些帳號的網域登入（identity 訊號）
IdentityLogonEvents
| where Timestamp > ago(lookback)
| where AccountUpn in~ (PhishedUsers)
// Step 3：關聯端點遠端登入（device 訊號）
| join kind=inner (
    DeviceLogonEvents
    | where Timestamp > ago(lookback)
    | where LogonType == "RemoteInteractive"
    | project DeviceName, AccountName
) on DeviceName
// Step 4：聚合——短期內碰過 3 台以上裝置的帳號優先調查
| summarize TouchedDevices = make_set(DeviceName), Logons = count() by AccountUpn
| where array_length(TouchedDevices) >= 3
| order by Logons desc

逐行解說：let PhishedUsers = ... | distinct ... 把受害者名單存成可重用清單（let 也能存表格結果）；in~ 是不分大小寫的清單比對，跨資料來源比對 UPN 時務必用它；join 端點登入表把身分訊號與裝置訊號接起來；make_set() 把每個帳號碰過的裝置收成「去重陣列」（若要保留出現順序與重複用 make_list()）；array_length() >= 3 是搜捕假說的門檻——一個帳號三天內遠端登入三台以上裝置，值得開單調查。這就是考綱說的「跨資料來源搜捕威脅」的典型長相。

05 — ⚗️ parse 家族

parse 家族：欄位煉金術

很多高價值資訊藏在「一整串字串」或 JSON 欄位裡——syslog 原文、命令列參數、AdditionalFields。parse 家族就是把它們煉成可 where、可 summarize 的欄位：

工具做什麼典型寫法
parse依「文字樣板」切割字串，一次抽多個欄位| parse SyslogMessage with * "user " User " from " SrcIp " port" *
extract()用正規表示式抽第一個符合的片段| extend Ip = extract(@"(\d+\.\d+\.\d+\.\d+)", 1, RawLog)
extract_all()抽出所有符合片段成陣列| extend AllIps = extract_all(@"(\d+\.\d+\.\d+\.\d+)", RawLog)
parse_json()／todynamic()把 JSON 字串轉成 dynamic 物件，才能用 .屬性 取值（兩者同義）| extend AF = todynamic(AdditionalFields) | extend Status = tostring(AF.SigningStatus)
split()依分隔符切成陣列，用索引取段| extend Domain = tostring(split(AccountUpn, "@")[1])
⚠️ 最常踩的坑：欄位「長得像 JSON」不代表「是 dynamic」。schema 裡型別是 string 的欄位（如部分表的 AdditionalFields），直接寫 AdditionalFields.SigningStatus 只會拿到空值——必須先 todynamic() 轉型再取屬性；取完屬性通常再用 tostring()／tobool()／toint() 轉回純量型別，才能拿去比對與聚合。反之像 SigninLogs 的 InitiatedBy、DeviceDetail 本身就是 dynamic，可直接點下去。判斷方法：查詢編輯器左側 schema 樹會標欄位型別。

選擇心法：格式固定、肉眼可見樣板 → 用 parse 最快；格式多變、需要模糊比對 → 用 extract() 正規表示式；JSON → 一律 todynamic()。正規表示式效能成本最高，能用 parse 或 has／contains 先縮小範圍就別讓 regex 掃全表。

06 — 🧲 let、arg_max 與去重

let、arg_max 與去重：每個實體只看最新一筆

let 除了存常數與清單，還能定義可重用函式：let toUpn = (name:string) { strcat(name, "@contoso.com") };——團隊共用的搜捕查詢庫幾乎都靠 let 組裝。而搜捕裡最常見的需求之一是「每台裝置／每個帳號只要最新一筆」：裝置目前登入者是誰？帳號最後一次成功登入在哪？這時用 arg_max()：

// 每台裝置「最新一筆」互動式登入＋解析 AdditionalFields
DeviceLogonEvents
| where Timestamp > ago(7d)
| where LogonType == "Interactive" and ActionType == "LogonSuccess"
| extend IsLocal = tobool(todynamic(AdditionalFields).IsLocalLogon)
| summarize arg_max(Timestamp, *) by DeviceId
| project Timestamp, DeviceName, AccountName, IsLocal

逐行解說：先把範圍縮到 7 天內的成功互動式登入；todynamic(AdditionalFields).IsLocalLogon 示範上一節的欄位煉金——字串轉 dynamic 再取屬性、tobool() 收尾；重點是 summarize arg_max(Timestamp, *) by DeviceId：每個 DeviceId 分一組，在組內找 Timestamp 最大（最新）的那一列，星號 * 表示「把那一列的所有欄位整列帶出來」。反向需求（最早一筆、首次出現）用 arg_min()——找「這個帳號第一次登入這台裝置是什麼時候」就是它。

🎯 考點聚焦
arg_max(Timestamp, *) vs max(Timestamp)：前者回傳「時間最新的那一整列」（含所有欄位），後者只回傳「最大的時間值」本身、其他欄位全丟失。題目若要「最新紀錄的完整內容／該次登入的帳號與 IP」，答案一定是 arg_max；選項出現 top 1 by Timestamp 也能達成單一實體的需求，但「每個裝置各取最新一筆」只有 summarize arg_max(...) by 實體 做得到。
07 — 📈 時間序列異常

時間序列異常：讓統計幫你盯基線

人工盯儀表板找異常不可靠，KQL 內建時間序列分析讓統計代勞。兩步驟：make-series 把事件變成「等間隔的數列」，series_decompose_anomalies() 把數列拆解成基線＋季節性＋殘差，並標出異常點：

// 找出「登入失敗次數」出現異常尖峰的帳號
let lookback = 14d;
SigninLogs
| where TimeGenerated > ago(lookback)
| where ResultType != 0          // 只看失敗登入
| make-series FailedCount = count() default = 0
    on TimeGenerated from ago(lookback) to now() step 1h
    by UserPrincipalName
| extend (Anomalies, Score, Baseline) =
    series_decompose_anomalies(FailedCount, 2.5, -1, 'linefit')
| mv-expand TimeGenerated to typeof(datetime),
    FailedCount to typeof(long), Anomalies to typeof(int)
| where Anomalies == 1
| project TimeGenerated, UserPrincipalName, FailedCount

逐行解說：make-series 以每小時（step 1h）為一格、對每個帳號（by）產生 14 天的失敗次數數列，default = 0 讓沒事件的時段補 0——這步不可省，缺格的數列會讓分解失真；series_decompose_anomalies() 三個關鍵參數：門檻 2.5（分數超過即標異常，預設 1.5，調高＝更嚴格更少誤報）、季節性 -1（自動偵測週期，例如上班日的日週期）、'linefit'（趨勢用線性擬合）；輸出三個「與時間格對齊的陣列」——Anomalies 每格是 1（正向異常）／0（正常）／-1（負向異常）；因為 make-series 的輸出是「一列一帳號、欄位裝陣列」，要用 mv-expand 展回一列一時段，才能 where Anomalies == 1 篩出異常時點。想先目視再篩選，把最後三行換成 | render timechart。

💡 summarize count() by bin(TimeGenerated, 1h) 與 make-series 都是時間分桶，差別在：summarize 輸出「一列一桶、缺桶就沒列」，make-series 輸出「等間隔完整數列（缺桶補 default）」——所有 series_* 函式都只吃後者。題目看到 series_decompose、序列預測，前面必配 make-series。
08 — 🧩 考綱補洞

考綱補洞：影片沒講、考試會考的 KQL 進階點

EP6 聚焦查詢語法本身，但考綱把 KQL 埋進 Sentinel 與 Defender XDR 的各個角落，這些「語法之外的規則」影片不會講：

  • NRT（近即時）分析規則的 KQL 限制：NRT 規則走簡化執行路徑，官方文件明列查詢只能參照單一資料表，不支援 union／join 跨表、也不支援跨工作區查詢——「需要跨表關聯的偵測」就得用排程（scheduled）規則。這是規則類型選擇題的高頻陷阱。
  • 排程分析規則：查詢回看範圍上限 14 天；單次執行最多產生 150 個警示，超過會截斷——寫 join 產出大量配對列時要先聚合再輸出。
  • Defender XDR 自訂偵測（custom detection）：進階搜捕查詢要轉成自訂偵測規則，結果必須包含 Timestamp、ReportId 與至少一個可對應實體的識別欄位（如 DeviceId、AccountObjectId）——用了 summarize 之後這些欄位常常被聚合掉，記得用 arg_max(Timestamp, *) 這類寫法把它們帶回結果。
  • externaldata()：直接從外部儲存體（如 Azure Blob 的 CSV/JSON）把資料讀進查詢當表用——externaldata(Ip:string) [@"https://.../ioc.csv"]，適合臨時比對外部 IoC 清單；若清單需要長期維護、給分析規則引用，考試的正解通常是監視清單（Watchlist）（查詢時用 _GetWatchlist('別名')），兩者的取捨要分清楚。
  • 效能工具：materialize() 把 let 子查詢結果快取，避免同一段子查詢被多次執行；維度小表關聯可用 lookup 運算子取代 leftouter join，效能更好。
  • 2026 新考點 今天這套 KQL 會在新考點裡反覆出現：Sentinel data lake 的 KQL jobs（對資料湖層排程跑 KQL）、summary rules（用 KQL 聚合高量資料）都是同一套語法，Day 10 詳談——語法基本功就是今天練的這些。
🎯 考點聚焦
題幹給你一段含 join 的偵測查詢，問「哪種規則類型可以直接使用」——NRT 立刻淘汰（單表限制），答案往排程規則走；反過來問「為什麼 NRT 規則儲存失敗」，先檢查查詢裡有沒有 join／union／跨工作區。另一個變形：問自訂偵測規則存不了，八成是 summarize 後遺失 Timestamp／ReportId／實體欄位。把「語法正確 ≠ 平台接受」這件事記牢。

QUESTION 1 · D3-0006
A security operations analyst runs the following query in advanced hunting: IdentityLogonEvents | join (DeviceLogonEvents) on AccountName. No kind parameter is specified. Which join flavor does KQL apply by default?
（安全性作業分析師在進階搜捕執行查詢：IdentityLogonEvents | join (DeviceLogonEvents) on AccountName，未指定 kind 參數。KQL 預設會套用哪一種 join？）
A. inner — every matching pair of rows from both tables is returned
inner——左右兩表每一組配對的資料列都會輸出
B. innerunique — duplicate keys on the left table are deduplicated before matching
innerunique——左表鍵值先去除重複，再與右表配對
C. leftouter — all left-table rows are kept, unmatched right columns are null
leftouter——左表資料列全部保留，配不到的右表欄位補空值
D. fullouter — all rows from both tables are kept
fullouter——左右兩表的資料列全部保留
看正解與解析
正解：B

KQL 的 join 未指定 kind 時，預設是 innerunique：左表相同鍵值的重複列會先被去重（每個鍵值僅隨機保留一列），再與右表做 inner 式配對。因此輸出筆數常比預期少，這是搜捕查詢與考試的高頻陷阱——需要逐筆配對時必須明確寫 kind=inner。

  • A：inner 會保留左表所有重複鍵值並逐筆配對，但它不是預設值——必須明確指定 kind=inner 才會使用。
  • C：leftouter 保留左表全部資料列並為未配對列補空值，屬於必須明確指定的 kind，不是預設行為。
  • D：fullouter 保留兩表所有資料列，是最寬鬆的 kind，同樣必須明確指定，並非預設。

QUESTION 2 · D3-0007
You are hunting for accounts that signed in successfully but have never registered for MFA. You build: SigninLogs | where ResultType == 0 | join kind=??? (MfaRegisteredUsers) on UserPrincipalName. You need to return only the sign-in rows for users that have NO matching row in MfaRegisteredUsers. Which join kind should replace ????
（你要搜捕「成功登入但從未註冊 MFA」的帳號，查詢為：SigninLogs | where ResultType == 0 | join kind=??? (MfaRegisteredUsers) on UserPrincipalName。你需要只回傳「在 MfaRegisteredUsers 中沒有配對列」的登入紀錄。??? 應填入哪一種 join kind？）
A. leftouter
leftouter
B. inner
inner
C. leftsemi
leftsemi
D. leftanti
leftanti
看正解與解析
正解：D

題幹關鍵字是「沒有配對列（NO matching row）」：leftanti 只保留左表中配不到右表的資料列，正好回傳「有登入、但不在 MFA 已註冊清單」的帳號。解題口訣：找『缺席／不存在於另一表』→ leftanti。

  • A：leftouter 會保留左表全部資料列（配到與配不到都輸出），還需要再加一段 where isempty(...) 過濾才能達成目的，不是最直接的答案。
  • B：inner 只保留「兩表都有」的配對列，回傳的是已註冊 MFA 的使用者登入，與需求正好相反。
  • C：leftsemi 保留的是「配得到」右表的左表列（右表當過濾清單），同樣與『沒有配對』的需求相反；它的反義才是 leftanti。

QUESTION 3 · D3-0008
An analyst runs: DeviceEvents | extend Status = AdditionalFields.SigningStatus | where isnotempty(Status). The query returns zero rows even though AdditionalFields visibly contains JSON with a SigningStatus property. The AdditionalFields column is typed as string. How should the analyst fix the query?
（分析師執行：DeviceEvents | extend Status = AdditionalFields.SigningStatus | where isnotempty(Status)。雖然 AdditionalFields 內容明顯是含 SigningStatus 屬性的 JSON，查詢卻回傳零筆。該欄位的型別是 string。分析師應如何修正查詢？）
A. Use extend Status = tostring(todynamic(AdditionalFields).SigningStatus) to convert the string to dynamic before accessing the property
改為 extend Status = tostring(todynamic(AdditionalFields).SigningStatus)，先把字串轉成 dynamic 再取屬性
B. Use extend Status = tostring(AdditionalFields).SigningStatus to cast the column first
改為 extend Status = tostring(AdditionalFields).SigningStatus，先轉型再取屬性
C. Use extend Status = split(AdditionalFields, ",") to break the JSON into fields
改為 extend Status = split(AdditionalFields, ",")，把 JSON 切成多個欄位
D. Use summarize make_set(AdditionalFields) to expand the JSON properties
改為 summarize make_set(AdditionalFields) 展開 JSON 屬性
看正解與解析
正解：A

型別為 string 的欄位即使內容是 JSON，也不能直接用點語法取屬性——會靜默回傳空值而非報錯。正確做法是先用 todynamic()（同 parse_json()）把字串轉成 dynamic 物件，再以 .SigningStatus 取屬性，最後用 tostring() 轉回純量型別以便比對與聚合。口訣：先轉 dynamic、再取屬性、再轉回純量。

  • B：tostring() 的輸出仍是 string，對字串做 .SigningStatus 屬性存取一樣拿到空值，問題完全沒有解決。
  • C：split() 只依分隔符把字串切成陣列，不會解析 JSON 結構，無法以屬性名稱取值；逗號也可能出現在 JSON 值內造成錯切。
  • D：make_set() 是聚合函式，把多列值收成去重陣列，與解析單一欄位內的 JSON 屬性無關。

QUESTION 4 · D3-0009
An analyst builds a time-series hunt: SigninLogs | make-series FailedCount = count() default = 0 on TimeGenerated from ago(14d) to now() step 1h by UserPrincipalName | extend (Anomalies, Score, Baseline) = series_decompose_anomalies(FailedCount, 2.5). What does the Anomalies output contain for each user?
（分析師建立時間序列搜捕查詢：SigninLogs | make-series FailedCount = count() default = 0 on TimeGenerated from ago(14d) to now() step 1h by UserPrincipalName | extend (Anomalies, Score, Baseline) = series_decompose_anomalies(FailedCount, 2.5)。每個使用者的 Anomalies 輸出內容是什麼？）
A. A list of datetime values containing only the anomalous time bins
只包含異常時段之 datetime 值的清單
B. The expected baseline value calculated for the whole series
整條數列計算出的預期基線值
C. A dynamic array aligned to every time bin, with 1, 0, or -1 marking a positive anomaly, no anomaly, or a negative anomaly
與每個時間格對齊的 dynamic 陣列，值為 1、0 或 -1，分別代表正向異常、無異常、負向異常
D. A single number representing the total count of anomalies detected
代表偵測到的異常總數的單一數值
看正解與解析
正解：C

series_decompose_anomalies() 回傳三個與輸入數列「逐格對齊」的陣列：Anomalies 每格標 1（高於基線的正向異常）、0（正常）或 -1（低於基線的負向異常）；Score 是異常分數；Baseline 是預期基線值。因為輸出是陣列，後續通常要用 mv-expand 展開成一列一時段，再以 where Anomalies == 1 篩出異常時點。

  • A：Anomalies 陣列涵蓋『所有』時間格（正常時段為 0），不是只列出異常時段的時間清單；要取得異常時點需 mv-expand 後再過濾。
  • B：預期基線值是第三個輸出 Baseline 的內容，不是 Anomalies。
  • D：函式不會輸出異常總數的單一數值；若要總數，需自行對展開後的結果做 summarize count()。

QUESTION 5 · D3-0010
You are investigating suspected lateral movement after a phishing campaign. You run: let Phished = EmailEvents | where ThreatTypes has "Phish" and DeliveryAction == "Delivered" | distinct RecipientEmailAddress; IdentityLogonEvents | where Timestamp > ago(3d) | where AccountUpn in~ (Phished) | summarize arg_max(Timestamp, *) by AccountUpn. What does this query return?
（你在網釣行動後調查疑似橫向移動，執行：let Phished = EmailEvents | where ThreatTypes has "Phish" and DeliveryAction == "Delivered" | distinct RecipientEmailAddress; IdentityLogonEvents | where Timestamp > ago(3d) | where AccountUpn in~ (Phished) | summarize arg_max(Timestamp, *) by AccountUpn。此查詢會回傳什麼？）
A. Every logon event in the last 3 days for each account that received a delivered phishing email
每個收到已送達網釣郵件之帳號，最近 3 天內的全部登入事件
B. For each phished account that logged on in the last 3 days, the single most recent logon row including all its columns
每個最近 3 天內有登入的受網釣帳號，各回傳時間最新的那一列登入紀錄（含該列所有欄位）
C. For each phished account, the earliest logon row in the period, which reveals the start of the lateral movement
每個受網釣帳號在期間內最早的一列登入紀錄，可看出橫向移動的起點
D. The total number of logons per phished account in the last 3 days
每個受網釣帳號最近 3 天內的登入總次數
看正解與解析
正解：B

let 先以 distinct 建立「已送達網釣郵件」的收件者清單；in~ 做不分大小寫的清單比對，篩出這些帳號的登入事件；關鍵在 summarize arg_max(Timestamp, *) by AccountUpn——每個帳號分一組，取組內 Timestamp 最大（最新）的那一列，星號代表把該列所有欄位完整輸出。因此結果是「每個受害帳號各一列：其最近一次登入的完整紀錄」，適合快速確認每個帳號最後出現的位置與方式。

  • A：summarize arg_max(...) by AccountUpn 會把每個帳號聚合成單一列（最新那筆），不會保留全部登入事件；要全部事件就不該加這段 summarize。
  • C：取「最早一筆」是 arg_min(Timestamp, *) 的行為；本查詢用的是 arg_max，回傳最新一筆。
  • D：計算登入總次數是 summarize count() by AccountUpn 的行為；arg_max 回傳的是整列紀錄，不是次數。
