01 — 📌 本日導讀

本日導讀：讓 Sentinel 自己動手

前兩天把分析規則寫完了——偵測有了，事件也產得出來。但真實 SOC 的痛點從來不是「偵測不到」，而是「人來不及處理」：一天三百張事件，每張都要指派、標記、通知、開工單。今天學的 SOAR（安全性協調、自動化與回應）就是解法，在 Microsoft Sentinel 裡分成兩層：自動化規則（automation rule）負責事件層的分流與治理，劇本（Playbook）負責跑出去跟外部系統打交道。D2「回應安全性事件」占 35–40%，這個主題的考題幾乎都長同一個樣子：四個選項都做得到，要你選「管理負擔最低」或「成本最低」的那一個。所以重點不只是兩者能做什麼，更是邊界在哪。

學習目標（對應官方考綱 D2「回應安全性事件」條目）：
  • ☐ 設定與管理自動化規則：觸發時機、條件、動作與執行順序
  • ☐ 以 Azure Logic Apps 建立與設定 Sentinel 劇本（create and configure playbooks）
  • ☐ 選擇正確的 playbook 觸發程序（incident／alert／entity trigger）並理解各自可取得的資料
  • ☐ 設定自動化所需權限：Microsoft Sentinel Automation Contributor、受控識別與連線授權
  • ☐ 判斷何時用自動化規則、何時用劇本，並與 Defender XDR 的自動調查與修復（AIR）分工

03 — ⚙️ 自動化規則拆解

自動化規則：事件佇列的家規

自動化規則是事件層的 if-then：符合條件就對事件做幾件標準動作。它跑在 Sentinel 內部，不必另建資源、不額外計費，是自動化的第一選擇。一條規則由四部分組成：觸發時機 → 條件 → 動作 → 順序與到期日。

觸發時機（trigger）何時開跑條件重點可用動作
事件建立時
When incident is created		新事件產生當下，含 Defender XDR 送進來的事件標題、嚴重性、狀態、戰術、擁有者、產品名稱、分析規則名稱、標籤、實體屬性、自訂詳細資料變更狀態／嚴重性、指派擁有者、加標籤、新增事件工作、執行劇本
事件更新時
When incident is updated		事件被修改後（狀態或擁有者變更、加入新警示或註解）上述全部，再加上「變更了什麼」與「由誰更新」同上
警示建立時
When alert is created		排程分析規則產生警示時，不等事件成形以警示屬性為主，通常限定特定分析規則只有「執行劇本」一種——警示沒有狀態、擁有者可改

條件用「屬性－運算子－值」堆疊，運算子有等於／不等於、包含／不包含、開頭為／結尾為；條件之間是 AND，同一條件的多值之間是 OR。最常用兩種寫法：用分析規則名稱鎖定來源，以及用實體屬性鎖定資產（例如帳戶名稱包含 svc- 的服務帳戶）。

💡 最被低估的用途是雜訊抑制：把已知誤判自動關閉，狀態設 Closed 並填上分類（Benign positive／False positive）與理由。考題關鍵字 suppress、reduce noise、automatically close 全部指向自動化規則，不是劇本、更不是刪掉分析規則。

執行順序（order）最容易失分。同一觸發時機下，多條規則依 order 由小到大依序執行，且前一條造成的變更會被後一條看見。典型災難：第 1 條把低嚴重性事件關閉，第 2 條想把同批事件指派給分析師——結果指派到一堆已關閉的事件。正確設計是先抑制（關閉／降級），再指派與加標籤，最後才跑耗時的劇本。另外「事件更新時」的條件寫太寬，可能被規則自己造成的更新再度命中，要用條件把自己排除。

到期日（expiration date）：建立時可指定未來時間，時間一到規則自動失效，專為暫時性需求設計——滲透測試期間抑制特定告警、維護時段自動關閉預期中的警示。考題問「如何避免忘記關掉臨時規則」，答案是到期日。

04 — 🎭 劇本與 Logic Apps

Playbook：需要請外援的時候

劇本就是一個 Azure Logic Apps 工作流程，開頭是 Sentinel 觸發程序，後面接一連串連接器動作。自動化規則只能改事件欄位，劇本才能走出 Sentinel：發 Teams 訊息、寄核准信、開 ServiceNow 工單、叫防火牆封鎖 IP、叫 Defender for Endpoint 隔離裝置、停用 Microsoft Entra ID 帳戶、查威脅情報再寫回註解。方案有兩種：Consumption（多租用戶）按動作執行次數計費，適合量少；Standard（單一租用戶）按主控方案資源計費，可放多個工作流程並支援虛擬網路整合，量大時較划算。

觸發程序（trigger）拿得到的資料怎麼啟動典型場景
事件觸發程序
incident trigger		整張事件物件：事件屬性、所有相關警示、所有實體、註解與標籤由自動化規則呼叫（事件建立／更新時），或在事件頁手動執行主力用法：通知、開工單、逐一擴充實體、依嚴重性決定是否升級
警示觸發程序
alert trigger		單一警示與其實體；沒有事件層欄位（無擁有者、無事件註解）由「警示建立時」的規則呼叫，或從分析規則的舊版警示自動化掛載不等事件成形就要動作；或合併成一張事件的多筆警示要各處理一次
實體觸發程序
entity trigger		單一實體（帳戶、主機、IP、URL、檔案雜湊）的屬性只能手動執行：從實體清單、調查圖表或搜捕結果執行，不能掛自動化規則隨選擴充與處置：查這個 IP 的信譽、隔離主機、撤銷帳戶權杖
💡 口訣：incident＝自動跑、資料最全；alert＝自動跑、只看得到一張警示；entity＝資料最少、但只能人工按下去。題幹出現「在調查圖表上針對某個 IP 隨選執行」＝實體觸發程序；「事件一建立就自動通知」＝事件觸發程序＋自動化規則。

可靠性與成本：每次執行都留在 執行歷史，可展開每個動作的輸入輸出看是哪一步失敗，修好後能重新提交（resubmit）；個別動作可設重試原則與逾時。成本上記住：自動化規則不計費，劇本才產生 Logic Apps 費用，Consumption 又是按動作數算的——包二十個動作又被每張事件觸發的劇本帳單很有感。

🎯 考點聚焦

「最低管理負擔／最少工作量」題型的判斷梯子。看到 least administrative effort、minimal effort、least cost，照這個順序往下走：
(1) 需求只是改事件欄位嗎？（關閉、改嚴重性、指派、加標籤、加工作）→ 自動化規則，不要建劇本。
(2) 需要跟 Sentinel 以外的系統互動嗎？（寄信、Teams、工單、封鎖、隔離、查外部情報）→ 劇本，而且用自動化規則掛載，不用分析規則裡的舊版警示自動化，因為前者能集中管理條件與順序。
(3) 要現成的嗎？→ 從 Content hub 匯入劇本範本再改，而不是從空白工作流程自己刻。
陷阱選項常是「寫一支 Azure Function」「用 Automation 帳戶跑 PowerShell Runbook」——技術可行但管理負擔明顯更高，best answer 題型一律出局。

05 — 🔑 自動化的權限模型

三層權限：誰授權、誰執行、對誰動手

「劇本手動跑得動、掛到自動化規則就不動」是最經典的實務與考試場景，原因幾乎都在權限。拆成三層背：

  • 第一層：Sentinel 有沒有權限執行這本劇本。自動化規則是由 Microsoft Sentinel 服務主體代跑劇本，必須把 Microsoft Sentinel Automation Contributor 角色授與該服務主體，範圍是存放劇本的資源群組；入口網站上就是 Automation 頁面的「管理劇本權限（Manage playbook permissions）」。沒做這一步，劇本會在下拉選單裡呈灰色或執行失敗。
  • 第二層：劇本有沒有權限動目標系統。劇本裡每個連接器都有自己的連線授權，主流做法是受控識別（managed identity）：為邏輯應用程式開啟系統指派的受控識別，再把它加上目標資源的角色，例如要更新事件、加註解就需要工作區上的 Microsoft Sentinel Responder。傳統的使用者帳戶連線會過期、會綁在離職員工身上，考題偏好受控識別的理由就是「不必管理認證」。
  • 第三層：操作的人有沒有權限。要把劇本掛上規則、或在事件頁手動執行，操作者需對劇本所在資源群組具備 Logic App Contributor 之類權限，並在 Sentinel 端至少是 Responder。「看得到事件卻執行不了劇本」通常在這層。

跨訂用帳戶與跨租用戶：劇本與工作區可不在同一訂用帳戶，只要在劇本所在資源群組完成第一層授權即可；跨租用戶（MSSP 幫客戶管理）要靠 Azure Lighthouse 委派管理權限並在委派範圍指派相同角色。題幹出現 MSSP、多租用戶、delegated，Lighthouse 就是答案的一部分。

🎯 考點聚焦

「劇本跑不動」的排查順序（照著背，題目換皮也不怕）：
① 劇本在自動化規則的下拉選單看不到／灰色 → Sentinel 服務主體缺 Automation Contributor（管理劇本權限沒做），或觸發程序不對——只有事件觸發程序的劇本能掛在「事件建立／更新時」規則上，實體觸發程序的劇本永遠不會出現。
② 規則有跑、劇本執行失敗 → 進執行歷史看紅色那一步：多半是連線認證過期，或受控識別缺目標資源角色（要更新事件卻沒有工作區的 Microsoft Sentinel Responder）。
③ 劇本成功、事件卻沒變 → 動作參數綁錯欄位或條件分支沒進去，用執行歷史比對輸入輸出。
④ 規則完全沒被觸發 → 條件寫太嚴、來源產品不符、規則已過期或停用，或 order 前面有規則先把事件關掉了。

06 — ⚖️ 該用哪一個

自動化規則 vs 劇本：決策表

比較面向自動化規則（automation rule）劇本 Playbook（Logic Apps）
能做什麼只動事件本身：變更狀態（含分類與理由）、變更嚴重性、指派擁有者、加標籤、新增事件工作、執行劇本幾乎什麼都行：通知、核准流程、工單、封鎖 IP、隔離裝置、停用帳戶、查外部情報、寫回註解
條件與分支單層 AND 條件，沒有 if／else、沒有迴圈完整流程控制：條件、迴圈（逐一處理實體）、平行分支、等待人工核准
成本不額外計費依 Logic Apps 計費：Consumption 按動作執行次數、Standard 按主控方案資源
管理負擔低：表單幾分鐘完成，集中在 Automation 頁面管理與排序高：要設計流程、管理連線與受控識別、監看執行歷史與失敗重試
失敗與除錯幾乎不會失敗，頂多條件沒命中會失敗：認證過期、API 逾時、參數錯誤；靠執行歷史與重新提交處理
典型場景雜訊抑制、自動分派、依戰術加標籤、當自動化的統一入口釣魚通報處理、封鎖與隔離、值班通知、工單同步、實體擴充

一句話：自動化規則像家規，劇本像請外援。家規免費、立刻生效，但只管得到自己家裡的事；外援什麼都辦得到，可是要付錢、要授權、還可能請不動。實務上兩者搭配而非二選一——用自動化規則當唯一入口，由它決定哪些事件跑哪本劇本、以什麼順序跑。

與 Defender XDR 端自動化（AIR）的分工也常入題：AIR 在 Defender 內部自動調查警示，對端點、信箱、身分執行清理型修復（隔離檔案、移除郵件、停止處理程序），動作留在 Action center 可核准與復原；Sentinel 自動化則站在事件層與跨系統層，處理通報、工單、非微軟設備的封鎖與流程治理。健康的設計是讓 AIR 做微軟生態內的即時清理、Sentinel 做跨系統協調，重複動作只留一邊。

07 — 🧪 端到端演練

釣魚事件的全自動處理鏈

🧪 實戰情境：釣魚事件從觸發到封鎖

分析規則「Suspicious inbox forwarding + credential phishing」在凌晨產生高嚴重性事件，實體含使用者 anna@contoso.com、一個外部 IP 與一條 URL。夜班只有兩人——整條鏈這樣設計：

  1. 自動化規則（order 10）「已知誤判抑制」：條件為分析規則名稱等於此規則、且標籤包含 known-simulation（釣魚演練）。命中就關閉為 Benign positive。本次未命中，往下走。
  2. 自動化規則（order 20）「釣魚事件分派」：條件為戰術包含 Initial Access 且嚴重性 High。動作依序：指派擁有者給夜班群組、加標籤 phishing、新增事件工作「確認使用者是否輸入認證」，最後執行劇本。
  3. 劇本第一段：擴充。事件觸發程序取得完整事件物件 → 迴圈逐一取出實體 → 查 IP 與 URL 信譽、取得使用者部門與主管 → 結果寫回事件註解（需受控識別具備工作區的 Microsoft Sentinel Responder）。
  4. 劇本第二段：通知與核准。發 Teams 自適應卡片到 SOC 頻道，附摘要與兩個按鈕，流程停在等待核准。分析師看完按下「封鎖」。
  5. 劇本第三段：處置。核准分支往下：呼叫 Defender for Endpoint 把 IP 與 URL 加入封鎖指標、呼叫 Microsoft Entra ID 撤銷重新整理權杖並要求重設密碼、開 ServiceNow 工單並把編號寫回註解。若按「誤判」則走另一分支，關閉事件並加上 known-simulation 標籤——下次同類事件在第 1 步就被抑制。
  6. 隔天檢視。事件活動記錄看得到「由自動化規則執行」的每一步；劇本那側到執行歷史核對，發現 ServiceNow 動作曾逾時一次、由重試原則自動成功。夜班人工作業從 20 分鐘壓到一次點擊。
🎯 考點聚焦

三個常考切點。(1) 「封鎖前要人確認」 → 人工核准分支是劇本的能力，自動化規則做不到。(2) 「同一張事件跑多條規則」 → 抑制型規則要排最前面（order 小），否則後面的指派與劇本白跑，甚至對已關閉的事件寄通知。(3) 「要對每個實體各做一次」 → 事件觸發程序拿得到實體清單，用迴圈處理；「不等事件建立、只處理單一警示中的實體」才是警示觸發程序；「在調查圖表上針對這個帳戶隨選撤銷權杖」則是實體觸發程序，只能手動執行。

08 — 🧩 考綱補洞

影片之外，考綱還要你會這些

  • 舊版警示自動化 vs 自動化規則：分析規則精靈仍保留 alert automation（classic）可直接掛劇本，但官方建議全部改用自動化規則統一管理。考題問「如何集中管理散落在各分析規則的劇本」，答案就是改掛自動化規則。
  • 事件工作（incident tasks）：自動化規則可自動為事件加上待辦清單（通知資料擁有者、確認 MFA 狀態），讓分析師照同一份 SOP 走，是「標準化回應流程」題型的答案之一。
  • 手動執行劇本：事件頁與警示頁都能隨選執行劇本，這也是驗證權限與參數的最快方式——手動跑得動、自動跑不動＝Sentinel 服務主體的權限問題。
  • Defender 入口網站整合：Sentinel 併入 Defender 入口網站後，自動化規則同樣作用在統一事件佇列（含 XDR 來源事件），要留意「XDR 已自動處理過的事不要再做一次」。
  • 連接器生態：劇本能用的就是 Logic Apps 全部連接器——ServiceNow、Jira、Slack、第三方防火牆、自訂 HTTP 呼叫都在內。「能不能跟我們的工單系統整合」答案永遠是「用劇本」。
  • Security Copilot 與自動化 2026 新考點：Logic Apps 已有 Security Copilot 連接器，可在劇本中執行提示或提示手冊，把事件摘要與建議動作寫回註解；Defender 端則有代理程式（例如釣魚分類代理程式）自動分類使用者回報的釣魚信。考題方向是「不增加人力下提升分診品質」。
