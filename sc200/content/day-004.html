03 — 🗺️ 統一入口整合地圖

defender.microsoft.com 收編了什麼

Microsoft Defender XDR（XDR）統一入口網站把過去四、五個獨立安全性入口收整成一站。首先把「舊入口 → 新位置」的對照背起來，考題描述舊入口名稱時你才不會迷路：

功能原產品／原入口統一入口後的位置
端點警示、裝置清查、弱點管理Microsoft Defender for Endpoint（MDE）— securitycenter.windows.com統一事件佇列＋「資產 > 裝置」＋「端點」設定區
郵件威脅調查（Threat Explorer）、隔離區Microsoft Defender for Office 365（MDO）— protection.office.com「電子郵件與共同作業」區
身分識別偵測、橫向移動路徑Microsoft Defender for Identity（MDI）— 獨立 ATP 入口統一事件佇列＋「資產 > 身分識別」
雲端應用程式可見性與控制Microsoft Defender for Cloud Apps（MDA）獨立入口「雲端應用程式」區
SIEM：分析規則、資料連接器、自動化Microsoft Sentinel — Azure portal統一事件佇列＋「Microsoft Sentinel」導覽區 2026 新考點
跨產品查詢各產品各自的搜尋／查詢頁單一「進階搜捕」：一條 KQL 同時查 Device*、Email*、Identity*、CloudApp* 資料表

整合的本質可以濃縮成三件事：事件佇列合併（跨產品警示自動關聯成單一事件，分析師分診一個事件就能看到完整攻擊故事）、進階搜捕跨產品（一條查詢跨所有訊號來源）、統一設定（通知、權限、保留期集中管理）。舉一段跨產品查詢感受一下——追查「釣魚郵件附件在端點被執行」，過去要跨兩個入口，如今一條 KQL：

EmailAttachmentInfo
| where Timestamp > ago(7d)
| where FileType == "exe"
| join kind=inner (
    DeviceProcessEvents
    | where Timestamp > ago(7d)
  ) on SHA256
| project Timestamp, RecipientEmailAddress, FileName, DeviceName, InitiatingProcessFileName

EmailAttachmentInfo 是 MDO 的訊號、DeviceProcessEvents 是 MDE 的訊號，以 SHA256 做 inner join——「郵件裡的附件雜湊」對上「端點上執行的程序雜湊」，就是附件落地執行的證據。這種跨表關聯只有統一入口的進階搜捕辦得到，是考題最愛的「為什麼要用統一入口」情境。

統一設定：通知、功能開關、資料保留

  • 通知與電子郵件設定：在設定區可建立事件與警示的電子郵件通知規則——依嚴重性、裝置群組或服務來源篩選，寄給指定收件者；弱點管理也有獨立的通知規則。考點：通知規則是「設定」，需要有設定管理權限的角色才能建立。
  • 功能開關（preview features）：預覽功能是租用戶層級的單一開關，打開後才看得到最新功能。考 2026 新功能時，題幹偶爾會提「已啟用預覽功能」當前提。
  • 資料保留設定：Defender XDR 的警示與事件資料預設保留 180 天；進階搜捕可查詢的原始資料是 30 天。端點資料保留期可在設定中調整（30–180 天）。要留更久做長期搜捕？那是 Sentinel／data lake 的工作——Day 10 會講。
04 — 🔐 統一 RBAC 深入

一套自訂角色模型，管到所有工作負載

入口統一了，權限也要統一。過去 MDE 有自己的角色、MDO 權限藏在 Exchange Online、MDI 用 Entra 群組——三套模型三種邏輯。Microsoft Defender XDR 統一 RBAC 用一個自訂角色模型取代它們：一個角色、一次指派，套用到你選擇的多個工作負載（workload）。

自訂角色的權限從三大權限群組勾選，這個結構要記熟：

權限群組涵蓋權限（節錄）給誰
安全性作業（Security operations）安全性資料基本（讀取）、警示（管理）、回應動作：即時回應（Live Response）、進階修復動作、檔案收集、電子郵件與共同作業修復分析師：讀資料、分診、做回應
安全性態勢（Security posture）弱點管理（讀取／例外處理／修復處理）、Secure Score（讀取／管理）弱點管理與態勢團隊
授權與設定（Authorization and settings）授權（管理角色與指派）、安全性設定、系統設定SOC 管理者／工程師——這一組等於「可以改環境」

建立自訂角色的流程：建立角色 → 勾選權限 → 建立指派（assignment）。每個指派包含三個要素：指派給誰（Entra 使用者或群組）、資料來源（套用到哪些工作負載：MDE、MDO、MDI、MDA⋯⋯）、範圍（MDE 可進一步限縮到特定裝置群組）。一個角色可以有多個指派——例如同一組「分診權限」，指派 A 給台北團隊管台北的裝置群組、指派 B 給倫敦團隊管歐洲的裝置群組。

啟用與遷移：統一 RBAC 是「按工作負載啟用（activate）」的。某個工作負載一旦啟用，該產品的舊 RBAC 角色立即停止生效，只認統一 RBAC。因此正確順序是：先用「匯入角色」功能把 MDE／MDO 等既有角色匯入統一 RBAC、檢查對應無誤，再逐一啟用工作負載。另外有一條保命規則：Entra 的 Global Administrator 與 Security Administrator 不受啟用影響，永遠保有完整存取——所以永遠不會發生「全員被鎖在門外」。

🎯 考點聚焦
「最小權限該選哪個角色」的答題公式：先抓題幹兩個訊號——（1）需要做什麼：只看＝讀取、分診改狀態＝警示（管理）、隔離裝置＝回應動作、建通知規則或改功能＝授權與設定；（2）需要管到哪：全租用戶還是特定裝置群組。然後套用鐵律：Global Administrator 永遠不是最小權限的正解；題目說「不可變更設定」就刪掉 Security Administrator；題目要求「限縮到某些裝置群組」或「只給部分工作負載」，Entra 內建角色一律做不到，答案必是統一 RBAC 自訂角色。
05 — ⚖️ Entra 角色 vs 統一 RBAC

內建角色何時夠用、何時該自訂

Entra ID 內建角色是「快速起步」方案：指派一次，所有安全性入口都認得。統一 RBAC 是「精細治理」方案。比較如下：

面向Entra 內建角色統一 RBAC 自訂角色
粒度粗：整個租用戶、所有產品一體適用細：權限 × 工作負載 × 範圍（裝置群組）三維控制
管理位置Entra ID（Microsoft Entra 系統管理中心）Defender portal 的「權限」設定
常用角色Security Reader（唯讀）／Security Operator（管理警示與事件、執行調查回應）／Security Administrator（前者＋管理安全性設定）自行組合三大權限群組
能否限裝置群組不能能（MDE 資料來源可設範圍）
適用情境小團隊、職能單純、全域授權可接受大型 SOC 的 tier 分層、MSSP、最小權限稽核要求

記法：Reader 看、Operator 動手、Admin 動設定。三個內建角色是同心圓，一圈比一圈大；自訂角色則是把圓切成扇形，要哪塊給哪塊。

🛡️ 實戰情境：新進 Tier-1 分析師的角色決策

你是 SOC 的權限管理者。新進 tier-1 分析師 Amy 下週報到，需求是：檢視事件、變更事件狀態與指派、加註解——但不可變更任何入口設定。走一遍決策：

  1. Security Reader 夠嗎？不夠。Reader 是唯讀，Amy 改不了事件狀態、做不了指派——分診工作直接卡死。
  2. Security Administrator？過頭了。它包含管理安全性設定的權限，違反「不可改設定」的限制條件，最小權限原則直接淘汰。
  3. Security Operator？可以動事件、不能改設定——需求全中。若團隊小、不要求限縮範圍，這就是答案。
  4. 還要更嚴？注意 Security Operator 也帶著「執行回應動作」的能力（例如隔離裝置）。如果政策規定 tier-1 只能分診、回應動作留給 tier-2，就改用統一 RBAC 自訂角色：勾「安全性資料基本（讀取）」＋「警示（管理）」，不勾任何回應動作、不碰「授權與設定」，指派範圍限 tier-1 負責的裝置群組。

結論：考題只給「分診＋不可改設定」→ 選 Security Operator；題幹多了「不得執行回應動作」或「僅限特定裝置群組」→ 選統一 RBAC 自訂角色。條件多一個，答案就換一個。

06 — 🏢 多租用戶與 MSSP

一個分析師，看很多租用戶

MSSP（託管安全服務供應商）或多租用戶集團的痛點：分析師要在十幾個租用戶之間切換。Defender 的解法有兩層：

  • 多租用戶入口（multi-tenant portal，mto.security.microsoft.com）：把你有權存取的多個租用戶聚合成單一檢視——跨租用戶的事件佇列、跨租用戶的進階搜捕（同一條查詢同時打向多個租用戶）、以及內容管理（把自訂偵測規則同步到多個租用戶）。它不是新的權限系統，你在每個租用戶裡有多少權限，聚合檢視就顯示多少。
  • 存取怎麼來：GDAP（granular delegated administrative privileges，細緻委派系統管理權限）。CSP 夥伴透過 Partner Center 與客戶建立 GDAP 關係：指名特定 Entra 角色（例如只給 Security Operator）、有時效（到期須重新核可）、可稽核。它取代了舊制 DAP（預設近乎全域管理員的委派，權限過廣，已淘汰）。企業內部的跨租用戶存取則常用 Entra B2B 邀請＋各租用戶內指派角色。
🎯 考點聚焦
MSSP 題的正解長相：題幹說「MSSP 需要以最小權限、可時效控管的方式存取客戶租用戶」→ 正解是 GDAP。干擾項套路：DAP（真實存在但已淘汰、權限過廣）、在客戶租用戶建 Global Administrator 帳號（違反最小權限）、共用帳號（違反可歸責性）。另一型：「分析師要在單一檢視分診多個租用戶的事件」→ 正解是多租用戶入口，干擾項會是「輪流登入各租用戶」或「把所有記錄集中到單一工作區」（可行但題目問的是 Defender 原生的聚合檢視）。
07 — 🛰️ Sentinel 進 Defender portal

統一 SOC 平台 2026 新考點

XDR 管「微軟訊號」，SIEM 管「所有訊號」——過去這兩個世界分屬兩個入口。把 Microsoft Sentinel 工作區連入（onboard）Defender portal 之後，兩者合體為統一 SOC 平台：

  • 單一事件佇列：Sentinel 分析規則產生的事件與 XDR 事件進同一條佇列，關聯引擎會把相關警示歸進同一事件。
  • 單一進階搜捕：同一個查詢介面同時查 XDR 資料表與 Sentinel 工作區的資料表（含第三方記錄），跨來源 join 不用換入口。
  • 自動化與 AI 同棚：Sentinel 的自動化規則、劇本（Playbook）照常運作，Security Copilot 的事件摘要與引導式回應也在同一入口。

2026 年的關鍵事實：Azure portal 中的 Sentinel 體驗已進入退場時程（2026 年 7 月起以 Defender portal 為唯一主要體驗），且新一代能力——Sentinel data lake、Sentinel Graph、Sentinel MCP Server——都只在統一平台上提供。考題若問「該在哪裡操作 Sentinel」或「如何取得單一事件佇列」，方向一律是把工作區連入 Defender portal。連入動作本身需要工作區層級的足夠授權（例如工作區的 Owner），連入後的日常操作權限仍由 Sentinel 的 Azure RBAC 角色與統一 RBAC 各管各的資源。

一句話記憶：「XDR 給你深度（微軟產品訊號的自動關聯），Sentinel 給你廣度（任何來源的記錄），統一 SOC 平台讓兩者共用同一條佇列、同一個搜捕介面。」明天開始逐一部署這些訊號來源，第一站就是 MDE。
08 — 🧩 考綱補洞

EP1 沒講透、考試會考的

EP1 是全景導覽，以下考綱項目影片著墨有限，本文已補講、這裡做最後確認：

  • 統一 RBAC 啟用順序：先匯入既有角色 → 檢查 → 再逐工作負載啟用；啟用後舊產品 RBAC 即失效；Global Administrator／Security Administrator 不受影響（§04）。
  • 通知規則、預覽功能、資料保留：三者都在統一設定區；事件通知可依嚴重性與裝置群組篩選；XDR 事件資料保留 180 天、進階搜捕原始資料 30 天（§03）。
  • Entra 三角色分界：Reader 看、Operator 動手、Admin 動設定；要範圍限縮就轉統一 RBAC（§05）。
  • GDAP 取代 DAP：指名角色、有時效、可稽核（§06）。
  • 連入 Sentinel 工作區：考綱明列「設定從 Defender XDR 到 Sentinel 工作區的連線」——記住連入的效果（單一佇列、單一搜捕）與 2026 主要體驗的定位（§07）。
